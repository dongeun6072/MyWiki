# Slack #10_prj-orbis-navisdk 대화 (2026-05~10)

TomTom Orbis Map NaviSDK POC 공개 채널 `#10_prj-orbis-navisdk`의 2026-05-01~10-27 구간 기록이다(실제 메시지 범위는 2026-05-06~10-08). 프로젝트 허브는 [[orbis-sdk]], 이전 개발 흐름은 [[orbis-navisdk-development-2025]], 상용화 스크럼은 [[navisdk-commercialization-scrums-2025-2026]], 탐색 데이터 라이브러리는 [[orbis-route-data-lib]], 대만 개발은 [[orbis-taiwan-development-2026]]을 본다. 다른 기간 기록은 [[navisdk-prj-slack-2025-h1]], [[navisdk-prj-slack-2025-q3]], [[navisdk-prj-slack-2025-q4]], [[navisdk-prj-slack-2026-h1a]]에 있다.

구간 내 채널 메시지 24건(입장 알림 4건 포함)과 스레드 답글 90건을 모두 읽었다. 답글이 달린 스레드 15개를 전부 열었고 미열람은 0개다. 첨부는 파일명·종류만 기록했다(내용 미열람). 사람은 역할로 적었고, 서버 주소·포트·경로·링크·키·메일은 옮기지 않았다(링크 있음, 미수록).

## 1. 탐색엔진 Route Data Library v1.0.1.6와 Navi SDK 1.0.3 (5월)

- **2026-05-06 공지(개발 PM 수석)**: Orbis Route Data Library v1.0.1.6 배포로 탐색엔진 서버 포트 변경 작업이 필요하다. 현재는 포트 하나가 NaviSDK v1.0.1, 다른 포트가 v1.0.2에 대응한다. 라이브러리 v1.0.1.6을 적용해 Navi SDK v1.0.3을 배포하고, 이 버전을 v1.0.1 대응 포트에 올린다. 다른 포트는 v1.0.2 대응을 유지한다. 신규 탐색엔진 적용은 5월 18일, SDK와 Agent도 같은 날짜에 맞춰 진행하도록 요청했다.
- **05-06 답글(탐색엔진 담당 수석)**: 5월 18일에 휴가 일정이 있어 적용을 5월 19일로 진행한다.
- **05-13 답글(Agent 담당)**: Agent 개발기 반영 상태는 v1.0.1 대응 포트가 Navi SDK v1.0.3(라이브러리 v1.0.1.6), 다른 포트가 v1.0.2(라이브러리 v1.0.1.4)다. 앱 버전이 1.0.2, 1.0.3이 아닌 요청은 `NOT_SUPPORT_APP_VERSION` 응답 코드를 반환한다.
- **05-13 답글(개발 PM 수석)**: 멘션 누락으로 재공유한다. 라이브러리 v1.0.1.6이 적용된 MMC 엔진 발행이 필요하다. **05-14**: MMC(맵매칭) 엔진 담당 팀장이 5월 15일(금)까지 배포하겠다고 답했다.
- **05-19**: 개발 PM 수석이 탐색 신규 포트 작업 진행상황을 문의 -> 탐색엔진 담당 수석이 릴리즈 노트와 업데이트 상세 내역을 포함해 1시간 내 업데이트하겠다고 답하고, 14:36에 "INAVI Route Server for Taiwan (v2.1) 작업 완료"를 보고. 14:46 Agent 담당이 앱 버전 1.0.3 대응 Agent 적용을 완료했고 Swagger 테스트상 이상 없다고 보고.
- **05-22 SDK 배포(개발 PM 수석)**: Global Navi SDK 1.0.3(AOS aar `1.0.3`, iOS xcframework `v1.0.3`)과 Navi/Map SDK Flutter 플러그인(각 `1.0.0`, 수정 내역은 "Flutter Plugin 지원")을 배포했다. Navi/Map SDK 가이드는 개발가이드에 아직 연동되지 않아 링크로 업체에 안내하기로 했고 이후 연동할 예정이다.
- **05-27 Flutter 항목 추가**: Navi/Map SDK의 Flutter 배포 완료에 맞춰 개발자 사이트에 Flutter 항목이 필요해, 개발 PM 수석이 HTML을 작성해 전달했다(SDK 설명 내 "Flutter Plugin" 항목 추가, 이미지 `image006[56].png` 첨부, 다운로드 링크 있음·미수록). 웹서비스개발팀 담당이 16:29 개발서버에 반영했고, 개발 PM 수석이 문제 없다며 상용 반영을 요청, 17:31 상용 반영이 완료됐다.

- **05-19 답글(개발 PM 수석)**: 검토된 적이 없어 일단 법적고지 없이 진행하되, 지도 개발 담당 팀장이 TomTom 지도의 법적고지 표출 방식을 확인하고, 사업(전략)팀 과장이 법무팀이나 TomTom과 논의된 내용이 있는지 확인하도록 요청했다.
- **05-19 답글(지도 개발 팀장)**: TomTom이 공개한 2026-03판 제품 귀속(attribution) 고지 문서를 확인해 공유했다. 대만 항목은 경찰방송국 교통사고 데이터의 정부 공개 라이선스, 내정부 국토측량제도센터 원자료, DATA.GOV.TW의 Open Government Data License v1.0 데이터셋, 내정부 호정사(戶政司) 데이터셋 고지를 포함한다. Google 지도 고지 링크도 함께 공유했다(링크 미수록).
- **05-21 파트너십 계약서 조항(사업(전략)팀 과장)**: 계약서 제10조 제1항 제2호를 찾아 공유. "about box" 또는 법적고지 섹션에 TomTom 제공 데이터 사용 문구와 저작권·재산권 고지를 명시해야 하고, ODbL 데이터를 쓰면 OSM 재단 저작권과 Open Database License 문구를 추가해야 한다.
- **05-21 개발 PM 수석 제안**: 지도(Web, SDK) 로고 클릭으로 안내하기보다 개발 사이트에 "법적고지" 항목을 하나 만들어 위 문구를 싣고, 필요하면 로고 클릭 시 그 페이지로 연결하는 것이 가장 간단하다. 17:55 TomTom 확인 결과(사업(전략)팀 과장 전달): 고지 제공 방식은 당사 정책에 따라 결정 가능하며, 별도 Legal Notice 페이지 생성과 로고 클릭 연결 방향이 가능하다.
- **05-21 결정(웹서비스 책임자급 담당)**: 우선 웹사이트에 페이지를 추가해 반영한다. **05-22**: 웹서비스개발팀 담당이 개발사이트 하단에 '법적고지' 항목을 추가해 개발서버에 선반영(정책 화면 이미지 `global maps_policy.png` 첨부, 피드백 확정 후 상용 적용 예정). 개발 PM 수석이 개발서버 반영 방식으로 진행을 요청했고 14:25 상용 배포가 완료됐다. 15:25 개발 PM 수석은 Web 지도가 개발자 사이트에 추가됐으니 업체 전달 시 개발자 사이트의 "Map JS"를 확인하라고 안내하도록 공유(스크린샷 첨부).
- **05-20 부수 건**: 개발 PM 수석이 Orbis 사이트 하단 support 메일 도메인이 잘못 입력되어 있다고 지적(스크린샷 첨부)하고 올바른 도메인으로 변경을 요청. 웹서비스 책임자급 담당이 웹서비스개발팀 담당에게 수정을 지시했고, 담당이 수정해 상용 반영을 보고, 개발 PM 수석이 변경을 확인했다.

## 3. 다국어 스타일 메타데이터 변경 (5~6월)

- **2026-05-29 제안(웹서비스개발팀 담당)**: 다국어 설정(영어/중국어) 포맷을 국내향 스펙과 통일하기 위해 Light/Dark 스타일(2604) `metadata.language.field` 값을 `"NAME_EN"`/`"NAME_ZH"`(AS-IS)에서 `"{NAME_EN}"`/`"{NAME_ZH}"`(TO-BE, 중괄호 템플릿)로 바꾸려 하며, 영향 여부 검토를 요청했다. 이슈가 크면 기존 방식을 유지한다.
- **05-29 답변**: Web 담당은 MapJS는 큰 이슈가 없고 참조 코드 일부 수정으로 대응 가능하다고 봤다. SDK 담당 책임은 SDK도 일부 참조 코드 수정으로 가능하며, as-is Expression 방식에서 to-be token(value) 형태로 바뀌는 것으로 이해한다고 했고, metadata 영역은 순수 문자열(Key)로 관리하는 편이 더 낫다고 보는데 검토된 내용이 있는지 질의했다.
- **05-29 변경 이유(웹서비스개발팀 담당)**: 가장 큰 목적은 향후 다국어 데이터 조건이 바뀌어도 코드를 고치지 않고 메타데이터만으로 대응하는 것이다. 현재 구조는 field뿐 아니라 font 영역도 메타데이터로 관리한다. 예: 중국어 설정에서 "중국어 이름 없으면 영어, 영어도 없으면 기본 name" 같은 coalesce 우선순위 표현식이 추가될 때, 순수 문자열 Key 방식이면 규칙마다 코드를 수정·배포해야 하지만 중괄호 템플릿이면 표현식으로 확장해 메타데이터만 바꿔 즉시 반영할 수 있다.
- **05-29 개발 PM 수석 질문과 답**: 번체는 zh가 아니라 zh-tw가 맞는 표현이 아닌지 물음. 웹서비스개발팀 담당은 현재 지도 데이터가 간체/번체로 나뉘어 있지 않고 스타일 키도 통합 코드 `zh`로 지정돼 있다고 답했다. 개발 PM 수석은 이후 제공될 맵 스타일부터는 수정된 메타데이터 형식과 함께 `zh-tw` 키로 전달하겠다고 했다.
- **06-01 일정**: 대만 지도 스타일(Light/Dark)은 변경된 버전(2605)으로 준비 완료, 개발·테스트용 경로를 공유(링크 미수록). SDK 다국어 대응 일정 질의에 지도 개발 팀장이 "차주 정도로 계획"이라고 답했다. 웹은 StyleJSON과 WebJS 업데이트를 6월 4일(목)로 계획하고, Web 지도·모바일 SDK·Navi SDK 3개 플랫폼 모두 동일 주소의 스타일을 바라보게 한다. 개발 PM 수석은 현재 서비스 중인 Web 지도에 영향이 없다면 6월 4일 진행해도 좋다고 확인.
- **06-04**: Web 담당 책임이 Style JSON 변경 적용 완료를 보고.

## 4. 대만 탐색 실패(도로 확장 실패) 분석 (6월)

- **2026-06-04**: 대만 업체 테스트 중 탐색 실패가 발견되어 개발 PM 수석이 분석했다. 출발지 좌표 25.059637, 121.617550에서 경로 탐색 시 "도로 확장 실패" 오류가 발생한다(최신 엔진 연동 버전).
- **06-04 원인(탐색엔진 담당 수석)**: 출발지와 가장 가까운 링크를 선정할 때 선택된 링크가 일방통행 링크라 역주행이 불가능해 생기는 실패 케이스다. 해당 링크 둘이 같은 OSM way에 속한다(링크 일방통행 스크린샷 2장 첨부). 추가 사양 설정이 필요하며 예: 일방통행으로 주행 불가하면 차선 반대쪽의 출발지 링크를 찾을지, 일방통행이라도 강제로 탐색할지.
- **06-05 제안(개발 PM 수석)**: 출발지가 일방통행으로 주행 불가한 경우에만 반대편 링크를 찾는 사양으로 적용하는 것이 문제가 크지 않을 듯하다.
- **06-08 정리(개발 PM 수석)**: 현재는 출발지/목적지 Projection에서 가장 가까운 링크를 찾는 사양만 있다. 출발지/목적지 모두 일방통행으로 주행 불가하면 반대편 링크(차선 반대쪽)를 찾는 사양을 적용하는 것으로 구두 논의 내용을 정리. 구현 여부·일정은 스레드에 기록되지 않음. ^[inferred]

## 5. Global Maps API 추가와 TomTom 과금 기준 점검 (6월)

- **2026-06-12**: 웹서비스(개발) 담당이 Global Maps API에 Geocoding, Reverse Geocoding, Fuzzy Search 3개가 추가됐다고 알렸다(고객 사이트 규격서와 Redoc 기반 규격서, 내용 동일). 개발 PM 수석은 "TomTom API 래핑" 건으로 개발사이트에 위 3개 API가 적용됐다고 설명하고, 추가 API는 업체 요청 시 일정을 산출해 추가하겠다고 했다. Redoc 규격서는 개발자 고객사이트에 연결되지 않았는데 외부 공유 가능한지 묻자 담당이 아직 내부용이라 외부 업체 공유는 하지 않는 편이 좋다고 답했다.
- **06-25 개발 PM 수석 1차 분류**: 사용 중인 TomTom API가 Non-Tile과 Tile 중 어느 과금 기준인지 확인 요청. Traffic Flow, Traffic Incidents는 `Tile`, Speed Camera, Search(Fuzzy, Category), Geocoding, Reverse Geocoding은 Non-Tile로 분류했다. 통계(이미지 첨부)상 `Map Display API`가 호출되는 것으로 확인되는데 SDK에서는 사용하지 않아 다른 팀의 사용 이력을 문의했다. 사업(전략)팀 과장은 TomTom 요금 안내 문서를 공유했다(링크 미수록).
