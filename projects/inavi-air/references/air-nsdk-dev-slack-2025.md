# Slack #001_air_nsdk_dev 개발 대화 (2025)

에어·NSDK 앱 개발자 비공개 채널의 2025년 기록이다. 프로젝트 개요는 [[inavi-air]], 앞선 기록은 [[air-nsdk-dev-slack-2024-h2]]를 본다. 2025년에는 국내 에어 운영(시간제 통행규제, 16KB 페이지, 광고 SDK)과 함께 TomTom Orbis Map 기반 대만향 NaviSDK(샘플앱 이름 U-Map) 개발이 채널의 중심이 됐다. 대만향 SDK 전반은 [[orbis-sdk]], [[orbis-navisdk-development-2025]], [[demo-exhibition-app-scrums-2025]]와 함께 읽는다. 같은 해 운영·배포 기록은 [[air-operations-2025]], [[air-app-version-notes-2025]]에 있다.

참여자는 팀장(PM), iOS 개발자, Android 개발자(저장소 소유자 이동은), 엔진·SDK 개발자 2명이다. 매주 월요일 플래닝/리뷰, 수요일 스크럼을 했다. 1월 22일 공지로 그다음 주부터 회의를 본사에서 하기로 했지만, 3월 이후 수요일 스크럼은 다른 사무실 회의실에서 하는 등 장소는 상황에 따라 바뀌었다.

## 조직·계획

- **연초 작업(01-02~01-07)**: 국내향 NaviSDK(KMP) 내부 Base 로직 세분화 티켓(MMC 모듈 통합, SMR Control, NaviController `runRoute`·API 리스트업, 지도 인터랙션 API 리스트업 등)을 담당자별로 등록했다. Orbis는 대만 RouteServer API 설명서 `v0.3`과 경로 비교용 테스트 페이지가 공유됐다(서버 주소 미수록). TomTom에 요청할 협조 항목은 전담 기술 지원 인력, 예제·샘플 소스, 현지 이슈 대응이었고, 단속카메라·주차단속 데이터 제공 여부도 확인하기로 했다. Epic 이름은 "Orbis Map NSDK 상품 상용화".
- **인력 지원(01-13~17)**: 스탬프 프로젝트(오르다 리뉴얼)에 Android·iOS 개발자를 지원했다. 이 채널의 iOS 개발자가 UI 화면 개발 지원으로 갔고, SDK 개발자 한 명은 NSDK에 집중하도록 했다. 01-21 이동은의 Apple 개발자 계정을 요청했고, 프로비저닝 등록 절차는 팀 내부 문서를 따르기로 했다(링크 미수록).
- **국내향/해외향 우선순위(02-18)**: 계획은 ~2월 국내향 리뉴얼, 3~9월 Orbis Map PoC, 10~12월 국내향 완료·서비스였다. 사업 측이 국내향(기존 NaviSDK + Flutter 대응, 신규 업체)을 3~4월에 먼저 해 달라고 요청해 Orbis를 1~2개월 미룰 수 있다는 논의가 있었다(확정 아님). 02-27 리뷰 결과는 국내향을 그 주에 마무리하고 다음 주 공식 킥오프 후 해외향을 진행하는 것이었다.
- **TTS(02-05)**: PoC 기간에는 단말 기본 내장 TTS를 쓰고(삼성 Android 우선), 중국산 Android 폰 지원이 필요해지면 Google Cloud TTS를 검토하기로 사업 측과 정리했다.
- **킥오프(03-04)**: Orbis NSDK 공식 킥오프. 3월(3/27) 리뷰 항목은 WBS 1.0, 해외향 구조 설계, TomTom API 검토, Figma 디자인 초안, 번역(OneSky)이었다. WBS 초안(`v0.6`, 03-05)은 기존 워킹데이 106일 기준으로 러프하게 일정을 잡았고, 탐색엔진 완료(3/28 예정)와 MMC 엔진 배포(6/9 예정)에 맞춰 경로탐색 API 연동·현위치 기능 일정을 동기화했다. 03-10 PAMS 등록 프로젝트도 정해졌다. OrbisMap 이슈 체크리스트는 팀 공용 시트로 관리했고(03-07), WBS는 체크리스트 형태의 `v1.0`(03-13 기준)으로 갱신해 03-19·03-26에 공유했다.
- **PM(03-18)**: 팀장이 커넥티드 해외향 PM을 맡는 것이 확정됐다(국내향은 다른 PM). 직접 참여 시점은 미정이었다.
- **IPO 실사(05-13, 06-27)**: Orbis NaviSDK를 디자인 워크플로와 UI 일부가 들어간 구동 산출물로 시연하기로 했고, 현장 실사는 6월 27일이었다.
- **전사 방향(06-02)**: Orbis NaviSDK의 DP(지도 표출) 엔진을 MapLibre/Mapbox 기반으로 자체 개발하는 방안을 우선 검토하고, TomTom과의 파트너십은 유지하되 중장기적으로 내재화하자는 의견이 나왔다.
- **마일스톤(10-28)**: 25년 4분기 iOS NaviSDK 서비스, 26년 1분기 MapsSDK 서비스. 상시 항목은 상용서버 전환, 업체 요청 대응, 차로 안내, 연결로 진입·진출(고가·램프) 안내 강화, 회전구간 안내 강화였다. 역할은 엔진·SDK 개발자가 실차 개선·상시 대응(검색, MMC, 연결로 안내 선행 검토), iOS 개발자와 이동은이 4분기 iOS 개발 구성을 맡기로 했다. 선행 작업으로 이동은은 국내향·해외향이 섞여 있던 코드를 해외향 전용으로 바꾸고(국내향 코드 때문에 불필요한 변환 구조가 복잡해짐), iOS 개발자는 모듈별 iOS 빌드 환경을 구성한다. 전시회 기준 PoC 완료 항목은 태그로 구분하고, 상용화를 위해 국내향 관련 코드는 제거하자는 의견에 팀장이 동의했다.
- **준상용 서버(11-24)**: Orbis SDK가 개발서버에서 운영 중이라 제휴처 평가 시 안정성 리스크가 있어, 12월 중 준상용 서버를 구성하기로 보고됐다. iOS Navi SDK는 CES 2026에서 공유할 예정이었다. 같은 주간회의에서 2025 Tech day(12-15 오후) 일정도 공지됐다. 11-12 iMPS 글로벌 사이트가 채널에 공유됐다.

## AIR 국내 운영

### 1~3월 패치

- **전기·수소차 통행료 할인(01-03, AIR-1876)**: 앱미터기와 같은 사양(2024년 50%, 2025년 40%, 2026년 30%, 2027년 20%)을 OS가 제공하는 날짜로 연도를 판단해 적용했다. 3월(03-21)에 21~22시 출퇴근 시간대 할인이 잘못 반영된 문제가 나왔다(안내 600원, 실제 500원, AOS·iOS 공통). 원인은 기존 50%·면제처럼 전기차 할인율만 계산한 것이었고, 기존 시간대 할인율과 전기차 할인율을 함께 적용해야 했다.
- **1~2월 기타**: 주차장 i정보 표출 사양(`detailinfo`의 휴무일·영업시간·이용료 등)과, 탐색엔진이 새로 정의한 리턴코드를 앱이 모를 때 죽는 문제를 플래닝 안건으로 올렸다(01-20). 안내엔진 `RoadColor`는 Company 값이 INavi(2)일 때만 내려오고 SDK(3)로 초기화한 AIR에서는 항상 0이어서, 안내엔진에 두 값을 통합해 달라고 하고 테스트는 2로 하기로 했다(02-24). 온다 택시에서 난 확대도→전체경로→백그라운드 복귀 크래시는 온다가 `TWExtendView`를 커스텀하며 recycle된 비트맵을 재사용한 문제로, AIR 영향은 없었다(01-24~02-04). AES128 암호화 키 노출 건은 메인에서 쓰는 키가 아니고 Agent만 확인이 필요하다는 답이었다(01-14). iOS 크래시 확인을 위해 iOS·Android 개발자가 본사에서 실차를 나갔고(01-16), 팀장 개인폰에서 지점 고정핀이 간헐적으로 사라지는 iOS 문제가 AIR-1894로 등록됐다(01-31).
- **아바티 이미지 '황금티켓'(01-16)**: Android `03.05.48 (301414)`를 내부 테스트 트랙에 올렸고 사전 출시 보고서도 문제가 없었다. 스토어용은 Bundle 빌드, 내부 APK는 Jenkins 빌드로 같은 버전을 나눠 만든다. 2월 패치에는 AOS 오토 검색결과 비정상 종료 수정, iOS 아바티 번들 이미지, DP(SSL 변경 버전), 검색 부가정보 추가가 들어갔고, 로그 서버 상용 반영은 그 주 목요일 예정이었다(02-18).
- **선행 로그 규격(2월 패치)**: 신규 사용자 로그 규격 추가는 2월에 하고 Agent 규격은 2월 초 발행 예정이었다(01-07). 선행 테스트용 `03.05.49 (301415)`는 개발서버에만 붙는 버전이었다. iOS `carplay_u`는 카플레이 지도 화면이 뜰 때 보내고, 주변 인기장소 카드의 파이브핀 웹 연동은 POI ID와 명칭만 보내기로 했다. 3월 말 iOS 작업도 끝나 AOS/iOS 테스트 빌드를 공유했고, 개발서버 로그 업로드가 404(AOS는 결과코드 1002)로 실패해 서버에 문의했다(03-28~31). 8월 2차 테스트에서 `CARPLAY_SETTING_A`가 대시보드와 메인 카플레이 화면이 동시에 appear되며 두 번 들어오는 문제와, iOS가 `NEARBY_FAV_POI_A`를 보내지 않는 문제(규격 오탈자 수정 미반영)가 나와 그 패치에 고쳐 넣기로 했다.
- **검색 부가정보 순서(02-07)**: AOS와 iOS의 주차·부가정보 순서가 달라 iOS 순서(전기차 정보가 마지막)로 맞췄다. 홈페이지는 별도 파라미터로 받는다.
- **캐시 더 받기(03-04)**: 사업 요청으로 주행 후 캐시 적립 시 핀크럭스(오퍼월)로 가도록 통일했다. AOS는 확인 버튼에서 포인트홈을 띄우던 사양이었고, 다음 날 DP 엔진 교체 패치에 같이 넣었다. 스토어 85% 출시는 03-06이었다.
- **강제·선택 업데이트(02-25)**: AOS `03.05.35`/iOS `03.05.14` 이하 강제, 그 위는 선택으로 설정했지만 AOS `03.05.35`에서 팝업이 뜨지 않았다(서버가 내려준 최신 AppVer가 로컬과 같은 `03.05.35`여서 앱이 강제 패치를 건너뜀). 원인은 Agent 사양이었다. Agent는 업데이트 설정과 상관없이 마지막에 등록한 값을 최신 버전으로 보고, 강제/선택 플래그는 그 직전 값으로 정한다. 등록 순서를 "선택 → 강제 → 최신"으로 지켜야 한다. AOS는 개발과 상용의 스토어 `app_url`이 달라 개발서버에서는 스토어 이동이 안 됐다.

### 크래시·안정성

- **AppLovin NoSuchMethodError(02-19)**: `03.05.48`에서만 48명·427건. 스택에 에어 패키지가 없고, 포인트홈 광고 미디에이션(IGAWorks SSP → AppLovin MAX → Pangle)에서 나는 문제였다. 당시 포인트홈 `1.3.1.83`, 미디에이션 `com.avatye.cashblock:ad-plus-*` `2.1.0.22`였고 `2.1.0.23`으로 올렸다. 최신 미디에이션을 넣은 AOS는 테스트에서 특이사항이 없어 사전검토 보고서 절차를 거쳐 스토어에 올렸고, iOS 심사도 맞춰 진행했다(02-20). 이때 새로 들어간 검색 결과 i정보의 홈페이지·부가정보 영역은 터치 영역이 작아 AOS에서 링크를 누르기 어렵다는 의견이 나와, SDK 리뉴얼 뒤 GUI 개선 때 다루기로 했다.
- **중국산 헤드유닛(02-25~26)**: `QUAD-CORE T3 P1`(루팅 99%, Android 10 81%)에서 DP의 `createContext failed: EGL_SUCCESS`가 처음 4명·26건, 다음 날 87명·707건으로 늘었다. 정식 서비스 단말이 아니라 모니터링만 하기로 했다. Play Console에서는 같은 로그가 최신 갤럭시 단말에서 보인다는 지적도 있었다.
- **스토어 리젝(02-21, AIR-1905)**: Android 15 이상에서 Android Auto 실행 후 초기화 실패 화면의 "아이나비 에어 실행" 버튼을 누르면 권한 부족으로 Activity를 시작하지 못해 앱이 죽었다. Screen의 `CarContext` 대신 `CarAppService`의 baseContext로 Activity를 띄워 해결했다(Android 16에서 재현·수정 확인). Android 15의 백그라운드 Activity 실행 보안 강화 영향으로 추정했다. ^[inferred]
- **사전 출시 보고서 크래시(05-09)**: x86_64 가상 단말에서 `NaviBank.GetKeyInfo` `UnsatisfiedLinkError`. jniLibs가 armeabi-v7a, arm64-v8a만 있어서였다. `abiFilters`로 x86 계열을 빼고 `03.05.51 (301425)`로 다시 올렸다.
- **iOS MMC 크래시(06~09월)**: `GravityDriver_GPSReader::readValues`가 905건/525명. 백그라운드 안전운행 모드로 오래 두었다가 포그라운드로 돌아올 때 났다. iOS 사양상 백그라운드에서 10분간 속도 0이면 앱이 스스로 종료하고(OS가 종료하는 것이 아님), 비주행·도착 상태에서는 `stopMapmatch`·`stopUpdatingLocation`을 불렀다가 포그라운드 진입 시 `startMapmatch`를 다시 부른다. 내부에서는 XR 단말에서 1회만 재현되어 엔진 쪽에 로그를 넘겼다. 7월에는 크래시 2위 DP 로그(140건/129명)도 함께 넘겼다. 9월(09-03) Crashlytics 분석에서 99%가 백그라운드→포그라운드 복귀 중 MMC 재시작 시점이어서, 백그라운드 진입 때 MMC는 멈추지 않고 위치 측위만 멈추는(`mmc stop` 호출 제거) 개선안을 적용해 iOS 빌드를 다시 올리기로 했다.
- **안내엔진 재발행(05-15)**: iOS 비정상 종료 없는 사용자 비율이 약 98%에서 91.61%(399건/270명)로 떨어졌다. 로그상 초기 비정상 종료였고 내부 재현은 안 됐다. iOS만 엔진 교체 긴급 패치를 스토어에 냈고, AOS는 5월 말 패치에 넣었다.

### 기타 AIR

- **iMPS 인증 통합(02-28)**: NHN Maps API, B2B Maps API 인증 URL이 iMPS 하나로 합쳐졌다. 업체가 iMPS에 가입해 AppKey를 직접 발급받고, 자사 개발 키는 따로 받는다. 진행 순서는 개발 키로 Auth 도메인 변경 테스트 → SDK·SDK-SHI(삼성중공업 프로젝트) 수정 → 사업 측에 적용 버전 공유(업체 안내는 5월 말까지)였다. 3월 초 받은 공용 개발 키가 삼성중공업으로 매칭되고 삼성중공업 키는 300 오류가 나서 재확인을 요청했다. AIR도 MapsSDK 버전을 올리며 Agent(ServiceGate `inaviAuthKey`)로 새 키를 받도록 했고 04-09 상용 반영을 AOS·iOS 모두 확인했다(AIR-1912). 키 값은 원본에 있음(미수록).
- **GA 정리(03-19)**: 임원이 회사 모바일 계정 기준으로 GA에서 실제로 쓰지 않는 속성 앱을 삭제했다고 공유했다.
- **기타(04-04, 04-09)**: 오르다 스탬프 알림이 AIR에 뜨는 일이 있었다(04-04). 수석이 국내 탐색 결과의 TBT에서 경유지를 어떻게 처리할지 방안을 고민해야 한다고 했다(04-09, 결론 없음). 메일로 공유된 Polestar 차량 내비 앱은 Play 스토어 유럽 계정으로만 받을 수 있어, 수석 개발폰에 설치해 다음 주에 함께 보기로 했다(05-16).
- **Firebase Dynamic Links 종료 대비(04-17)**: 링크 생성 실패 시 AOS는 반응이 없고 iOS는 빈 링크를 공유하던 것을 full URL 공유로 바꿔 5월 패치에 넣었다.
- **수해지역(침수) 안내(05~07월)**: VVMS를 `SetSmartVVMSInfo`(거리 1~700m)로 넘긴다. VVMS 타입 구분은 기존처럼 안내에서 받은 ID로 메인이 판단하는 방식을 유지했다. 다른 안내(터널 내 카메라, 스쿨존, 마을주민 보호구역)보다 우선순위가 낮아 모의주행에서 묻히기도 했다. 06-30 탐색 기준 VMS 정보를 안내에 넘겼을 때 모의주행에서 전달되지 않거나 한 번만 넘어오고 끊기는 현상이 있어 현재 개발 스펙을 문의했고, 같은 날 iOS 개발자가 좌표 변환 시트를 공유했다. 화면 점멸은 스쿨존과 같고, 효과음은 기존 과속 경고음 사용 여부를 문의했다. 7월 초 AOS 스토어 등록(iOS는 DP 엔진 빌드 오류로 수정본을 기다림), 이후 상용서버 작업과 배포(07-14)를 했다.
- **도착시간 Hold(07-11)**: 15/30/60분 단위로 각각 3/10/20분 오차를 임계값으로 본다.
- **방향성 탐색(09-01)**: 목적지 방향성 탐색은 항상 켜 둔다. 출발지 방향은 MMC `reversed` 기준이고 오프로드면 -1, AOS의 네트워크 좌표 기준일 때도(기존 0) -1, 목적지는 -1로 통일했다(iOS는 프로젝션으로 정하던 것을 바꿈). 경유지는 AOS가 목적지와 같은 로직(-1)이어서 iOS도 AOS 사양으로 맞췄다.
- **AI 요금(01-10)**: 재경팀 문의로 확인한 11월 결제 4,235원은 Perplexity 검토용이었고, ChatGPT API는 잔액이 남아 12월 추가 결제가 없었다.
- **에어봇(09-08)**: OpenAI API 키가 유출되어 자동 비활성화됐다. 키가 앱에 하드코딩되어 있었고, 최신 AIR 프로젝트가 공유되는 과정에서 다른 부서 업로드 등으로 노출됐을 수 있다고 보았다. ^[inferred] 에어봇 서버를 임시로 끄고 서버에서 키를 받는 구조로 바꾸기로 했으며, 09-30 서버 기반 패치가 끝나 서버 오픈을 요청했다. 11월 1일 크레딧 유효기간 만료로 잔액이 0이 되어 결제 플랜을 취소했다. 4/9~5/9 한 달 사용량은 1,192회, 약 0.13달러(잔액 약 96달러)였다.
- **HUD(로드피아, 4~10월)**: 4월 말 HUD 규격서 검토를 요청받아 iOS 개발자가 검토 문서를 정리했다. 9월 iOS HUD 미연결 이슈는 유지보수 계약이 끝나 업체 수정이 어려워 범위가 크지 않으면 내부에서 고치기로 했다(lib 대신 코드베이스로 추가, BMW CarPlay 이슈와 함께 패치). 업체가 보내 준 `BluetoothLibrary.framework`(헤더만 포함)로 정상 동작을 확인하고, 9월 말 iOS 빌드(HUD lib 교체, 정상 종료 때 크래시 로그가 올라가던 문제 수정)에 넣었으며 10-02 시료 단말 연결을 확인하고 빌드했다. HUD 이력은 [[air-image-hud-review-2025]], [[air-hud-integration-2023]]를 본다.
- **통합로그인 암호화(12-08~16)**: 팅크웨어 통합로그인 URL이 바뀌고 AES256으로 바꾼다고 전달받았다(가이드 문서는 암호가 걸려 있었고, 암호는 원본에 있음·미수록). 12-15 검토에서는 문서와 실제 데이터가 AES128이라 Agent URL만 바꾸자는 결론이었다. 그러나 Android에서 새 로그인 URL로 테스트하자 로그인 직후 Google Play의 다른 앱(아이나비 Connected)으로 이동했다. 콜백 intent의 scheme이 기존 `twauthair3`가 아니라 다른 앱용 `twauthcntd` 형태로 내려오고, 데이터 형식도 달랐다. 서버 측 복호화 코드(PBKDF2WithHmacSHA1로 256비트 키 생성, AES/CBC/PKCS5Padding)를 받아 확인한 뒤, 12-16에 iOS/AOS에 복호화 로직을 넣고 서버 URL을 바꿔 다음 날 AIR를 빌드하기로 했다. 키·IV·salt 값은 원본에 있음(미수록).
- **경유지 통과 사양(12-16)**: 오토모티브 개발팀이 TMC·KGM과 비교하려고 요청했다. Android AIR는 경유지 좌표의 LinkID·MapID가 현재 위치와 같거나, 현재 위치에서 경유지까지 100m 이하이면 통과로 본다. 경유지 순서대로 처리하지 않고, 아직 통과하지 않은 경유지 목록을 매번 검사해 passed로 표시한다.
- **결빙구간(12-26)**: 안내엔진에서 상습결빙구간 코드를 받아 심볼만 표출한다. 위험지역 안내 사양과 같고 별도 음성은 없다(모의주행으로 확인).
- **AOS MMC ANR(12-24~01-07)**: AIR Android에서 MMC `nativeInitMap`(`CMapMatchWalk::initiate`) 안에서 블로킹되어 ANR이 났다. MMC 측은 AIR에 없는 보행자 모드 경로에서 문제가 난 점을 물었고, 메인은 `nativeSetConfigureMMC`를 2015년부터 한 곳에서만 쓰고 있었다. 메일로 받은 새 MMC 엔진으로 ANR은 해결됐다. 함께 다룬 단일 링크 모의주행 이슈는, 경로가 아닌 곳에서 출발하는 문제는 고쳐졌으나 진행률과 턴 정보 거리가 틀리게 계산됐다(링크 2개일 때는 정상, iOS도 동일). 안내엔진을 포함해 문의했고 1월 초 새 엔진에서 진행률 문제가 고쳐졌다.
- **스쿨존 시간제 카메라(11-19)**: 시간제 카메라 안내가 나오지 않는다는 제보가 있어 주행 로그와 시간제 카메라 DB(`camera_exc.txt`) 다운로드 여부를 확인했다.
- **외부 연동**: 콜앱이 AIR를 broadcast intent(`APP_LAUNCHING`, `ROUTE_SEARCH`)로 부르는 방식은 최신 단말에서 정상이었다(01-10, API 28 이하는 `startActivity`, 그 위는 Notification 경유. 구형 단말은 추가 확인 필요).
- **공지·이벤트 웹뷰(08-26)**: 공지 안에서 "포인트 쌓아 에어캐시" 페이지로 이동할 때 웹이 넘긴 URL의 `SN` 파라미터 `/`가 인코딩되지 않았고, 일부 jpg가 `ERR_BLOCKED_BY_ORB`로 막혔으며, 서브리소스 오류에도 `onReceivedError`가 불려 오류 문구가 떴다. 메인 프레임 오류만 처리하도록 고쳤다.

## 국내 NaviSDK(KMP)·외부 고객사

- **iOS Core 빌드 실패(01-24)**: Kotlin 2.0.21(K2)에서 `linkDebugFrameworkIosArm64`가 "Generation of stubs ... not supported"로 실패했다. `LocationInfo`가 `@Serializable` open 클래스 `MMCInfo`를 상속하게 바꾼 커밋(NSDK-335, PR #50) 이후였고, 상속을 끊어 빌드를 살렸다. 같은 시기 develop에서 AOS가 MMC 모듈의 `nativeDebugLog(-1, null)` 호출로 바로 죽어 임시로 주석 처리했다.
- **4월 기타**: 이동은이 TomTom Maps SDK API 검토 문서에 자차 Custom 이미지 변경 검토를 추가했고(04-01), iOS 개발자가 지금까지의 SDK 구조도(네트워크 유틸 제외)를 drawio로 그려 공유했다(04-14). CX가 진행하는 번역 리스트(한국어)를 4월 말 번역 시작 전에 시트 댓글로 검토했다(04-16~17). 대만향 Routing API를 아이나비와 구글로 비교하는 사업용 사이트가 공유됐다(04-03, 주소·계정은 원본에 있음·미수록, 외부 공유 금지). 현재 서비스 중인 국내 NaviSDK iOS에는 `destroyNavi`가 없다. iOS는 앱 종료 시 따로 destroy할 필요가 없어서이며, SDK 실행 시간 측정용 종료 시점이 필요하면 SDK 내부에서 앱 종료 noti를 받도록 구현할 수 있다(04-30).
- **KMP iOS 모의주행(02-05~14)**: iOS에서 MMC 모의주행이 출발지에서 움직이지 않았다(SMR checksum 오류 로그는 SMR 엔진 내부 로그). 원인은 iOS `NSTimer`가 비동기 컨텍스트에서는 동작하지 않는 것으로, 메인이 타이머를 Main Thread에서 만들도록 바꿔 해결했고 기존 엔진도 정상 동작했다.
- **구조**: 이동은이 Koin DI를 기능별 모듈로 나누고 Constructor DSL을 쓰자고 제안했다(01-22). UI 진입점 이름은 `MapLayer`가 헷갈린다는 의견으로 iOS와 같은 `INaviMapView`로 바꿨다(03-13). `mapview_submodule` 브랜치에서 `AppContext`, `FontType`, `Resources`, `DataStore`, `FileManager`를 common 모듈로 옮기기로 했고(03-19), 공통 모듈의 Util/Model을 서브모듈로 옮겼다(04-09). 8월에는 국내향 API의 해외향 호환 여부를 정리한 "미개발 항목 현황"을 만들고(08-06), `NaviMapView → MapIF → AndroidOrbisMap → MapFragment(MapLibre)` 구조에서 내부 API가 노출되는 문제를 공개 인터페이스로 감싸는 리팩토링을 제안했다(08-08). LocationComponent tracking 모드는 카메라를 직접 움직이면 풀려서, 추적 상태용 카메라 API를 `LocationController`에 추가했다(08-08). 공용 서브모듈(`core/share`, `model/share`)을 붙이며 백엔드 코드의 jackson 직렬화를 KMP용 kotlinx serialization으로 바꾸기로 했고(08-21), 9월 초 패키지 경로를 바로잡고 `TTS` 모듈 이름을 `Media`로 바꿨다(09-03).
- **배포**: 7월 1차 AAR Maven 배포를 끝냈다. `navisdk-ui`(ui-android) 하나만 추가하면 Core Manifest 권한까지 병합된다. 7월 말 인증서버 개발 URL을 `isDevMode`에 따라 쓰도록 하고 대만향 전용 Orbis SDK 키를 새로 발급받아 적용했다(키·URL 미수록). 문서는 KDoc(javadoc 대체) 템플릿(08-06)과 gitbook 초안(07-31)을 만들었으나, 웹 쪽이 gitbook을 보안 정책으로 임베드할 수 없다고 해 HTML로 넘기는 방식으로 바뀌었다(09-09 mkDocs 검토, 09-23 HTML 전달로 정리). 자세한 내용은 [[orbis-navisdk-kdoc-and-mkdocs-guide]].
- **고객사 문의**: 웨이즈원 문의 검토 중 지도 Style을 Mapbox로 바꾸면 앱이 죽는 문제 발견(02-06, 단순 I/F 제거가 아니라 DP 원인 분석부터 하기로 함), 가이드 `v0.7.2`대로 빌드가 안 된다는 문의(작년 가이드 영상 전달, 02-20), 기사앱의 백그라운드 TBT(다른 앱 위 그리기) 지원(07월, 서버 도메인 변경·density 대응과 함께 발행), Expo/React Native 앱의 `1005 유효하지 않은 APP Key`(iMPS 키 변경 필요), `runRoute` 옵션은 반드시 2개로 맞춰 요청하는 사양(미지정 시 빠른길·추천길, 08-28), 오프라인 첫 실행 시 `UnknownHostException`을 `AgentError`로 캐스팅하다 죽던 샘플앱 버그(06-04), 경로선택 화면 예제 소스 요청(08-26, 공개 데모 저장소의 예제 안내), 국내향 SDK 반복 이탈 제보(08-27), 경로선택에서 `routeZoomMap` 갱신이 안 된다는 문의(09-09, 메일 회신).
- **두리텍·오믈렛(10월)**: 탐색엔진이 두리텍용 '위수지역회피' 옵션을 추가해(10-01 예고), 국내 NaviSDK 10-29 발행에 I/F를 넣기로 했다. 11-20 확인 결과 위수지역 회피는 개발서버에만 반영됐고 상용 반영 작업 내역은 없었다. 오믈렛은 Flutter 앱에 NaviSDK를 붙이며 `fail DP (3010)`(MapAdapter 미초기화: `initializeNavi` 전에 `initLayout`을 먼저 불러야 하고, 에뮬레이터는 `setEmulatorMode(true)` 필요), 에뮬레이터의 `No configs match configSpec`, PlatformView 생명주기 차이로 `onAttachedToWindow`에서 `MapLayer` NPE를 겪었다. 공식 Flutter 지원은 없어 HC(Hybrid Composition) 강제 방식을 안내했다. 사업적으로 Tmap 사용이 어려워 오믈렛은 11월 말 완료가 목표였고, 10월 21일 미팅에서 HC 미적용을 고치고 MapAdapter/MapLayer를 XML이 아닌 코드로 직접 만들어 넘겨 SDK 수정 없이 해결했다. 안 되면 AIR App-to-App(도착 시 오믈렛 앱으로 이벤트 전달 기능 추가)으로 갈 계획이었다. 11월에는 iOS Flutter 연동 문의가 이어졌다. `runRoute` 시 찍힌 `bad param - map_id[-1]` 로그는 SMR 오류로 탐색과 무관했고, iOS는 초기화가 성공한 뒤에야 검색·탐색이 동작하므로 초기화 완료 후 호출하도록 안내했다(11-11). `routeZoomMap` nil 예외는 `routeZoomMap`과 `startSimulation`을 동시에 불러서 났다. `routeZoomMap`의 지도 처리가 비동기라 `startSimulation`이 먼저 돌며 경로 캐시를 지웠고, 그래서 routeId를 찾지 못했다. SDK에 예외 처리를 넣고 두 함수를 따로 부르도록 안내했다. iOS 모의주행은 100% 도달 시 도착 콜백을 보내지 않아(`guideManagerSimulatorPos`의 pos 100으로 판단 가능, AOS는 보냄) 모의주행에서도 도착 콜백을 보내도록 고치기로 했다(11-12). Flutter 계획은 [[navisdk-flutter-plugin-plan-detail]].
- **React Native(Expo) 검은 화면(12-05)**: Maps SDK `0.8.0` 문의로 들어왔지만 실제로는 NaviSDK였다. react-navigation 7부터 react-native-screens가 기본 적용되어 탭 이동 때마다 View가 detach/attach되며 새 인스턴스가 생기자 지도가 검게 나왔다. SDK는 엔진과 지도 렌더링(EGL Context)이 Surface 생명주기에 묶여 있어 잦은 재생성을 지양한다. 고객사가 요청한 "View를 수동으로 다시 붙이는 API"는 구조 재설계가 필요해 지원 불가로 답했고, `detachInactiveScreens` 옵션을 쓰거나 재생성 때마다 `initLayout`과 `initializeNavi`를 다시 부르라고 권했다.
- **탐색 918 오류(11-25~26)**: 탐색엔진 서버의 read timeout으로 SDK 샘플앱에서 918이 났다. SDK는 서버 오류를 그대로 전달하고, AIR에서도 간헐적으로 났다.

## Orbis Map·TomTom 대만향 NaviSDK

### TomTom 검토 (1~5월)

- TomTom 측은 개발자 사이트 기능 대부분을 무료로 쓸 수 있다고 안내했다(Search API 하루 2,500콜). 내비 자체는 우리가 만들고 TomTom에서는 지도 표출용 MapSDK만 쓰기로 했다(지도 표출까지 직접 하면 개발 기간이 너무 길다는 이유, 01-03). 평가 계약(Search API·Maps SDK)용 개발자 포털 계정은 원본에 있음(미수록). Routing 모듈에 넣는 API 키는 기본 키로도 동작했다(03-28). 4월 말 키 상태가 "paying"으로 바뀌었으나 호출에는 문제가 없었다.
- **"일본해" 표기**: MapsSDK에 "일본해"가 나왔다(01-24). `TomTomMap.layers`에서 "NatureLabels - Water area"를 숨기면 모든 대양 이름이 사라졌고, 레이어의 `source-layer`는 바꿀 수 없었다. TomTom이 "동해"로 바꿔 주기로 했다(03-27). 이후 안내받은 `NdsStoreConfiguration` 업데이트 URI 방식은 우리 SDK 구성에 해당 클래스가 없었고(05-02~07), 다시 KR 지정학 뷰(`geopoliticalView="KR"`, KR 전용 API 호스트) 설정을 안내받았다(05-14).
- **Orbis 지도 활성화(05월)**: 탐색엔진은 OSM 데이터를 쓰는데 배경지도가 TomTom 자체 지도라 경로선이 어긋났다(05-14). Orbis 지도를 쓰려면 Map Maker에서 Orbis 스타일 JSON을 뽑아 `MapOption`에 넣고, 반드시 Public Preview API인 `FeatureToggleController`로 `TomTomOrbisMapFeature`를 켜야 했다(05-19~20). 안내 시작 전 50초~1분 기다려야 ANR이 나지 않았다. 5월 말 TomTom 기술미팅용 문의(ANR, 지도 캐시 정책, 경로선 구간별 색, 국가 범위 검색)를 정리했다. 같은 시기 TomTom PBV 디자인 문서(Automotive UI `v1.4.0`, 05-09), CX가 정리한 다국어 내비 단위·표기 사양(05-23), 상태 관리 Flow 문서(05-08)가 공유됐고, w3w 현대 미팅용으로 텍스트로 w3w를 검색하는 영상을 만들었다(05-07). TomTom이 보낸 대만 샘플맵 `pbf`를 Maps SDK에서 쓸 수 있는지 확인 요청이 있었고(05-24, 다운로드 링크·토큰 미수록), MMC 테스트용으로 대만 경로(용산사 → 타이베이 시립 동물원) 탐색 결과 JSON을 넘겼다(05-13).
- **라이선스 벽(05-29)**: TomTom은 Orbis Display API가 준비되지 않아 누구에게도 라이선스를 주지 않고, uncompiled map으로 자체 구축하라고만 했다. Orbis 스타일이 Mapbox에서도 똑같이 그려지는 것을 확인했고(05-27, Map Maker 자체가 MapLibre Style Spec 기반), 자체 구축 또는 서드파티 방안의 일정을 산정하기로 했다. 서드파티 업체는 MapTiler로 보인다는 의견이 있었다. 서드파티안의 초안 항목은 타일서버 구축(iNaviMaps 서버 일정 참고), Orbis 스타일 분석(maputnik으로 JSON 레이어 검토)·CTT on/off·다국어 표기, MapLibre SDK 인터페이스(현위치, 주행, 자차 모드, zoomToFit 등 카메라 구조), 경로선·유도선 개발이었다. 이후 전사 방향(06-02)에 따라 자체 타일서버 + MapLibre 기반 DP로 진행했고, 6월 말 IPO용 APK에 MapLibre(DP)를 1차 적용했다. 검토 기록은 [[orbismap-route-and-tomtom-sdk-review-2025]], [[orbis-tile-map-style-analysis]].
- TomTom Routing API는 쓰지 않고 앞으로도 쓸 계획이 없다(04-22). 차선 정보는 Routing API의 lane section으로 제공된다는 답을 9월에 받았지만, 이는 TomTom 자체 탐색 결과의 안내 코드에 들어 있는 정보여서 특정 링크의 차로 정보를 받을 API가 따로 있는지 확인이 필요했다(09-11). Orbis Search API는 6월에 별도 키를 받아 붙였다(키 미수록, 두 계정 운영도 개발상 문제 없음).
- **검색 사양(9~10월)**: 검색은 대만 한정, 관련성+거리 정렬, 최대 20개, POI·주소 통합검색이다. 검색어는 영어·중국어 번체/간체·한국어를 받는다(09-03). 주소는 한국어 "도+시(군)+구+로/길+번호", 번체/간체 "시+구+로/가+번호", 영어 "번호+로/가+구+시" 순으로 조합했고(09-30), 자동완성 옵션은 중국어에서 결과가 달라 적용하기로 했다(10-23). Taipei Zoo처럼 입구점 좌표는 파싱하지만 마커 작업 후 입구점 탐색을 적용할 예정이었다(08-07).
- **검색 API 선택(12월)**: 쓰고 있던 Orbis Search API는 평가판이고, 상용 Orbis Search API는 TomTom이 개발 중이었다(2026년 2분기 완료 예정). 그때까지 Genesis 검색(TomTom Search API)과 Orbis 평가판 중 품질이 나은 쪽을 쓰기로 하고 POI 검색 결과를 비교했다(12-11, Confluence "Genesis 검색 API 검토"). 사업 측과 협의해 **Genesis를 쓰다가 Orbis 상용판이 나오면 전환**하기로 했다. 두 API는 URL이 달라, 이미 배포한 샘플앱과 평가 계약 업체에 영향이 없도록 Agent에 Genesis 검색 API를 새로 추가하고 메인은 서버 플래그로 Genesis/Orbis를 고르게 했다. 키는 SDK, URL은 Agent가 관리한다. Orbis 키(`searchApiKey`)는 ReverseGeocoding/Geocoding에만 쓰고 있었다(12-24). URL·키는 원본에 있음(미수록). 상세는 [[genesis-vs-orbis-search-api-review-taiwan]].
- **검색 입구점(11-04)**: Starbucks를 목적지로 고르면 목적지와 떨어진 곳에 도착하는 문제는, 탐색 요청 시 입구점 좌표를 우선하는데 그 POI만 TomTom이 준 입구점 좌표가 엉뚱한 곳이어서였다. 검색 이슈로 분류했다.
- **Change Route(11-04)**: 사업 측 피드백("Change Route를 눌러도 경로가 안 바뀐다")에, 수동 재탐색은 현재 위치에서 최적 경로를 다시 찾는 기능이라 기존 경로가 이미 최적이면 같은 경로가 나올 수 있다고 영상과 함께 설명했다.

### 탐색·MMC·DP 엔진

- **탐색 API**: 대만 RouteServer API 설명서(`v0.3` → `v0.5` → 10월 엔진 `v1.5`)를 기준으로 개발했다. 링크 정보에 목적지까지 남은 시간 필드를 탐색엔진이 추가하기로 했다(05-15). 경유지는 링크를 끊어 가상 노드로 계산하므로, 연속 링크의 id/osm_id가 같고 회전코드가 U턴이 아니면 그 사이가 경유지다(04-09, 별도 구분 필드 없음). Content-Type은 json 요청을 넣었지만 GET이면 수정이 필요 없었다. 6월 탐색 속도 개선용 인스턴스가 추가되어 접속 포트를 바꿨다. 다중경로는 8월 말 목표(08-07)였고 경로 수는 상황에 따라 1~3개로 가변이다(08-28). Agent 다중경로 API는 9월 말 개발서버에 반영됐고, 10월 Agent에 새 지도 데이터(`1_0_1_1`)와 `sideroadstart/sideroadend` 필드가 추가됐다(10-17). 3999 오류는 Agent와 오류 코드가 아직 통합되지 않아 알 수 없는 오류로 표시된 것이었다(09-25). 탐색 서버 정보는 원본에 있음(미수록).
- **턴 안내 개선 논의(09-08)**: 직진 구간의 불필요한 좌회전 안내, U턴을 10시 방향 좌회전/좌회전으로 나눠 안내, 회전교차로 우회전을 우회전 2번으로 안내하는 문제를 탐색엔진이 먼저 검토하고 필요하면 메인에서 추가 연산하기로 했다. TBT 남은 거리는 10m 이하에서는 절삭하지 않기로 했다(06-26).
- **U턴·회전교차로 코드**: U턴을 `7,7,7`로 주던 것을 `7,0,0,...`으로 바꾸고(10-01), U턴·회전교차로는 시작과 끝에만 회전코드를 넣고 사이는 0으로 채운다(10-16, 예 `7,0,0,7`). U턴 코드는 단독 `7`로 나올 수도 있다. 10-14 U턴 유도선은 차기 링크 + 10m까지 더 그리도록 고쳤다. 11-07 정리: 회전교차로 쌍 사이의 0 개수로 출구를 판단한다(`9,9` 첫 번째, `9,0,9` 두 번째, `9,0,0,9` 세 번째 출구). 링크 개수를 맞추려고 탐색엔진이 사이에 미정의 코드를 넣을 수 있고, 이 규칙은 회전교차로에만 적용한다. 메인은 `11~22`(`ROUNDABOUT_EXIT_CLOCK_1~12`) 코드로 턴 이미지를 그리므로 이 필드 유지 여부를 물었다. 11-28 탐색 서버 Release로 확정된 형식은 기본 `22, RS, RE, RS, 22`, 목적지가 교차로 안이면 `RR, RS, RE, RS, -1`, 출발지가 교차로 안이면 `-1, RS, RE, RS, 22`다. `11~22`는 진입 시계 방향, `RS`는 교차로 안 직진 코드(메인은 무시), `RE`는 진출 코드로 그 개수로 몇 번째 출구인지 계산한다(0이면 첫 번째). RS/RE 실제 값은 당시 미정이었다. U턴은 차기 링크 + 10m까지 유도선을 더 그린다.
- **방향성 탐색(11-06)**: 경유지 방향성 탐색에서 출발지·목적지 모두 방향성 탐색을 하는지 확인했다. 최초 출발 방향 각도는 -1로 보내고 있었다.

- **7월 기타(Orbis)**: `OpenOrbisNetwork`는 초기화 함수와 같은 일을 하며 메인도 초기화 때 부른다. MMC가 이를 중복 호출하는 문제는, 라이브러리 로딩 확인용으로 MMC에서 호출을 뺀 테스트 버전을 만들어 메인에서 시험한 뒤 원복하고, 최종적으로는 탐색 Reader가 중복 호출돼도 1회만 동작하게 처리하기로 했다(07-03). 이동은이 로그주행 파일을 탐색기로 넣는 번거로움을 줄이려 테스트 함수(뒤로가기 → Write Log File → 로그주행 시작)를 넣었다(07-17). 스타일 JSON에는 TomTom이 쓰는 `pmd-theme-marker-halo-flag` 같은 템플릿 변수가 있어, SDK 안에서 변수 값을 KR/EN/TWN 등으로 바꿔 쓰는 방법도 검토 대상으로 올렸다(07-28). TBT 거리를 턴 링크의 남은 거리 기준으로 계산하면 실제 회전 전에 0m가 되므로 턴 링크 끝점 기준이 맞는지 문의가 있었으나 결론은 채널에 없다(07-14). 대만향 API·SDK 개발가이드 웹사이트 구축 초안이 공유되어 그 주부터 협의를 시작했다(07-25).
- **8월 기타(Orbis)**: 대만 타일 지도 1차 검토 항목은 도로 번호·고속도로 이미지 현지화, 도로명·방향성 표출, 건물 데이터, 도로 라운드·연결 지점, 고도별 레이아웃, 같은 레벨에서의 도로 선형 차이였다(08-04). 디자인 튜닝까지 반영된 스타일은 마지막에 받은 style JSON이고, 도로 외곽선은 넣으면 오히려 지저분해져 뺐다(08-28). develop 소스의 기본 빌드는 AAR이라 로컬 AAR(MMC, Maps 엔진)이 있으면 실패하고, APK는 `aos-playground`를 assemble해야 하며 buildVariant `inavi`는 국내 지도, `orbis`는 Orbis 지도다(08-08). 한국지도 테스트 앱 `0.0.1 (5)`(08-21)은 외부 공유용이라 뒤로가기 디버그 메뉴를 빼고, 이탈 재탐색과 화면 꺼짐 방지를 넣었으며, TBT에서 일반도로로만 나오는 도로명은 표출하지 않게 했다. 실차에서 매칭이 전혀 안 되던 문제는 `0.0.1 (6)`에서 고쳤고, GPS 음영에서 처음 실행하면 MMC 수신 전까지 대만 고정 좌표로 잡히는 문제는 다음 배포 때 고치기로 했다. MMC `0.4.0`(08-29)에서는 Agent 연동 작업 이후 탐색 응답의 `searchRouteDto`가 null일 때 처리가 없어 파싱 오류가 났고, 국내 요청은 국가 코드 문제로 `NO_ROAD_NEAR_START`가 돌아왔다. 탐색 파일 규격도 바뀌어 기존 파일 읽기 모듈에서 오류가 났다.
- **9월 기타(Orbis)**: 9월 초 MMC `0.5.1`에서 이전 이슈가 고쳐졌고, 대만향 샘플앱을 디버그 메뉴를 숨기고 타임락 10/31로 발행했다(FakeGPS 필요). 대만 스타일이 지도 전체를 그리지 못해 지도 측에 확인을 요청했고, 이후 받은 스타일을 확인해 CDN 적용을 요청했다(09-04~05). 서브모듈(model)은 작업 브랜치에서 서브모듈 커밋·푸시 → develop 머지 → develop에서 서브모듈 pull 후 커밋·푸시 순서로 갱신하고, 받는 쪽은 `git submodule update --init --recursive`를 실행한다(09-04). 카테고리 검색 enum 이름을 `TTCategory`에서 카테고리 검색 타입 이름으로 바꾸기로 했다(09-09). 경유지는 탐색 API는 동작하고 안내 로직(U턴이 아니고 id/osm_id가 같은 연속 링크)도 들어가 있어 화면 시나리오만 남은 상태였고(09-08), 경유지가 링크 중간에 있어도 링크 끝까지 갔다가 돌아오는 경로가 나와 탐색에 영상과 함께 전달했다(09-08~15). MMC가 경유지를 시험할 수 있게 샘플앱 메뉴로 테스트하도록 고쳐 넘겼다(09-09). 9-10 실차판 `0.1.1 (8)`은 다크 테마에서 앱 아이콘 뒤에 흰 배경이 나왔고(DayNight 테마, Light에서는 정상), 경유지 거리 계산은 개선됐지만 경유지 링크와 다음 링크가 같아 현위치 기준 이동 거리가 틀리고 지난 경유지가 다음 턴에 남는 문제가 있어 안내 어댑터 수정만 체리픽해 `(9)`를 냈다. 09-17 실차(Galaxy A52s, USIM 없음)에서는 지하차도는 일부 주행됐지만 긴 터널은 주행되지 않았고, 그 로그로 돌리면 터널 구간에서 위치가 점프했다. MMC에 보낼 최신 테스트 프로젝트는 MMC AAR → SDK 버전 올려 사내 저장소 배포 → 서브모듈을 받아 샘플에 넣는 순서로 만들었고, MMC가 말한 `status`는 MMC 로그의 매칭 상태 필드였다(09-17). 데모앱을 한국판 위에 업데이트 설치하면 FakeGPS가 먹지 않았는데, 삭제 후 재설치하자 정상이어서 LastGPS 영향으로 보았다(09-18). 대만판 경로선택·전체경로에서 도로명이 빈 항목은 전체경로는 "일반도로"로, TBT는 미표출하는 원래 사양이 빠져 있던 것이었다(09-23). SDK 가이드의 키 발급 안내는 국내향 문구(제휴 사업 담당자를 통해 별도 요청)를 그대로 쓰고, 번역은 markdown 원문을 그대로 넘겼다(09-24). 다중경로 대응을 위해 MMC가 시험할 수 있도록 다중 탐색 포맷(경로 1개) 파일 저장이 끝나면 테스트 프로젝트를 넘기기로 했다(09-29). 9월 초 iOS 효과음 원본(과속, 안전운전 종료 안내의 light/soft 2종)을 wav로 받았고, 이탈 효과음 wav는 없어 과속 카메라 효과음만 있다는 답을 받았다(09-04~09).
- **10월 기타(Orbis)**: MMC의 다중 탐색 실차 준비에 맞춰, 메인은 Agent 다중경로 결과(`SearchRouteMultiDto`)에서 안내할 경로의 `features[i]`만 골라 파싱해 경로 파일에 쓰는 테스트 앱을 넘겼다(10-02, `features` 외 필드는 공통). MMC가 픽셀 단말에서 NMEA가 잘 안 들어온다고 한 것은 수신이 약할 뿐 잡히는 단말이었고, MMC는 초기 GPS 궤적이 부정확할 때 링크에 매칭하도록 튜닝 중이라 초기 위치 사양(GPS Fix > 네트워크 > 기본 위치)을 먼저 적용한 뒤 보기로 했다(10-10~13). 대만향 SDK 인증은 Agent를 거쳐 국내 인증서버로 가며, 개발 키는 기존 SDK 키와 같고 업체는 `AndroidManifest`에 키를 넣으면 된다(10-30, URL·키 미수록). MMC가 현지 실차 이슈 위치를 물어 목적지 부근 마지막 고속·고가도로 진출 구간이라고 답했고, FakeGPS로도 검색 결과가 한국으로 나온다고 해 MMC `0.6.0` 테스트 프로젝트를 다시 넘겼다(10-31~11-03).

KMP iOS용 Maps 프레임워크는 `assembleNaviSDKMapsXCFramework` Gradle 태스크로 만든다(11-05). Android 현위치 도로명 영역의 아이콘이 특정 단말에서 작게 보여, 단말을 빌려 확인하기로 했다(11-14).
- **MMC(Orbis 맵매칭)**: 6월 첫 엔진(06-05)은 `matchStatus` 0, 속도·`IndexOnRoute` -1 등 값이 비었다. MMC 측이 프로젝션 API 개발을 맡기로 했고(06-13), `linkProjection` 결과가 원하는 대로 나오는 것을 확인했다(06-16). MMC 측이 테스트용 메인 소스를 요청해, 메인 코드를 AAR로 감싼 Android 테스트 프로젝트를 넘겼다(07-04). 국내는 so+java, 대만은 AAR에 java까지 포함해 받는다(07-18). 버전은 `0.1.0`(7월, `linkProjection`의 `linkRatio`가 항상 0.0) → `0.2.0`(8월, `initmap → initGPSModule → startmapmatch` 순서로 바꾸자 로그주행 정상, 실주행 notFIX는 Mock Location 문제) → `0.4.0`(8월 말, Agent 연동으로 경로 파일 규격이 바뀌고 `user_info→userInfo` 등 필드명 변경, `setOrbisRoute` 응답 0/1이 문서와 반대) → `0.5.0~0.5.6`(9월, LocationListener 위치 갱신, `setRouteResult` 응답 정상화, 터널 가상주행, 속도 갱신) → `0.5.7`(전시회) → `0.6.0`(10월 말). 모의주행 SEEK 기능은 `setSimulateIndex`만 쓰면 된다(08-28). 9월 실차에서 NMEA가 끊긴 터널 구간 가상주행(`0.5.4` 재현, 개선판 정상), 터널을 나와도 가상주행이 끝까지 계속되는 문제(MMC 검토), 속도 0을 무시하던 메인 로직(GPSStatus 판단 제거)을 다뤘다. 경유지에서 `indexOnRoute`가 4→6으로 건너뛰는 문제도 MMC에 전달했다(09-15). 9월 중순 MMC가 직접 국내 실차를 돌 수 있게 NMEA 로그 저장 기능을 넣은 테스트 프로젝트를 넘겼다. 엔진 이력은 [[dp-mmc-engine-maplibre-scrums-2025]].

LastGPS는 3D Fix 전 네트워크 좌표를 5분마다, Fix 직후 한 번, 이후 1분마다 저장하고 저장 시 좌표 유효성을 검사한다.
- **DP(MapLibre)**: 6월 개발 항목은 경로선(링크 구조, 지나간 링크 처리, 차기·차차기 유도선), 마커, 자차, CTT(geoJson 데이터와 연동 API 필요), 타일서버 기준 스타일, SDK 인터페이스 구조 반영이었다(06-11). 교통정보 경로선은 feature별 색을 칠해 지연이 있어 저사양 단말 테스트가 필요했고(09-26, S20+는 거의 지연 없음), 기존 CTT 버튼을 교통정보 버튼으로 바꿨다. 교통정보만 갱신하는 API가 없어 5분 주기 자동 재탐색을 넣었다(09-25 제안, 10-17 교통정보 갱신 주기가 2분이라 5분이면 충분하다고 정리). 스타일 JSON은 국가별로 나오고 한국은 TomTom 스타일을 쓴다(07-28). 8월 중순 타일이 바뀌어 대만 스타일이 완성되기 전까지 TomTom 스타일판(`0.0.1 (4)`)으로 사업 시연을 했고, 9월 초 대만 스타일을 CDN에 올렸다. 겹치는 도로는 고도에 따른 위아래 구분이 안 되고, 폰트는 MapLibre 기본 폰트다(08-28). 지도 언어는 번체/간체면 번체 지도, 그 외 영어이며 도로명은 지도 데이터의 국가 공용어·영어·제2 공용어로 구성되어 대만향은 번체·간체·영어, 한국향은 한국어·영어다(09-03). 10월 일부 POI가 번체/간체 혼합으로 나와 OrbisMap 데이터 오류로 의심했고, 번체로만 나오는 스타일로 적용을 요청했다(10-10~17).
- **오픈소스(09-04)**: MapLibre는 BSD 2-Clause로 바이너리 재배포 시 고지만 하면 되지만, API를 그대로 노출하지 말고 2차 가공해야 한다는 의견이었다(지도 SDK 기본 기능: 마커, 정보창, 폴리곤, 위치, 카메라, 좌표계, 클러스터링). 대만향 MapsSDK는 inavi map SDK + 대만 Tile로 먼저 검토하기로 했고 이후 TF 구성 여부는 임원이 정하기로 했다. 국내향 MapsSDK로 대만 지도를 그리려면 국내 기준 범위 체크와 특정 레이어 기준 로직을 고쳐야 했다(09-11). 12월에 오픈소스 라이선스 목록을 정리했다.

IPO용 APK는 하단 모의주행 버튼이 동작하지 않아 메뉴의 "Start Simul"을 쓰도록 안내했고, 뷰모드는 AIR처럼 모의주행·주행 중에만 동작하며 경로가 없으면 GPS만 가운데로 추적한다(06-24~26). 이보다 앞서 Orbis 스타일을 입혀도 특정 경로선이 도로와 맞지 않았는데(구글·OSM 도로와는 일치), 내부 Orbis 지도를 구축한 뒤 다시 보기로 했다(06-17). `0.0.1 (2)`(06-26: MMC WGS84 좌표, 모의주행 bearing, 렌더 지연 개선) → `0.0.1 (3)`(08-05: 안내 음성 템플릿 조합, 앱별 언어 설정, 오디오 포커스) → `0.0.1 (4~6)`(8월: TomTom 스타일판, 한국지도판, 실주행 수정) → `0.1.x`(9~10월).

- **실차(9월)**: 9-10 판교 일대(판교역·매봉역·반포 순환)에서 국내 실차를 시작했다(`0.1.1 (8)`, 경유지 개선 `(9)`). 이후 터널 안내·ETA 토글을 넣은 `0.1.2 (10)`(09-16)으로 실차를 이어갔다. 경유지 추가는 상세정보 → 경유지 추가 → 검색, 다중경로는 하단 카드 좌우 스와이프(a/b/c 아이콘)로 시나리오를 정했다(09-15, 전시회 앱에 포함). 경유지에서 MMC `indexOnRoute`가 4에서 6으로 건너뛰는 문제(경유지로 끊긴 두 링크가 같은 id)도 다뤘다. 이탈 안내는 효과음 대신 TTS("경로를 벗어났습니다", "경로를 재탐색합니다", 기존 번역 문구 재사용)로 하고 실차에서 문제가 있으면 효과음으로 바꾸기로 했다(09-08). 과속 카메라 화면 Red 점멸은 넣지 않기로 했다(09-23). 모의주행 속도는 1x/2x/3x = 60/120/180km/h(09-01), 카메라 안내 거리는 고속도로 1km, 그 외 500m다(07-11, Waze는 일반도로 약 450m, Google 지도는 카메라 안내 없음).
- **대만 데모·다중경로(9월)**: 대만에 보낸 데모 APK `0.1.3 (11)`(09-18, 하단 메뉴 비활성화, 타임락 10/31)을 시작으로, `0.1.4 (12)`(경로선택 다중경로 UI, 공용 인증키 적용, 터널 음성 다국어), `0.1.5 (13)`(다중경로 지원, MMC 0.5.6; `0.1.4`의 Initialize Fail(1001)은 유니크키가 비어 있던 탓), `0.1.6 (14)`(대만향), `0.1.7 (15)`(OrbisRouteDataLib `1.0.1.1`, 교통정보 경로선)을 냈다. 한국향은 TomTom 스타일이라 세계지도가, 대만향은 대만 지도만 나온다.
- **전시회(10월, 대만)**: 대만 전시회(TAITRONICS) 리플렛용 영어·번체 화면 스크린샷을 8월 말에 제공했다. 전시회 앱 `0.1.8 (16)`(10-16, MMC 0.5.7, 유턴 안내, 경로선택·경유지 시나리오, 주기 재탐색, 주소 표출 개선)을 내고, LastGPS 저장 조건(매칭 시에만 저장)을 풀어 `0.1.9 (17)`, 타임락판 `0.1.10 (18)`(11/30)을 만들었다. 전시회 단말은 갤럭시 A23 2대였다. 개발 가이드는 한글로 쓴 뒤 사업 측이 번역해 HTML로 웹에 넘겼다(스크린샷은 시간 관계로 영어만, 10-14 전달 목표).
- **대만 현지 실차(10/20~23)**: 앱 실행 즉시 크래시는 LastGPS에 `9999` 좌표가 저장되어 MapLibre `LatLng` 범위 오류가 난 것이었다(10-21, `0.1.11 (19)`에서 유효성 검사 추가). 터널 진입 직전 모든 단말이 MMC(`OrbisMapCache::checkSize`)에서 죽었고(10-21~22), 목적지 부근 OFFROAD 로그도 MMC에 넘겼다. 재탐색·지도 이동을 반복할 때 MapLibre `GeoJSONSource.setCollectionAsync` SIGSEGV가 났다(10-23, 원인 미확정). `0.1.12 (20)`(10-23)에서 터널 크래시, OFFROAD, 초기 위치, 검색 자동완성을 반영했고 이전 버전과 동시 주행에서 이전 버전만 죽는 것을 확인했다. 현지 평가 이슈는 TC 문서의 '이슈정리' 시트로 모아 원인·해결 방법을 리뷰하기로 했다. 이동식 단속카메라 제한속도 75처럼 10 단위가 아닌 값은 과속 심볼(20~120, 10 단위)이 없어 표시되지 않았다(10-15). 10-30 대만 업체 전달용 `0.1.13 (21)`(타임락 11/30, MMC 0.6.0, 재탐색 실패 처리)을 냈고, MMC가 대만 실차 이슈를 재현할 수 있게 MMC 0.6.0 테스트 프로젝트도 다시 넘겼다(10-31).
- **U-Map 11~12월**: 대만 업체(Hetone) 테스트용 APK는 타임락 11/30(11-07), 업체 전달용 AOS `0.1.15 (23)`은 타임락 2025-12-31과 실차 개선 일부를 담았다(11-24). 최초 실행 '지도 다운로드 및 초기화' 알림 문구가 번체로 하드코딩되어 있어 번역을 받아 다국어로 바꾸기로 했다(11-04). 지도 이동 문제로 MMC 좌표가 1초에 몇 번 들어오는지 봤으나 대여 단말에서 재현한 결과 MMC 문제는 아니었다. 12-17~18에 차량을 빌려 다시 실차를 했고, CES용으로 12월 중 임원·개발 폰에 설치해 설명했다. 12월 develop에서 번들 ID가 바뀌어 새로 설치되며, 경유지 추가나 다른 경로 안내 시작 시 카메라가 상단에 고정되는 padding 문제가 있었다(지도 이동 후 현위치를 누르면 복귀). 야간 지도 스타일은 웹 쪽에서 테스트 페이지와 style.json을 받았으나 검수 완료 여부는 확인되지 않아 Agent에 스타일 업로드를 요청했다(11-14).
- **AOS 외부 배포(12월)**: iOS는 TestFlight를 쓰므로 AOS 외부 배포도 Firebase App Distribution(AppTester)으로 옮기기로 했다(12-24, 2026년 준비). 12-30 이동은이 개인 개발자 계정으로 Firebase 프로젝트를 만들고(소유자 이전 가능 확인) 배포 테스트까지 마쳤다. 기존 AIR 프로젝트 소유 계정은 원본에 있음(미수록).
- **MMC 최소 OS(11-17~12-01)**: MMC 최소 OS 테스트 중 샘플앱이 Android 8에 설치되지 않았다. MMC AAR의 minSdk가 26이었기 때문이다. MapLibre가 OpenGL ES 3.0 이상을 요구해 21이 아닌 23(Android 6)으로 맞추기로 했고, API 23 단말에서 정상 동작을 확인한 뒤 MMC 측에 minSdk 23 테스트 프로젝트를 다시 넘겼다.
- **iOS(11~12월)**: Orbis 탐색 lib Linux 배포판은 arm64가 없어 iOS에서 쓸 수 없었다. 탐색엔진이 C++ 기반이라 Objective-C 포팅 없이도 배포할 수 있고, static lib보다 시뮬레이터까지 호환되는 xcframework로 배포하도록 환경을 지원하는 쪽이 낫다고 봤다(11-04). 탐색 담당은 iOS 경험과 Mac 환경이 없어, iOS 개발자가 헤더만 넣고 구현부를 비운 샘플 프로젝트(`build_run.sh` → `OrbisRouteStaticLib.xcframework`)를 만들어 넘기고 본사에서 환경을 세팅하기로 했다. MMC도 AIR iOS 수준으로 준비한 뒤 xcframework로 받는다. 11-17 탐색 lib 인터페이스 호출을 확인했고, 공유한 iOS 프로젝트의 타깃이 26.0이어서 15.0으로 낮춰 다시 빌드하도록 요청했다(Android so는 NDK 빌드 설정의 minSdk 확인 필요). 초기 지도 다운로드는 스트리밍이 실패해 단일 다운로드로 먼저 구현했고 초기화까지 성공했다(11-07). 응답 gzip은 별도 처리 없이 문자열을 읽을 수 있었다. KMP에서 `CValue<CLLocationCoordinate2D>` 리스트를 MapLibre `setCoordinates`의 `CPointer`로 넘기기 어려워 Objective-C helper를 검토했다(11-21). 12월 `OrbisMapMatch.ios`에 추가된 `setMapMatchListener`가 참조되지 않던 것은 clean 후 gradle 전체 빌드로 해결됐다. iOS release 빌드의 `AUTH_JSON_PARSING_ERROR(1004)`는 인증 응답 파싱 중 NPE였고, proguard가 아닌 gzip 처리 문제로 12-26에 해결됐다.
- **이름·배포 저장소(12-24)**: 외부 명칭은 `iNavi Navigation SDK`, 이후 Maps SDK는 `iNavi Map SDK`로 정했다. iOS SPM용 GitHub 저장소 이름은 `iNavi-Navigation-SDK`가 국내향에서 이미 쓰여 `Global-` 접두어를 붙이기로 했다. 12-08에는 배포용 Artifacts/Packages 페이지 접근 권한 승인 문제를 확인했다. ^[ambiguous]
- **라이선스(11-13~12-29)**: 대만 업체 Hetone과 계약이 진행되며 개발 가이드와 라이선스 고지를 점검했다. 쓰는 오픈소스는 Apache 2.0 수준이라 특별히 고지할 것은 없지만 SDK 문서에 명시가 없었다. MapLibre는 BSD-2라 ① SDK 사용 사실을 문서에 고지하고 ② 라이선스 원문을 넣고 ③ 고객사가 최종 배포할 때도 포함해야 함을 알려야 해서, SDK 가이드에 오픈소스 라이선스 항목을 추가했다. 12-29 Navi SDK용 OpenSourceLicense 문서를 정리했다(상단은 AIR와 같고 문의 메일은 뺌). 대만 사업 맥락은 [[orbis-taiwan-business-2025]].
