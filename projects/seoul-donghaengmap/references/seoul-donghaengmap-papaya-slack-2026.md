# 서울동행맵 파파야 협업 채널 2026

서울동행맵의 **지하철 실내 지도·측위·내비게이션**을 맡는 외부 업체 파파야와 아이나비시스템즈의 소통 채널이다. 2026-08-13에 열렸다. 파파야는 공식 컨소시엄 구성원이 아니라서 컨소시엄 채널([[seoul-donghaengmap-consortium-slack-2026]])과 분리돼 있다. 사업 전체는 [[seoul-donghaengmap]], 지하철역 난이도는 [[seoul-subway-station-grade]]에 있다. 사람은 역할로 적었고, 서버·저장소 주소, IP, 토큰, 인증정보, 도면·POI 파일 링크는 값을 옮기지 않았다.

## 1. 제공물 구성

| 구분 | 내용 |
|---|---|
| 측위 SDK(SDAS) | 실내외 측위 Android SDK. 의존성은 파파야 저장소에서 받으며 아이나비 공인 IP 화이트리스트로 접근을 제어한다 |
| 측위 API | `/navigating/estimate-sdas`. 기존에는 헤더에 `App-Code`가 필수였으나 9-21에 **Bearer 토큰 방식**으로 바뀌었다. 서울동행맵 전용 토큰이 새로 나왔고 Bearer를 쓰면 `App-Code`는 생략한다 |
| 경로탐색 API | 실내는 `POST /navigating/find-route/indoor`(`fromPoiId`, `toPoiId`). 설명서에 파라미터 설명이 빠져 있어 문서를 갱신하기로 했다 |
| Fusion SDK | 9-21에 전달된 통합 SDK. 측위 개선, 움직임, 경로 매칭(보정)을 합쳤다. REST 통신을 SDK에 내장해 앱의 역할을 줄이는 방향. 매뉴얼, 예제 프로젝트, 전용 인증정보가 함께 왔다 |
| 데이터 | 판교역 실내도면(아이나비 포맷으로 변환, 파파야가 채울 수 있는 데이터만 포함), POI 리스트 CSV, shp 변환 데이터. 엘리베이터·에스컬레이터·계단 시설 정보 포함 |

- 길찾기 API는 9-21에 **가장 가까운 실내 진입점으로 길찾기**하는 기능을 배포했다(`from`이 좌표와 층이고 `floor = 0`이면 결과의 `startPoint`가 실내 진입점이 된다). 응답 DTO가 바뀌어 응답 쪽만 참고하라고 안내했다.
- 길찾기 결과로 위치를 보정하는 방식은 새 SDK에 경로를 입력하고 측위를 요청하는 구조로 적용할 예정이다.
- Swagger 필드 주석이 부족하다는 요청에 파파야는 자기들이 쓰는 API를 그대로 줘서 불필요한 필드가 섞여 있다며, 정리하거나 주석을 추가해 재공유하기로 했다.
- **보안 참고**: 채널 본문에 저장소 인증정보, API 토큰, 서버 주소, IP가 평문으로 올라와 있었다. 위키에는 옮기지 않았다. 슬랙 쪽 회수·교체 필요 여부를 확인하는 편이 좋다.

## 3. 판교역 샘플앱 테스트 결과 (09-21)

**이슈**
- 실내 위치 측위 API의 **오차 범위가 너무 크다**. 영상으로 공유됐고 노란 원은 측위 API가 준 위치, 빨간 원은 아이나비가 경로로 매칭한 위치다.
- 길찾기에서 실제로 갈 수 없는 경로가 생성되는 케이스가 있다.
- 판교역 중앙 광장(1층 실외)에서도 실내로 판단한다.

**파파야 답변과 합의**

| 요청 | 답 |
|---|---|
| 측위 정확도·신뢰도 수치 | 내부에 precision 값은 있으나 정확도·신뢰도와는 거리가 있다. 일단 전달하는 방향으로 수정하겠다 |
| 측위 개선 | 9월 말~10월 초 SDK 버전업(측위, 움직임, 경로 매칭 추가). 이후 통합 SDK를 전달 |
| 길찾기 결과로 위치 보정 | 새 SDK에 경로를 입력하고 측위를 요청하는 방식을 적용 예정 |
| 실외에서 가까운 입구점으로 길찾기 | 가능. 이후 기능 배포 |
| 층별 이동 시설 정보 | CSV와 도면에 담아 전달. 길찾기 응답에 층별 이동지점 종류(엘리베이터, 에스컬레이터, 계단)를 함께 주는 방안은 내부 논의하겠다고 함 |

- 아이나비는 ID로 받으면 이동지점 변환이 필요하고 종류를 같이 받으면 간단하다는 의견을 냈다. 원본 CSV의 `poi_id`는 도면 geojson의 `fmcode`로 종류를 판별할 수 있고, 그 외 ID는 매핑 테이블이 필요하다.
- 목적지가 에스컬레이터가 아니면 1번 출구에서 B2로 갈 때 **계단으로만 안내**된다. 파파야는 수직 이동 동선을 cost로 관리하며 현재 설정의 결과라고 했다. 의도된 설정인지는 확인 중이다.
- 10-7 아이나비의 API 업데이트 검토: 실외 출발 시 가까운 진입점으로 정상 탐색되고 응답에 이동지점 정보가 포함된다.

## 4. Fusion SDK 테스트와 시나리오 문의 (10-27)

**테스트 결과**
1. GS 편의점 탐색 시 개찰구를 통과하는 길안내가 나온다(기존 이슈, 실제로는 개찰구를 지날 필요 없음).
2. 제공된 예제의 B2 역무실 POI도 개찰구를 통과한다.
3. 층을 바꿀 때 전환이 이전보다 느리다. 층 이동 후 다른 위치로 측위되고 본 경로에 붙기까지 수 초가 걸린다.
4. 승강장(탑승 위치) POI가 없어 지하철 탑승 안내는 계단이나 승강장 앞까지만 된다.
5. 인접 출구에서 길찾기를 하면 교통약자 안내가 안 되고 근처 엘리베이터도 매칭되지 않는다.
6. 1번 출구 방향으로 가면 계단·에스컬레이터 중간쯤부터 실외로 측위되고 그 뒤로는 도착 안내가 안 나온다. 도착 안내가 없을 때 실내 내비를 종료하는 기준이 필요하다.
7. 1번 출구 기준 계단 경로로만 탐색된다. cost에서 이동수단별 교통약자 항목 비중 조정이 필요하다.
8. POI 검색을 API로 제공하는지, 전달된 POI CSV로 처리하는지, POI를 구분할 상세 정보(예: 계단은 ID만으로 어느 계단인지 알 수 없음)가 필요하다.

**시나리오**(판교 인근 출발 → 서울시청, 교통약자): 실외 도보(실외 SDK) → 판교역 1번 출구에서 신분당선 강남 방면 승강장(파파야 실내 내비) → 지하철 판교→강남(신분당선), 2호선 환승, 시청역 → 하차 승강장에서 출구(실내 내비) → 시청역 출구에서 서울시청(실외 SDK). 앱은 역사 진입 시 실외 안내를 일시정지하고 실내 내비로 전환한 뒤 끝나면 실외로 복귀한다.

**문제**: 실외 경로에서 지하철 구간이 승차역 출구와 하차역 출구 두 지점으로만 제공돼, 앱이 실내에서 어디까지 안내해야 하는지 모른다. 승강장 위치와 출구 정보가 없다.

**문의**: ① 승차역에서 현위치와 도착역(또는 노선·방향)을 주면 해당 방면 승강장 탑승 위치까지 실내 탐색이 되는가 ② 교통약자용 탑승 위치(엘리베이터 인접 칸, 휠체어 탑승 위치)를 목적지로 지정할 수 있는가(장애인은 그 위치까지, 비장애인은 가장 가까운 승강장까지) ③ 하차역에서 지정 출구(또는 엘리베이터 경유 출구)로 탐색이 되는가 ④ 승강장이 여러 개인 역에서 노선·방향 기준 구분이 되는가 ⑤ 어렵다면 역사 조사 시 "역+노선+방향 → 승강장 POI ID" 매핑 테이블을 줄 수 있는가. 대상은 시범 구축 11개 역사, 현재는 판교역 테스트베드이며 강남역 환승 구간은 제외한다. 앱 시연은 시청역에서 하므로 판교역에 준 shp와 POI 리스트를 시청역 데이터로 달라고 요청했다. 파파야는 검토 후 답하겠다고 했다.

## 5. 감리와 서울시 협의

- **감리 산출물(09-30)**: 1차 설계 감리 10-7~10-15. 파파야는 실내 지도 DB 설계 항목(실내 지도와 센서맵) 작성이 필요했다. 아이나비 포맷이 Apple IMDF를 커스터마이징한 것이라 지원을 요청한 것이었다. 제안요청서에는 어드민 웹사이트로 업데이트를 관리하는 기능이 있어 설계 산출물이 필요했으나, **시청과 데이터 관리를 유지보수 용역으로 처리하고 관리자 기능을 제외**하기로 협의해 이 DB 설계 산출물은 작성하지 않기로 했다. 회의록 증빙은 아이나비 총괄 이사가 남기고, 파파야 대표가 동의했다.
- **서울시 미팅 안건(10-21)**: ① 프로젝트 진행 현황 리뷰(앱, 서버, 지하철역사 구축) ② **실내 내비게이션이 Android만 가능한 이유**(iOS 불가에 대한 기술적 설명 필요) ③ 시범 서비스 오픈(2027-01)과 최종 오픈(2027-06) 범위 협의. 파파야는 자료를 메일로 보냈고 그 내용은 이 채널에 없다. iOS 불가 사유는 확인되지 않는다. ^[ambiguous]
- 미팅 전에 아이나비와 주관사가 크로스체크하고, 같은 요청을 여러 번 한 점에 양해를 구했다.

## 6. 미해결

- 10-27 테스트에서도 층 전환 지연과 실외 판정이 보고돼 측위 오차가 얼마나 개선됐는지 불확실하다.
- 측위 정확도·신뢰도 수치의 형태와 길찾기 응답의 이동지점 종류 포함 여부.
- 승강장 POI와 "역+노선+방향 → 승강장 POI" 매핑 테이블 제공 여부, 실내 내비 종료 기준(도착 안내 없는 경우).
- cost 가중치 조정과 계단 편향이 의도된 설정인지.
- POI 검색의 제공 방식(API 대 CSV)과 시청역 데이터 전달 일정.
- 시범 서비스(2027-01)와 최종 오픈(2027-06) 범위. 10-28 서울시 미팅 결과는 채널에 없다.
- 시연 샘플앱 소스는 파파야가 공유가 어렵다고 했고 이후 공유 여부는 불확실하다.
