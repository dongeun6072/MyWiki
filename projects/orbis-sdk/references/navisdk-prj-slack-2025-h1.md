# Slack #10_prj-orbis-navisdk 대화 (2025 상반기)

TomTom Orbis Map NaviSDK POC(대만향) 공개 채널 `#10_prj-orbis-navisdk`의 2025-02-01~06-30 구간 기록이다(채널은 2025-02-03 개설, 구간 내 마지막 메시지는 06-19). 프로젝트 허브는 [[orbis-sdk]], 같은 해 개발 흐름은 [[orbis-navisdk-development-2025]], 대만 사업 맥락은 [[orbis-taiwan-business-2025]], 상용화 스크럼은 [[navisdk-commercialization-scrums-2025-2026]]을 본다. 다른 기간 기록은 [[navisdk-prj-slack-2025-q3]], [[navisdk-prj-slack-2025-q4]], [[navisdk-prj-slack-2026-h1a]], [[navisdk-prj-slack-2026-h1b]]에 있다.

구간 내 채널 메시지 52건(입장·채널 설명 설정·캔버스 갱신 알림 포함)과 스레드 답글 58건을 모두 읽었다. 답글이 달린 스레드 19개를 전부 열었고 미열람은 0개다. 첨부는 파일명·종류만 기록했다(내용 미열람). 사람은 역할로 적었고, 계정·서버 주소·링크·인증 URL은 옮기지 않았다.

## 1. 채널 개설과 참여자 (2/3~2/25)

- **2025-02-03**: 개발 PM 수석이 채널을 만들고 채널 설명을 "Orbis Map NaviSDK POC"로 설정했다가 곧 "TomTom Orbis Map NaviSDK POC"로 바꿨다. 같은 날 개발·사업·데이터 담당 다수가 입장했고, "TomTom Orbis Map NaviSDK POC를 위한 채널이며 관련 내용은 이 채널에서 소통"한다고 @channel 공지했다.
- 사업(전략)팀 대리가 이 프로젝트를 담당하게 되었다고 인사했고, 같은 팀 사원이 TomTom과의 커뮤니케이션 지원을 약속했다.
- 이후 합류: 02-04 MMC(맵매칭) 엔진 담당 수석, 로그 코스 작성 담당 책임, 02-25 교통정보 연동 담당 주임.
- 참여 역할: 교통정보·엔진 팀장, 탐색엔진 담당 수석, 지도 데이터 담당 책임, MMC(맵매칭) 엔진 담당 수석, 사업(전략)팀 대리·사원, 기타 개발 인원(PAMS 안내 때 CC로 등장).

## 2. WBS와 일정 관리 (2/4~6/19)

- **2025-02-04**: 개발 PM 수석이 이미 전달받은 내용으로 WBS 초안(탐색·MMC 파일, v0.1)을 올리고 탐색·MMC 일정이 맞는지 확인 요청. 교통정보·엔진 팀장이 MMC 엔진 일정을 워킹데이 기준으로 수정한 파일을 회신했고, 탐색엔진 담당 수석은 "탐색엔진 일정 이슈 없음"이라고 답했다.
- **2025-03-07 주간회의 안내(Path-1, 15시)**와 스레드 정리 항목:
  - 이슈 체크리스트 공유(구글 시트, 링크 있음(미수록)). 메일을 보내면 권한을 부여하겠다고 안내. 체크리스트 v0.9 xlsx 첨부.
  - 지도 관리 프로세스 정리: 이슈 체크리스트 항목 추가는 사업(전략)팀 대리, "기본 지도 데이터 전달 흐름" 초안은 지도 데이터 담당 책임.
  - WBS 담당: 교통정보 엔진은 교통정보·엔진 팀장, 지도 데이터 관리는 탐색엔진 담당 수석과 지도 데이터 담당 책임이 개발 항목·일정 확인.
  - 주간회의는 매주 목요일 15시 Path-1로 확정.
  - 03-10 개발 PM 수석이 정리되는 대로 공유 요청.
- **2025-03-10 교통정보 일정 안내(팀장)**: 이슈 확인 때문에 TomTom과 소통 중이며 검토는 이번 주 내 마무리될 것으로 보임. **03-12** 향후 필요 항목 공유: 서버는 현재 개발된 서버를 그대로 쓸 수 없어 변경이 필요하며, 서버 구축 방안과 실진행 일정은 주간회의에서 논의. 전체 소요 약 10.5D로 아래와 같다.
  - 생성/전송 엔진 포팅 3D(아나콘다 환경 구축·생성, 전송 엔진 포팅/테스트)
  - 모니터링 개발 4.5D(생성 시간, 생성 결과(성공/실패/정상화), 서버 프로세스 kill 여부, 서버 디스크 용량 확인 시나리오 정리와 로그 개발, 모니터링 슬랙 봇 작성·테스트)
  - 운영 개발 3D(생성된 교통정보 파일·로그 정리 도구, 이상 감지 시 재기동 로직)
- **2025-03-20, 03-27**: 개발 PM 수석이 해당 일자 WBS(OrbisMap_NaviSDK_CheckList v1.0, 250320/250327)를 공유. 03-27에는 시안(Key Color) 스크린샷 2장도 함께 올렸다.
- **2025-03-27 주간회의(Path-3로 장소 변경)**: 교통정보·엔진 팀장이 다른 미팅으로 시간을 놓쳤다고 답하며 회의 진행, 이슈는 이후 대응하겠다고 함.
- **2025-04-09 전체 구성도**: 개발 PM 수석이 "OrbisMap NaviSDK 전체 구성도"(png)를 공유하며 잘못된 부분 의견을 요청. 4/9, 4/11, 3/11, 3/14에 캔버스 탭 갱신 알림이 있다(개발 PM 수석이 편집).
- **2025-05-22**: 개발 PM 수석이 병원 방문으로 반차를 써서 당일 주간회의는 사업(전략)팀 대리가 진행. 탐색엔진 담당 수석이 "아프지 마세요"라고 응원.
- **2025-06-19**: 개발 PM 수석이 이번 주간회의는 따로 진행하지 않으며 주요 이슈가 있으면 공유해 달라고 안내(채널 내 구간 마지막 메시지).

## 3. 대만 GPS(NMEA) 로그와 맵매칭(MMC) 테스트 (2/10~4/2)

배경: 맵매칭 엔진은 지도는 준비됐지만 GPS 로그가 없어 매칭 작업을 못 하는 상황이었다. 국내는 직접 운전해 수집할 수 있으나 대만은 현지 수집에 제약이 있어 대안이 필요했다(2025-02-13 사업(전략)팀 대리 정리).

### 3.1 요청과 수집 방식 결정
- **2025-02-10**: 개발 PM 수석이 MMC 엔진용 대만 GPS(NMEA) 로그 필요성을 확인하고 "로그 아이나비 전달 일정"과 "코스별 로그(고속도로, 일반도로, 터널 등)" 외 추가 요구가 있는지 문의. 교통정보·엔진 팀장은 국내와 다른 코스 위주가 좋으나 전달이 어려울 수 있으니 필수 코스 위주로 요청해 달라고 답. **02-11** 로그 코스 작성 담당 책임이 GPS 수집이 필요한 도로 코스 문서(docx, pdf)를 작성해 전달.
- **2025-02-13 사업(전략)팀 대리 계획**: ①TomTom이 대만 오피스를 가지고 있어 NMEA 포맷 GPS 로그를 제공받을 수 있는지 사업팀이 문의 ②불가하면 대만 현지에서 실제 주행 로그 수집 대행이 가능한지 요청, 이를 위해 안드로이드 앱을 전달해 수집하도록 협조 요청 예정.
- **2025-02-27** TomTom이 제공한 대만 지역 NMEA 형식 파일(FILE250217 계열 .NMEA) 1건을 MMC 테스트에 쓸 수 있는지 사업(전략)팀 대리가 문의. MMC 엔진 담당 수석 답변:
  - 포맷 자체는 정상이고 사용 가능하나 주행거리가 짧아 긴 로그가 필요(02-27). 사업팀이 TomTom에 요청하기 전 확인 사항: 앞서 공유한 PDF 코스가 반드시 포함돼야 하는지, 필요한 최소 길이(시간·거리).
  - TomTom 답변: 제공 가능한 NMEA는 모두 5분 분량이며 30분 이상은 없고, 5분짜리 여러 개는 가능.
  - MMC 엔진 담당 수석 판단: 5분 로그가 한 사용자의 연속 데이터라면 순서대로 이어 붙여 맵매칭에 쓸 수 있으나, 서로 다른 사용자의 로그라면 어렵다. 가급적 긴 로그가 좋고 최대 30분 정도라도 있으면 기본 검토는 가능. 다양한 케이스 테스트를 위해서는 다양한 주행 케이스가 필요.
  - TomTom 원본(raw) 데이터와 GPX를 주면 NMEA로 변환 가능한지 문의 -> MMC 엔진 담당 수석: 원본이 어떤 형식인지 먼저 확인 필요, GPX는 변환 도구와 변환 후 사용 가능 여부를 별도 검토해야 하며 내부적으로 GPX를 쓰지 않아 지금까지 검토된 바 없음. GPX 샘플을 주면 변환 가능 여부를 검토하겠다고 함.
  - **02-28** 사업팀이 추가로 받은 NMEA(zip, 한 장치·한 사용자의 1시간 분량 추가)를 전달하자 MMC 엔진 담당 수석이 "한 사용자의 연속 NMEA가 공유된다면 맵매칭 테스트가 가능하며, 다양한 케이스의 로그만 제공되면 된다"고 확인.
- 결과: 02-27~28 시점에 TomTom 제공 형식은 사용 가능, 다만 길이와 케이스 다양성이 부족하다는 것이 결론이었다.

| 날짜 | 전달 내용 | 파일 |
|---|---|---|
| 2025-03-28 | TomTom이 한 차례 제공한 뒤 외부 인력으로 추가 수집, 맵매칭 테스트 요청 | 03-27 수집 nmea_log 4건(0.8~9.2MB) |
| 2025-03-31 | 3개 파일, 세부 내용은 스레드 댓글로 기재 | 03-29, 03-30 수집 nmea_log 3건(1.1~3.4MB) |

- **2025-04-01 교통정보·엔진 팀장**이 공유된 GPS 로그가 총 7건이라며 MMC 엔진 담당 수석에게 검토 후 회신 요청. 같은 날 **MMC 엔진 담당 수석**이 "NMEA 로그상 문제는 없어 보이고 해당 로그로 테스트가 가능할 것 같다"고 회신. 이후 맵매칭 테스트 결과는 이 구간 채널에 올라오지 않았다.

## 4. 교통정보(Traffic Flow, Incidents) 확인 (2/12~3/12)

- **2025-02-12 OpenLR 확인**: 개발 PM 수석이 Orbis Map에 TomTom OpenLR 정보가 있는지 지도 데이터 담당 책임에게 문의(캡처 첨부). 답변: 원도에서 OpenLR에 대한 직접 참조 값은 없고, OSM ID가 OpenLR과 연관된 것으로 알고 있으며 자세한 내용은 교통정보 담당 팀장이 알 것.
- **2025-02-13 사업팀 대리 정리(스레드)**:
  - CES 시연: 출발지와 목적지를 설정해 아이나비, Google Maps, TomTom의 경로 탐색 결과를 동시에 표출(Test 웹사이트 "Orbis Route Verification" 활용). CES에서 공개된 교통정보는 임시용 데이터였고, 표출에 쓴 원천 데이터와 수집 방법(TomTom API)을 참고해 향후 활용 방안을 정할 수 있음.
  - 상용화 시 교통정보 제공에는 서버 구축이 필요해 추가 비용이 생길 수 있어 비용·일정 내부 논의 필요. 교통정보가 길찾기용인지 지도 표출용인지 정하고 대만향 Navi SDK 활용처를 사업팀과 개발팀이 협의해야 함.
  - 개발 PM 수석: 교통정보 엔진 담당과 얘기한 결과 CES 때 TomTom API로 탐색엔진에 교통정보가 반영되도록 이미 개발해 신규 개발은 불필요하고 차후 포팅 정도만 하면 될 것으로 보임.
  - **02-14** 개발 PM 수석이 CES 때 시연용 임시 URL 2종(traffic flow, incidents)을 받아 TomTom 개발자 사이트에서 확인한 결과: Traffic APIs의 Intermediate Traffic API(Traffic Flow는 Protobuf, Traffic Incidents는 DATEX II)를 쓰면 문제없을 것으로 판단. 임시 URL 본체와 식별자는 원본에 있음(미수록).
- **2025-02-24 TomTom 안내 엑셀**: 사업팀 대리가 TomTom 담당자로부터 "Intermediate Traffic Flow and Incidents" 엑셀 파일을 쓰라는 안내와 함께 받은 파일(9.9KB)을 전달.
  - 02-25 개발 PM 수석이 검토 요청. 교통정보·엔진 팀장 답변: 엑셀 내용이 2024년 당 팀이 TomTom 교통정보 POC를 진행할 때 TomTom에게서 받은 엑셀과 100% 일치하고 키 값도 동일. 엑셀 키를 그대로 쓰는지, 자사가 발급받은 키로 바꿔야 하는지 확인 요청.
  - 개발 PM 수석: CES 때 받은 Key 값과 ProductName을 이번에도 쓰는 것으로 TomTom과 정리된 상태라 추가 작업은 없을 것으로 예상(키 값 자체는 미수록).
- **2025-03-12 TomTom 확인 요청**: 사업팀 대리가 이메일로 받은 "교통정보 연동 과정의 데이터 정합성 문제"에 대해 사업팀이 TomTom에 확인 요청 메일을 보냄. 기존 Traffic Flow 이슈가 여전히 남아 있고, 신규 이슈까지 발생해 추가 조치가 필요한지 확인을 요청한 내용이며 TomTom 업데이트가 있으면 전달 예정. 이슈 관리를 위해 OrbisMap 체크리스트에 관련 항목을 등록. 대만향 NaviSDK의 소통 채널을 슬랙으로 하기로 했으니 이메일 회신이 필요하면 말해 달라고도 덧붙임(이전 TomTom 교통정보 협의는 [[tomtom-traffic-flow-openlr-inquiries-2024]]).

## 5. Orbis Map 데이터 수령과 검토 (2/11~4/29)

- **2025-02-11 Orbis Map v25060**: 사업(전략)팀 사원이 TomTom Orbis Map 새 버전(v25060) 릴리즈 파일을 지도 데이터 담당 책임에게 전달(1.3GB, 용량이 커 다운로드 링크로 공유, 링크 있음(미수록)). 홍콩과 대만이 모두 포함. 책임은 같은 날 ORBIS Taiwan v25060 도로망 데이터 관련 내용을 메일로 전달했으니 사업팀 사원과 탐색엔진 담당 수석에게 확인 요청.
- **2025-02-18**: 개발 PM 수석이 탐색엔진 담당 수석에게 OrbisMap Reader 배포 일정이 당일까지로 되어 있으니 진행상황 공유 요청(답글 없음).
- **2025-03-10 기본 지도 데이터 전달 흐름**: 지도 데이터 담당 책임이 흐름 문서(원드라이브 문서, 링크 있음(미수록))를 공유. 후속 스레드:
  - 개발 PM 수석이 교통정보 서버와 Agent(CDN) 서버를 장표에 추가했다고 알림.
  - 사업팀 대리가 체크리스트에 이슈를 추가.
  - 탐색엔진 담당 수석이 경로탐색 서비스 데이터 작업·업데이트·배포 관련 내용을 장표에 추가.
  - 개발 PM 수석이 데이터 전달받는 방법(이메일, FTP, NAS 등) 추가 가능 여부 문의. 지도 데이터 담당 책임 답변: 도로망 ShapeFile은 이메일로 내용을 전달하고 데이터는 전략 POC 그룹 NAS의 HTTP 링크로 공유 중이며, 대용량이라 FTP·공용 NAS 전달 방식을 추가할 수 있을 것 같음.
  - 03-11 개발 PM 수석이 장표에 데이터 전달 방법 기재 요청, 사업팀 사원과 탐색엔진 담당 수석이 각각 장표에 반영. **03-13** 사업팀 사원이 "오르비스 맵 데이터 발행 주기"를 장표에 추가.
- **2025-03-26 CDN 테스트용 지도**: 개발 PM 수석이 CDN 테스트를 위해 OrbisMap 서비스 지도 데이터 공유 가능 여부를 탐색엔진 담당 수석에게 문의. 탐색엔진 담당 수석이 메일로 "INAVI Route Server for Taiwan" 서비스 데이터(v25060)를 전달했다고 답.
- **2025-03-05**: 탐색엔진 담당 수석이 대만 경로 탐색 서버 업데이트 관련 메일을 개발 PM 수석에게 알리고 참고하라고 공유(교통정보·엔진 팀장, 지도 데이터 담당 책임 등 CC). 서버 규격은 [[taiwan-routeserver-api]] 참고.
- **2025-03-19 도로명 분석**: 지도 데이터 담당 책임이 안내용 명칭으로 쓸 수 있는 도로명 분석 공유. 링크 중 63.5%가 도로명을 가지며, 도로명을 가진 링크는 거의 모두(99.97%) 중국어 번체·영문 명칭을 가지고, 각 명칭에 대한 발음기호 표시를 가진 비율은 중국어 번체 97.6%, 영문 99.9%.
- **2025-03-27 Ferry 데이터 검토**:
  - Ferry 데이터는 존재하나 데이터 상의 문제로 현재 경탐에 사용하기는 곤란하다는 결론(지도 데이터 담당 책임).
  - TomTom에 문의할 2건: ①Way ID 중복: 1개의 Ferry 경로가 여러 Feature로 분리돼 있는데 각 Feature의 Way ID가 동일(중복 ID 22개 계열, 최대 14회 반복, 목록은 원본에 있음). ②Geometry 중복: 동일한 Geometry를 가진 Feature가 존재(Feature 선택 시 2개 항목이 나옴). 다만 supported 태그로 필터링이 가능해 큰 문제로 보이지는 않는다고 판단.
  - 사업팀 사원이 TomTom에 문의하겠다고 답했다. 문의 결과는 이 구간에 올라오지 않았다.

## 6. PAMS 개발 공수 입력 (3/10~3/17)

- **2025-03-10**: 교통정보·엔진 팀장이 해당 프로젝트가 PAMS에 등록돼야 한다고 알림. 이미 등록돼 있다면 알려 달라, 없다면 사업부에서 추가하는 것이 맞아 보인다, 이날부터 PAMS 입력 일정이라 빠르게 확인 요청.
- 사업팀 대리 확인: 사업팀은 한 번도 다뤄본 적 없는 프로그램이라 안내 부서부터 확인했고 공수 입력 요청 부서는 관리 과장 쪽으로 확인됨. 이어 해당 과장이 프로젝트를 생성해 주기로 했고, 생성 이후 개발 공수 입력 가능(프로젝트 생성 화면 캡처 첨부).
- **03-17** 개발 PM 수석이 여러 이유로 PAMS 소분류를 세분화했다고 개발 인원(CC)에게 공유(화면 캡처 첨부). 교통정보·엔진 팀장이 관련 담당자 CC 추가.
