# Slack #01_inavi_air 대화 (2025 상반기)

아이나비 에어 x Auto x CarPlay 비공개 채널(2022-07 개설)의 2025년 1월~6월 기록이다. 프로젝트 개요는 [[inavi-air]], 같은 해 운영 이력은 [[air-operations-2025]], 버전별 변경은 [[air-app-version-notes-2025]], 앱/SDK 개발자 채널은 [[air-nsdk-dev-slack-2025]]를 함께 본다.

2025-01-01~06-30 채널 메시지는 122건(봇 배포 알림 포함)을 읽었고, 답글이 달린 스레드 69개를 모두 열어 반영했다. 사람 이름은 쓰지 않고 역할(앱 개발자, 서버 개발자, 기획자, 디자이너, 안내엔진 개발자, DP 엔진 개발자, 사업 담당, 총괄 등)로 적었다. 서버 주소, 키, 링크, 전화번호, 메일은 원본에 있으나 미수록이다. 채널 구성은 대체로 총괄(요청/지시) -> 앱 개발(iOS/AOS) -> 서버(Agent) -> 엔진팀(안내/DP) -> 기획/디자인 순으로 요청과 확인이 오가는 구조이다. ^[inferred]

## 1. 시간제 통행규제 (3월 패치의 중심 주제)

| 시점 | 내용 |
|---|---|
| 01-14~20 | 탐색엔진 규격이 바뀌어 Agent 대응 요청. Request에 "시간제 통행규제 사용/무시" 옵션, Response(요약/링크 정보)에 규제 유무 추가. 서버는 설 연휴 이후 로그 API 규격과 함께 상용 반영 예정이라고 답함 |
| 01-24 | Agent가 탐색엔진 프로토콜 2.2.6(시간제 통행제한 무시 옵션 `ignoreTimeRestrictedZone`)과 출발지 고속도로/자동차전용/도시고속 회피(`useHighwayProjectionStart`, `useHighwayProjectionEnd`) 규격을 반영. 일반 경로 탐색, 경로 리스트, 재탐색, 요약결과 경로 탐색 4종에 적용 |
| 02-18 | 총괄이 3월 패치 항목으로 "시간제 통행규제 서비스 적용" 티켓을 기획(시나리오는 기획 책임자가 작성)과 Agent로 나눠 생성. 02-20 서버 쪽 시간제 통행규제 IF 반영 완료, 상용 반영은 수요일(03-12 전후)로 조율 |
| 03-07 | 안내엔진 팀이 SMR(Android)에 `openRoadblockingTimeData`/`closeRoadblockingTimeData`를 추가하고, 찾은 링크의 시간제 통행규제 여부(`m_bIsRoadBlocking`)를 확인하는 안내엔진을 전달. iOS SMR은 다음 주 예정 |
| 03-12 | SMR 라이브러리 의존성을 제거하고 안내엔진이 직접 처리하도록 변경. 규제 데이터 파일을 `mrdata` 폴더에 복사하는 방식이며, 직전에 발행한 SMR(0307)은 이전 버전으로 롤백. iOS는 `FindLinkAndNodeExceptHighway` 시그니처에 `bGetRoadBlockingTime` 인자 추가. 해당 파일은 별도 DB이며 atl 묶음(1회성 다운로드)에 포함하는 것으로 협의 ^[inferred] |
| 03-13 | 새 엔진 적용 후 앱이 `FindLinkAndNodeObj` 호출 시 UnsatisfiedLinkError 발생. 원인은 엔진팀이 의도치 않게 `bExceptHighway` 파라미터를 추가한 것이었고 JNI 함수 파라미터를 롤백해 재발행 |
| 04-02 | 규제 데이터 파일이 없어도 안내엔진 초기화가 성공하도록 수정(필수 DB가 아니므로) |
| 04-22 | 시간제 통행규제 팝업 문구 변경 요청: "시간제 통행제한 도로가 포함되어 목적지 진입이 어려울 수 있습니다. 그래도 진행하시겠습니까?", 버튼 "목적지 재설정"/"계속 진행". 텍스트 색상 범위 지정 필요. CarPlay에서 문구가 잘려 Auto(AA)/CarPlay(CP) 문구를 통일하기로 함 |
| 04-25~05-08 | 안내엔진: 시간제 통행규제와 시간제 회전규제를 구분(04-25) -> 시간제 통행/회전 규제 판단 제거(04-30) -> 타임도메인 관련 SMR Reader 수정과 시간제 통행/회전 규제 판단 재추가(05-08). 현재 시각은 MMC 값이 있으면 MMC 시간, 없으면 단말 시간을 사용 |
| 04-29~05-08 | 주말 주행 중 직진 도로를 골목으로 우회 안내한 사례 조사. 앱은 최초 탐색을 스쿨존 "무시"로 요청하고 재탐색을 "회피"로 요청했으나 Agent는 스쿨존 옵션을 따로 제어하지 않았고, 서버가 탐색엔진에 보내는 패킷의 비트 설정 오류(시간제 통행규제가 OR 조건으로 묶여 3개 옵션이 모두 활성화됨)가 원인으로 확인. 탐색 서버가 수정해 에어/토요타/하이브리드 모두 반영 ^[inferred] |
| 05-15 | 안내엔진(iOS 03.05.27 로그 관련 비정상 종료 개선) 전달 |

### 시간제 규제 이후의 안정성 이슈
- iOS 03.05.27(479) 출시 후 안내엔진 소멸자 쪽 비정상 종료가 늘어(안내 관련 11건/10명 -> 55건/44명) 05-15에 03.05.28(480)을 "안내엔진 교체만" 하는 긴급 패치로 심사 제출. 정상 종료 free user 비율이 98%에서 91.61%로 약 6%p 하락했고, 원인은 시간제 규제 개발 중 동적 할당 메모리를 두 번 해제한 소멸자 코드로 추정됨. Android는 해당 이슈가 없어 iOS만 진행.

## 2. 로그 API 개편 (선행 연동)

- 01-20: 서버가 Log API 규격을 갱신(공통 헤더, 공통 내역, User Event). Android Auto 로그, 에어 연구소, 에어봇 사용, 주변 인기장소 정보 로그를 `/userEvent`로 보내도록 신규 추가. 에어 캐시 관련(캐시 발생/적립/쿠폰 구매)은 기존 로직 재사용 가능하여 제외.
- 02-04~02-11: 2월 패치 항목 "신규 규격 로그 적용"을 앱에서도 중순까지 반영. 앱 사양과 규격이 달랐던 "안내볼륨", "속도별 지도 확대/축소" 항목은 규격서 1.5.1에서 수정.
- 02-11: 개발서버 접속용 테스트 빌드를 iOS(TestFlight 03.05.26 473)와 Android(APK 03.05.49 301415)로 배포. 총괄이 "개발서버 연동 같은 주요 내용은 배포 시 미리 공유해 달라"고 요청.
- 02-18: 로그 API 검증이 추가로 필요하여 신규 규격 반영 연기. 개발 서버에는 "신규 규격 대응 이전" 상태로 반영하고 기존 규격이 앱에서 잘 동작하는지 확인 요청. 04-02에 사용자 로그 규격 수정이 앱 발행분에 포함됨.
- 03-13 선행 측 문의 점검 결과(원인과 처리 방침):

| 로그 | 문제 | 원인/처리 |
|---|---|---|
| Android Auto 설정(ANDROID_AUTO_SETTING_A) | 안내볼륨, 음악 볼륨 자동 조절 필드 공백 | 규격서 필드명이 잘못돼 AOS가 그 이름으로 전송 -> 규격서 수정, 앱 수정 |
| 캐시 적립(EARN_CASH_A) | 최초 가입 적립 항목 요청 | 로그인 후 첫 주행 적립(500캐시)을 `FIRST`로 추가. 주행 적립(예: 17캐시)과 합산하지 않고 2건으로 별도 전송하기로 결정 |
| 에어 연구소 설정(AIR_LAB_SETTING_A) | iOS 0/1, Android OFF/ON 불일치, routeOpt 공백 | iOS를 ON/OFF로 수정(앱), routeOpt는 Agent 필드명 오류(서버). 기존 `/userEvent` 사용 불가라 API 재설계, 내비 표출 UI 기준 "필드명/On\|..." 형식으로 파라미터 순서와 이름을 규격과 동일하게 전송 |
| 통합검색(UNITED_SRCH_A) | 에어봇 searchType 로그 미유입 | `searchType`에 AIRBOT 항목 추가(서버), 앱 반영 |
| 주변인기장소(NEARBY_FAV_POI_A) | 미유입 | AOS 앱 수정. 이후 "지역명", "Fivepin 메시지" 필드 제거 |
| 추가 이슈 | CarPlay 연결 시 CARPLAY_SETTING_A 중복 2회 인입, 에어 연구소 뒤로가기 시 로그 인입 불일치 | 앱 수정 대상으로 공유 |

- 이후 개발서버에서 로그 확인 중 에어봇 관련 flag(gen_ai_flag)가 false로 내려와 변경 요청. 에어 연구소 API는 개발서버에서 404가 났는데, 원인은 서버 개발자가 티켓별로 브랜치를 나누면서 MapsSDK 신규 AppKey 브랜치를 병합하지 않은 채 개발서버에 배포한 것이었다.

## 3. MapsSDK 신규 인증과 DP 엔진 (03-19~)

- 03-19: MapsSDK 인증 체계가 바뀌어 SDK 업데이트와 신규 AppKey가 필요. AppKey는 Agent가 서비스게이트 응답(`inaviAuthKey`)으로 내려주는 구조이므로 앱 버전에 따라 기존/신규 키를 구분해야 함. 신규 키는 AOS 03.05.51 이상, iOS 03.05.27 이상부터 내려가며(03.05.50은 기존 키) 개발서버에서 AOS/iOS 모두 정상 동작 확인. 키 값은 원본에 있음, 미수록.
- DP(Display) 엔진 발행 이력(DP 엔진 개발자):
  - iOS v0.0.6.x(4d) 01-20: curl/openssl 라이브러리 버전 업데이트(curl 7.71 -> 8.9.1, openssl 1.1.1p -> 1.1.1u). iOS 크래시(`ossl_connect_common`, 다운로드 스레드의 SSL 연결 중 발생, 18에서 빈도 증가)를 줄이기 위한 조치. 테스트 폰에서는 미재현, Xcode를 15.2에서 15.3으로 올리자 패키지 의존성 오류가 해결됨. 같은 시기 DP 엔진 빌드를 `.aar`로 전환하기로 하고 AIR(AOS)와 NSDK(Renewal)에서 문제 없음을 확인(AOS는 4e 사용).
  - AOS v0.0.6.x(4e) 01-24, (4f) 02-13, (4g) 03-05. MapboxType 설정 시 앱 비정상 종료는 이번 버전 이후 발생한 문제는 아니었고, Mapbox 스타일은 야간 지도를 별도 지원하지 않고 주간으로 취급하는 것이 현 코드와 맞음.
  - 02-26: Firebase 모니터링에서 중국산 헤드유닛(Android 10 중심, 루팅 99%)에서 DP가 동작하지 않는 이슈 발견. 원인은 GLES30 컨텍스트 생성 실패 후 GLES20로 폴백하는 로직의 문제(GLES20만 지원하는 하드웨어에서 발생)로 확인되어 수정(03-05 4g). 고객 문의로도 업데이트 직후 앱 종료가 보고됐고, 사용자 앱 버전 이력(03.05.48에서 49로 변경)으로 영향 범위를 확인.
  - 06-18: MapDisplay_Air v1.0.0(AOS/iOS, 내부 코드 유지보수 버전) 발행. iOS 적용 시 심볼 에러 발생(메인 개발 구성은 Xcode 16.4) -> v1.0.1(iOS)에서 Mapbox 코드가 섞인 소스가 컴파일 대상에 잡혀 jsoncpp 라이브러리를 임시로 추가했고 다음 버전에서 재정비 예정.

## 4. 오르다(Orda) 연동 (4~6월)

- 04-17: 1차 논의 후 항목 정리: 공지/배너(사업 담당), 지도상 주기 표출(지도팀), 아이나비 시나리오 연동(예: 목적지 도착)(에어 기획).
- 05-09: 시나리오 초안 리뷰 허들(오후 3시). 연동 API 규격 초안 공유. 구조는 "에어 앱 <-> 오르다 Agent" 대신 "에어 앱 <-> 에어 Agent <-> 오르다 Agent"로 변경하고, 파라미터는 `radius`를 최대 검색 범위로 재사용. 이후 서비스게이트에 `orda_flag`(활성), `orda_search_radius`가 추가되었다가, 반경 값은 Agent 내부 처리로 바뀌어 서비스게이트에서 제거. 연동 API 응답 코드는 에어와 같은 `result_code`, `result_msg`로 통일.
- 05-13~14: 연동 기획안 공유 및 디자인 요청(A/B안). 목적지 도착 시 20km 반경 안에 스탬프가 없으면 전국 단위 투어 중 참여자가 가장 많은 투어(오르다가 추천하는 유효 스탬프)를 대표로 노출하는 사양을 추가. 사용자가 오르다 앱을 설치했는지에 따라 앱 실행 또는 스토어 이동으로 분기. 시나리오 후보 중 "에어 캐시 적립 시 안내", "내비 지도에 표출"은 기획 측에서 과하다는 의견이 있어 목적지 도착 시나리오만 우선 확정.
- 05-14: 5월 말 서비스 목표(5월 초까지 개발 완료 기준 협의). GA 이벤트: 20km 이내 스탬프가 있는 경우 `ordastamp_20`(다이얼로그 조회)/`ordastamp_20_link`(투어하러가기 클릭), 없는 경우 `ordastamp_none`/`ordastamp_none_link`. OS 구분은 GA 기본 플랫폼 필터로 충분.
- 05-27~30: 리소스(`airre_popup_orda_default_img` 등 3종) 전달, 이미지에 round 처리가 들어가 배경이 비쳐 radius 값을 제거해 재전달. 팝업 문구가 "오르다 스탬프 투어 출시"에서 "아이나비스탬프 오르다 출시"로 변경(공식 명칭), 앱스토어 검증 중이라 이미지 교체 없이 진행. 스토어 문구와 5월 공지 시안(공지는 오르다 측 요청).
- 딥링크: 앱 미설치 시 오르다 스탬프 페이지(브라우저)로 이동 후 몇 초 뒤 스토어로 자동 연결(오르다 쪽 구현). 에어 측 요구로 스탬프가 있으면 투어 상세 대신 지도 스탬프 위치 딥링크로 변경(Agent 오르다 반영 6/2, 에어 Agent 상용 6/4).
- 06-04: Orda 연동 패치 서버 반영 완료. AOS/iOS 상용 테스트 특이사항 없음.

## 5. 6월 패치: SOS 대신 수해지역(홍수/침수) VMS

- 06-09: 킬로포스트(SOS 연동) 계약이 지연되어 6월 패치에서 SOS를 빼고 홍수/침수 안내로 변경(회의로 내용 공유). 기존 SOS는 준용(도로명+기점표지판 표출, 등록 번호가 없으면 대표 번호로 연결).
- 06-24~25: 수해지역 고도화 기획 공유. 서버는 경로 탐색 응답에 `type`(2,3)과 `d_level`을 추가하고 `/roadEventDetail`을 `eventType=2`로 호출하면 문구를 생성해 제공. 기존 사용자는 id가 flood로 시작하면 eventType을 2로 자동 변환하는 로직을 유지. 서버 규격: `msfrtType`(호우/산사태/홍수), `contentLevel`(01 경보 발령, 02 심각단계 발령, A1 경보 해제, A2 심각단계 해제). 효과음은 "경로 이탈 효과음"으로 결정하고 타입과 무관하게 1회 호출(재난 위험지점 반경 1.5km 이상 접근 또는 침수 위험 구간 전방 진입 시). VMS 문구는 3줄 사양, 아이콘 6종 추가. AOS는 일반 VMS에 산사태/호우 표출(홍수만 별도 처리), iOS는 수해지역 VMS에 표출하는 방식이라 GUI가 다르게 보일 수 있음. 목적지 10km 이내 VMS만 검색하는 로직이 있어 테스트 시 목적지를 근처로 옮겨야 함. 개발서버가 한 차례 내려가 재기동.
