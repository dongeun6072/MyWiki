# Slack #10_prj-orbis-navisdk 대화 (2026-01~04)

TomTom Orbis Map NaviSDK POC 공개 채널 `#10_prj-orbis-navisdk`의 2026-01-01~04-30 구간 기록이다. 프로젝트 허브는 [[orbis-sdk]], 개발 이력은 [[orbis-navisdk-development-2025]], 상용화 스크럼은 [[navisdk-commercialization-scrums-2025-2026]], 대만 사업/개발은 [[orbis-taiwan-business-2025]]와 [[orbis-taiwan-development-2026]]를 본다. 앞뒤 기간은 [[navisdk-prj-slack-2025-q4]], [[navisdk-prj-slack-2026-h1b]]를 본다.

구간 내 채널 메시지 21건(입장 알림 3건 포함)과 스레드 답글 83건을 모두 읽었고 답글이 달린 스레드 12개를 전부 열었다. 미열람은 0개다. 4월 8일 스레드(style.json 관리)의 답글 일부는 구간 이후(5~6월) 날짜인데, 같은 스레드라 함께 정리하고 날짜를 명시했다. 첨부는 파일명·종류만 기록했다(내용 미열람). 사람은 역할로 적었고 서버 주소·업로드 경로·링크·키는 옮기지 않았다. 채널 개설자는 개발 PM 수석(이하 "PM 수석")으로 적는다.

## 1. 준상용서버 구축 (1월)

- **2026-01-06 일정 공지**: PM 수석이 지난해부터 논의된 Orbis NaviSDK 준상용서버 구축을 **1월 16일 완료** 목표로 진행하겠다고 공지(품의는 금주까지, 차주부터 서버 구축). 서버 구성 화면 캡처 첨부.
- **클라우드 정합성 논의(01-06)**: 사업(전략)팀 팀장이 Orbis Maps 상용을 AWS 클라우드로 셋팅하는데 Routing Server가 NHN 준상용에 있는 것 같다며, 같은 클라우드 안에서 서버 간 연동이 필요하지 않은지 확인 요청. PM 수석은 이번 셋팅은 상용이 아닌 **준상용 단계**라며 같은 클라우드를 써야 하는 이유를 되물음. 사업 팀장은 "상용과 같은 환경 구성 1set 취지"라면 같은 인프라에 전용 구성이 되어야 하고, 고객이 없고 비용 문제라면 실제 고객 유입 시점에 같은 클라우드 내 엔진 연동이 되면 좋겠다고 답.
- **AWS 견적 확인(01-07~08)**: PM 수석이 AWS 대행 업체 견적 확인 중 나온 질문을 전달 — 서버 전부 리눅스 기반인지, DB 서버는 RDS인지/어떤 엔진인지. 사업 팀장이 서버는 모두 리눅스, DB는 RDS 사용, 현재 AWS 인프라 사양은 Amazon Linux와 Amazon Aurora(MySQL)라고 회신. PM 수석이 견적서 캡처를 올려 추가 확인을 요청했고, 클라우드 담당(01-08)이 견적상 RDS for MySQL인데 PostgreSQL도 가능한지 문의.
- **DB 결정(01-08)**: PM 수석이 DB는 원래 MapsAPI·Web·Agent용인데 교통정보도 같이 쓸 수 있는지, PostgreSQL로 바꿔도 되는지 확인 요청 후, 확인 결과 신규 DB는 MapsAPI·Web·Agent만 쓰므로 **견적 그대로 MySQL 사용**으로 정리. 준상용 구축 시 교통정보는 별도 DB를 써야 하며 필요하면 상용에서 신규 구축이 필요할 것이라고 정리.
- **일정 변경(01-09)**: 품의 절차상 **약 20일 계약 개시**로 정리되어 개발 시작을 20일, **23일 완료**로 변경.
- **결과(3월 스레드)**: 03-26 사업 담당 과장이 대만 상용 오픈이 2026년 3월쯤으로 들었는데 업데이트가 있는지 문의하자 PM 수석이 3월부터 대만 고객사에 SDK가 배포된 상태라고 답. 사업 과장이 "정식 서비스(SDK)가 오픈된 것으로 인지해도 되는지, 서버 전환 필요 시 요청하면 진행토록 하겠다"고 하자, PM 수석은 구두로 말씀드렸지만 **현재 준상용서버로 정식 서비스를 진행 중**이며 서버 확장이 필요한 시점에 상용서버 인프라를 구축할 예정이라고 정리.

## 2. 사내 방화벽·개발자 사이트 (1월)

- **2026-01-08**: PM 수석이 Orbis 개발자 사이트 상품 페이지가 본사에서는 열리는데 패스트파이브(외부 오피스)에서는 로딩되지 않는다며 외부 접근 불가 여부 확인 요청. 사업 팀장이 9층 전산실 장비라 사내 방화벽에 막힌 것 같다며, 우선 방화벽 신청으로 열고 차주 서버가 나오면 바로 옮겨야겠다고 하면서 인프라 담당에게 해당 장비 포트 3개월간 Any 개방 신청을 요청. 인프라 담당이 방화벽 오픈 요청을 올렸다.
- **01-08~09 확인**: PM 수석이 방화벽 오픈 후 패스트파이브에서 접근 가능한지 확인 요청 -> 01-09 SDK 담당 책임이 현재 접속된다고 확인.

## 3. 빌드/라이브러리 요청과 탐색엔진 연동

- **2026-01-07 경로 탐색 실패 개선 확인**: PM 수석이 탐색엔진 담당 수석에게, 지난 10월에 "출발지/목적지 근처에 도로가 없어 경로 탐색이 실패하는 결과"를 개선한 것으로 아는데 관련 사양 확인이 가능한지 문의. 사유는 CES 단말에서 오류가 났고 원인을 보니 출발지 근처에 링크가 없었기 때문. 탐색엔진 담당 수석이 **내부 사양은 약 15km로 설정**되어 있고 그렇다면 출발지 위치정보 확인이 우선일 것이라고 답.
- **디버그 로그 API 요청(01-07~08)**: 릴리즈 테스트 중 Debug 로그가 지속 출력되는 것으로 보여, PM 수석이 MMC lib와 탐색 RouteData Lib에 디버그 로그 출력 여부를 정하는 API 추가를 AOS·iOS 모두 요청. 탐색엔진 수석이 Route Data Library는 현재 Debug 로그를 출력하지 않는다고 확인, PM 수석은 추후 디버그 로그를 넣을 때 On/Off API도 함께 만들어 달라고 요청. 01-08 MMC 담당(팀장급)이 **디버그 로그 출력 및 저장 여부를 결정하는 API를 추가해 배포**하겠다고 답.
- **01-22 신규 Lib·지도 호환(스레드)**: 탐색엔진 담당이 신규 Lib와 신규 지도를 발행하자, PM 수석이 신규 지도가 기존 Lib와 호환되는지 문의(비호환이면 앱 발행과 지도 동기화 주기를 맞춰야 함). 탐색엔진 수석은 상세 속성정보가 변경되어 정확한 속성을 가져오려면 **최신 지도에 최신 라이브러리**를 써야 한다고 답. PM 수석은 전체 기능을 못 쓸 것은 예상했고, 앱 발행 전 지도만 먼저 서비스하면 문제가 생기는지 확인차 문의한 것이라 부연하고, 에이전트 담당에게 "일단 지도 업데이트는 하지 말아 달라"고 요청.
- **02-09 트럭향 지도·Lib 전달**: PM 수석이 에이전트 담당에게, 이날 탐색엔진 수석으로부터 **트럭향이 적용된 지도 데이터와 Lib**가 전달되었다고 알림. 3월부터 탐색엔진 지도버전 분기를 위한 **port 이원화 계획도** 포함되어 있으니 에이전트에서도 참고해 달라고 요청.
- **03-03 국내향 중단·포트 분기**: PM 수석이 3월부터 대만향 탐색엔진 지도분기를 위해 **국내향 서비스를 중단할 예정**이니 문제 여부 공유를 요청(스레드). 서비스 담당이 테스트를 완료했고 국내향 서비스를 중단해도 된다고 답. PM 수석이 탐색엔진 신규 포트 작업 일정을 요청하자 탐색엔진 수석이 **금주 중 INAVI Route Server for Taiwan 신규 버전 업데이트 및 포트 분기 작업 완료 후 Release**하겠다고 답.
- **03-19 차량 제원 옵션 응답 이슈(해결)**: 에이전트 담당이 탐색엔진 2.0 규격서의 신규 차량 제원 옵션(weight, height, length)을 준상용에서 세팅해 테스트했는데 응답 DTO `user_info`에 옵션 값이 돌아오지 않는다고 문의했다가, 원인이 파악되어 질문 본문을 취소선 처리(구체 원인은 미기재). 탐색엔진 수석이 수고하라고 답. 요청 JSON에 대만 좌표, traffic=1, routecount=3, 제원 각 10.0이 쓰인 것이 확인된다(경로·좌표는 대만 시험용).

- **01-15 가이드 갱신 스레드(01-16)**: PM 수석이 웹 문서 담당에게 이번 주 내 완료를 요청하며 일정 공유 부탁. 웹 담당이 전달 문서가 **기존 파일 구조와 다르다**며 같은 구조로 재전달을 요청 -> SDK 개발 담당이 directory url을 제외하고 이전 구조로 재전달. 웹 담당이 GitHub 브라우저 보안 정책으로 Demo Project·Changelog(Android, iOS) 페이지가 내부 노출이 제한되어 **새 창 연결 방식**으로 처리해도 되는지 문의, PM 수석은 내부 노출이 불가하면 새 창 연결로 하라고 답. 같은 날 15시 45분 상용 서버 반영 완료. PM 수석이 SDK 좌측 메뉴에서 이전 버전이 먼저 나오고 페이지를 전환하면 신규 버전이 노출되는 현상을 발견해 확인 요청 -> 웹 담당이 어떤 동작에서 발생하는지, 시크릿 모드에서 재확인을 요청 -> PM 수석이 시크릿 모드에서는 정상이라 **캐시 때문에 발생한 문제**로 정리.
- **03-11 Map SDK·Navigation SDK 가이드 HTML(스레드, 03-12~16)**: PM 수석이 Orbis NaviSDK 및 Map SDK 가이드 완료를 알리며 HTML 파일(Map SDK 최초 작성, Navigation SDK 이미지 개선 및 일부 수정, 공유 링크 있음(미수록))을 Orbis 개발자 사이트에 올려 달라고 요청.
  - 03-12 PM 수석이 적용 목표 일정 공유 요청 -> 웹 담당이 금일 작업 후 명일 상용 반영 예정이라고 답.
  - 03-13 웹 담당이 Navigation SDK 파일이 맞는지 확인 -> 맞다고 회신. 13시 54분 "Map SDK 가이드 문서 상용 반영, 캐시가 남을 수 있으니 시크릿 모드에서 확인"을 요청. PM 수석이 확인해보니 **Map SDK 버튼이 활성화되지 않는다**고 지적 -> 웹 담당이 Map SDK 신규 메뉴 노출 건으로 인지하지 못해 Navigation SDK 변경사항만 작업된 것이었다며 재작업 후 17시 44분 **신규 메뉴 노출 및 가이드 문서 상용 반영 완료**.
  - 03-16 PM 수석이 시크릿 창으로 MapSDK 가이드를 확인한 결과 **이미지가 전부 표출되지 않는다**며, 표출되지 않는 2곳(InfoWindow, Marker)의 캡처를 첨부. 웹 담당이 **적용 이미지 경로 오류**였다며 수정해 상용 반영을 완료했다고 답(03-16 10시 17분).
- **03-11 호주향 검토 M/M 산정 요청**: PM 수석이 탐색엔진·지도 담당 등에게, 현재 개발된 Orbis NaviSDK 기준으로 **호주향을 검토**하고자 M/M 산정을 위한 문서 작성을 요청. 호주향 항목은 위험물 회피 추가(호주), style.json 글로벌 관리(대만·호주·한국, 언어·테마 모두 1벌로 관리). 초안 문서(엑셀, 파트별 상세 개발항목 및 M/M 산정 요청) 첨부. 추가 질문은 문의하라고 안내.

## 5. 대만 Map SDK 지도 영역·빈 타일·메타데이터 (4월)

2026-04-09 맵플랫폼개발셀 담당이 대만향 Map SDK 관련 문의를 올렸다(이미지 4건 첨부). 문의 3건은 (1) TileJSON 기준으로 지도 영역을 설정하면 일부 **빈 타일 영역**이 존재, SDK는 지도 영역 설정 시 어떤 좌표 범위를 기준으로 지정했는지, (2) 국내향 Web JS 엔진은 좌측 하단에 **지도 타일 출처**를 표시하는데 SDK에서 표시하는지/값은 무엇인지, (3) **다국어 지원 여부**(법적 고지 페이지와 개발 중 에러 메시지가 중국어·영어로도 표시되는지)다.

- **빈 타일 검토(04-09~15)**: 지도 데이터 담당(D&D팀)이 대만 SDK 지도의 출처는 TomTom 데이터이고 빈 타일은 실제 데이터가 없는 곳이라고 설명, 바다 영역을 지우고 **최상위 레벨에서 6개 타일만 표출**하는 방안을 제안. 맵플랫폼개발셀 담당은 이 방식과, 기존 방식을 유지하며 6개 타일로 지도 영역을 제한하는 방식 모두 기술적으로 가능하다고 판단하나, 바다 영역에도 일부 섬 데이터가 있어 제외해도 되는지 확인을 요청. D&D팀이 해당 지점은 **프라타스 섬**으로 현재 대만이 실효 지배 중이라(중국·대만 영토 분쟁 지역) 표출이 필요하다고 판단하고, 파란 영역을 줄이기보다 빨간색 빈 타일 지점을 **중국 데이터를 받아 채울 수 있는지** 검토하겠다고 정정. 지도데이터 담당(선임)이 04-10 중국 데이터로 캡처를 추가해 **빈 타일 영역 없이 표출 가능**하다고 확인. D&D팀이 타일 영역 포함 지도 데이터 발행 여부·일정 검토를 요청했고, PM 수석은 현재 모바일에서는 고려하지 않고 있어 **Web 측만 확인**을 요청. 사업 팀장이 빈 지역에 대해 지도 타일 추가 작업을 요청하고 가능한 일정으로 검토해 공유해 달라고 하자 D&D팀이 **차 주 화요일 오후까지 업로드 완료** 예정이라고 답.
- **04-15 완료**: 지도데이터 담당이 대만향 지도 중국 영역 추가 타일 컨버전·업로드 완료를 알리며 검수 페이지 연결을 요청. 변경 사항은 **좌상단 타일 추가로 빈 영역 보완(전체 영역 [115, 20, 122.5, 27.5])**과 **텍스트 필드 명칭 규칙 통일(중국어 NAME_ZH, 영어 NAME_EN)**. light/dark 스타일 CSV 첨부(INAVI_TIWAN_SDK_LIF_light/dark_260415). 웹서비스개발팀 담당이 요청 경로로 **검수용 페이지** 연결을 완료하고, Web(JS) Loader의 style.json 경로 연결(Light/Dark)을 웹 JS Loader 담당에게 요청. 텍스트 필드 매핑 표준화: 중국어 `{name}/{NAME}` -> `{NAME_ZH}`, 영어 `{name_en}/{NAME_EN}` -> `{NAME_EN}`.
- **스프라이트(SSID) 정리(04-15)**: 웹서비스개발팀 담당이 대만향 벡터 심볼 스프라이트에 국내 전용 심볼(예: 수인분당선 등)이 포함되어 SSID·Sprites 정리가 필요하다고 지적, POI Plus팀 담당에게 현재 대만향 서비스에서 쓰는 정확한 SSID 리스트(또는 관련 문서) 공유를 요청하고 지도 담당에게는 해당 리스트로 Sprites 재추출을 요청. POI Plus팀이 금주 중 전달하겠다고 한 뒤 14시 32분 "현재 사용 중 및 사용 예정 심볼이 포함된 SS_ID 리스트, 실제 존재하지 않는 '0' 제외 **총 92건**"(ss_id_list.csv)을 전달. 17시 29분 웹서비스개발팀 담당이 **대만향 벡터 심볼 최신화 완료**(새 sprites 경로, 링크는 미수록)하고 동일한 light/dark style.json의 sprites 주소를 최신으로 업데이트했다고 보고.
- **미해결·후속**: PM 수석이 말한 "모바일은 고려하지 않음"(04-10)에 따라 Web 위주로 반영되었고, Map SDK(모바일) 반영은 이 구간 내 언급 없음 ^[inferred]. 법적 고지·에러 메시지의 중국어/영어 표시(문의 3번)와 지도 타일 출처 표시(문의 2번)에 대한 직접 답변은 이 구간 기록에서 확인되지 않는다 ^[ambiguous].

## 6. style.json 관리·인증 API (4월 문의, 5~6월 후속)

2026-04-08 웹서비스개발팀 담당이 대만향 SDK style.json 관리와 사용 방식을 문의했다. 질문: (1) 현재 전달받은 대만 스타일은 Light/Dark 두 가지인데 실제 서비스에서 Light만 쓰는지, (2) 지난 논의의 영어·중국어 스타일을 별도 관리한다는 구체 운영 방식 및 SDK가 **인증 절차(글로벌 Maps API의 navisdk 인증)**를 통해 스타일을 적용하는지. 국내(아이나비 맵스) 사례로는 지도 담당 수석에게 '일반/일반 지형' style.json을 받아 직접 서버에 업로드하는 방식이라고 설명. 이전 스레드(2025-10) 인용: "앱 패치는 필요 없으나 style 변경 필요(Agent), 캐시 데이터가 남을 수 있어 기존 설치 앱도 초기화 필요", 영어/중국어 스타일은 자동 반영되지 않고 별도 반영 후 알려주면 적용·테스트 진행.

- **04-08 SDK 담당 책임 답변**: (1) Light, Dark 둘 다 사용 중. (2) 별도 구성된 **Agent 내부에서 동일한 인증 절차**를 진행 중이며 인증으로 받은 스타일은 SDK에서 미사용. 언어별 style.json을 Agent에서 별도 내려받고, SDK는 시스템 환경 구성에 맞게 적용. 추가 확인은 에이전트 담당에게 문의 요청.
- **04-09 사업 팀장 의견**: 내비 SDK와 다른 style 파일을 쓰는 것으로 보이며, style 파일은 Maps API에서 인증 후 내려주는 프로세스이므로 글로벌 Maps API의 **map sdk 인증 API**에서 인증 시 map sdk style 파일을 내려주도록 하고 싶다고 제안. 우선 어떤 style 파일을 쓰는지 확인이 필요하고, style 파일은 웹 측에서 생성·관리하므로 언어별 구성(하나로 관리/언어별 분리)도 논의가 필요. 당일 16시 PF2 회의실 담당자 논의 제안.
- **04-09 에이전트 담당 정리**: SDK가 인증 API를 요청하면 에이전트가 글로벌 Maps API를 통해 SDK에 style json URL을 반환. CDN에 별도 업로드한 style.json(cn light/dark, en light/dark, tomtom light)은 사용 중이 아닌지 SDK 책임에게 확인 요청(주소 미수록).
- **05-21 Map SDK 동일 style.json 사용 검토(구간 이후)**: PM 수석이 Web 지도 스타일에 맞춰 Map SDK도 동일 style.json을 쓰려고 보니 인증서버가 내려주는 style.json이 **Light 테마 하나**뿐이라며, SDK는 Light/Dark를 한 번에 받아야 하므로 두 테마 json을 한 번에 내려줄 수 있는지 확인 요청, 인증 API 응답 필드 변경 시 에이전트 영향도도 문의 -> 에이전트 담당이 **영향 없음**이라고 답. 웹서비스개발팀 담당이 Response를 AS-IS(`result`, 단일 URL) -> TO-BE(`result_light`, `result_dark`)로 바꿀 수 있는지 문의하고, 현재 dark 주소는 다크 심볼이 적용된 스타일이라고 설명. 지도 스타일 담당 책임^[ambiguous]이 검토 후 문제없다고 확인.
- **05-22 확정**: 웹 담당이 Web JS Loader의 Dark styleJSON 주소 변경(다크 심볼 반영)을 요청. SDK 책임은 TO-BE에서 `result_light -> result`로 하여 국내 기준 기본 스타일 외 테마도 동일 형태(`result`, `result_dark`)로 가져가자고 요청, 에이전트 담당도 문제없다고 확인. 인증 API 담당 연구원(웹서비스개발팀)이 11시 배포 작업에 반영하겠다고 한 뒤 응답 구조·값 변경 반영 완료, 에이전트 담당이 정상 응답 확인(12시 56분). 에이전트 측 반환 예정 구조는 `authDto.imaps.result`/`resultDark`, accessToken, result.code(SUCCESS) 형태로 공유(값 미수록). 13시 42분 인증 API Response에 Dark styleJSON 추가 반영 완료.
- **05-26 인증 API 분리**: 사업 팀장이 Navi SDK 인증 API로 Map SDK 인증을 같이 쓰고 있는데 인증 API별 호출 통계가 따로 집계되므로 **Map SDK 인증 API로 호출하도록** 해달라고 요청하고 일정 확인 및 기존 Navi 인증 API 규격 변경 시 영향도 검토를 요청. 웹서비스개발팀 연구원이 Map SDK 인증 API 규격서를 전달(응답 본문 구조 변경 없음, **API Key 인증이 URL 경로 변수에서 Header 기반으로 변경**, 헤더 키 `X-INAVI-API-KEY`). PM 수석이 Navi와 Map 인증을 구분해 진행하겠다며 하나의 API Key로 둘 다 쓰는 현재 상태가 구분 후에도 유지되는지 확인 요청 -> 사업 팀장이 API Key는 **업체 기준 구분**이라 모든 API에 동일 사용 가능하다고 답.
- **06-15~16 개발서버 반영(구간 이후)**: 에이전트 담당이 Navi/Map SDK 인증이 구분되어 통계가 쌓이도록 **개발서버에 반영**했고 통계가 정상 집계되는 것으로 보인다고 보고(경로는 `/v1/sdk/mobile/navi`, `/v1/sdk/mobile/maps`), 준상용서버 적용 일정을 문의. PM 수석이 금주 중 진행을 요청했고 에이전트 담당이 **명일(06-16) 오후 1시 진행** 예정이라고 답.
