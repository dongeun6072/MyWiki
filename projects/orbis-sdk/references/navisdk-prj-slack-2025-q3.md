# Slack #10_prj-orbis-navisdk 대화 (2025 Q3)

TomTom Orbis Map NaviSDK POC 공개 채널 `#10_prj-orbis-navisdk`의 2025-07-01~09-30 구간 기록이다. 프로젝트 허브는 [[orbis-sdk]], 개발 정리는 [[orbis-navisdk-development-2025]], 스크럼 기록은 [[navisdk-commercialization-scrums-2025-2026]], 대만 사업 배경은 [[orbis-taiwan-business-2025]], 실차 평가는 [[taiwan-field-evaluation-2025]]를 본다. 다른 기간은 [[navisdk-prj-slack-2025-h1]], [[navisdk-prj-slack-2025-q4]], [[navisdk-prj-slack-2026-h1a]], [[navisdk-prj-slack-2026-h1b]]에 있다.

구간 내 채널 메시지 32건(입장 알림 10건 포함)과 스레드 답글 84건을 모두 읽었다. 답글이 달린 스레드 19개를 전부 열었고 미열람은 0개다. 일부 스레드 답글은 구간 이후(2025-10)까지 이어지며, 해당 답글도 읽어 날짜를 붙여 적었다. 첨부는 파일명·종류만 기록했다(내용 미열람). 사람은 역할로 적었고, 서버 주소·접속 경로·앱키·링크·스택 트레이스는 옮기지 않았다.

## 1. 일정·전시회 목표

- **2025-09-29~30**: 개발 PM 수석이 "지금 중요 마일스톤은 10월 22일 전시회 준비"라고 밝혔다. 이에 10월 초까지는 현행화(06월 기준) 데이터로 진행하길 희망했고, 10/20에는 대만 출장자 전원이 비행기나 현지에 있을 예정이라 문제가 없도록 챙겨 달라고 요청했다(4절).
- **2025-09-15**: 전시회 목표로 수정 중인 TBT 개선 이후에 경유지 경로 옵션을 처리하기로 협의됐다(3.3절).
- **2025-09-03**: 대만향 데모 앱 발행을 준비 중이라는 언급이 반복된다(멀티경로 영향 문의, 대만 지도 style 일정 문의).
- **2025-08-05**: 개발 PM 수석이 해당 주 주간회의를 별도 회의실(Path-2)에서 같은 시간에 진행한다고 공지. 스레드에서 MMC 엔진 팀장이 2025-08-14 "맵매칭 WBS 업데이트" 요청, 08-21 잔여 항목 진행률을 공유했다(2.1절).
- **2025-07-24**: 휴가자가 있어 해당 주 주간회의를 열지 않고 MMC 엔진 진척률을 대신 받기로 했다. 주요 이슈는 슬랙에 남겨 달라고 요청.

## 2. MMC(맵매칭) 엔진

### 2.1 진척률 (7~8월)

| 날짜 | AOS 단말 GPS 수신부 | 가상 맵매칭 로직 | 터널/지하차도 가상주행 | 히스토리 맵매칭 | 모의주행 |
|---|---|---|---|---|---|
| 2025-07-24 | 80% | 100% | 10% | - | - |
| 2025-07-31 | 90% | - | 20% | - | - |
| 2025-08-21 | - | - | - | 60% | 10% |

- 2025-07-24: MMC 엔진 팀장이 개발 PM 수석의 요청에 위 수치로 갱신하라고 답했다. 개발 PM 수석은 첨부 화면 1건(PNG)을 올렸다.
- 2025-07-31: MMC 엔진 팀장이 진척률 2항목 공유.
- 2025-08-21: 08-14 WBS 업데이트 요청(첨부 PNG 1건)에 이어 잔여 항목 진행률을 공유했다.

### 2.2 모의주행(SEEK) API (2025-08-28)

- MMC 엔진 팀장이 모의주행 기능 중 SEEK 관련(프로그레스바, 교차로 이동 등)에서 쓰는 맵매칭 API는 `setSimulateIndex(index)` 하나뿐이라며, 메인 쪽에서 공통으로 쓰는 것이 맞는지 확인을 요청했다.
- 개발 PM 수석 답변: 기존에 `SetSimulatePercentage`, `SetSimulatePos` 등도 있으나 프로그레스바 등이 없으므로 `setSimulateIndex`만 있으면 되고, 당장 percentage 등은 필요 없다.

### 2.3 실차 이슈 수정 계획 (9월)

- **2025-09-04**: 개발 PM 수석이 구두 논의를 정리해 MMC 엔진 팀장·MMC 책임에게 전달. 대만 실차 인원이 교체됐다(MMC 담당자 대신 개발 PM이 진행, 대만 실차 인원은 대만 담당 책임과 개발 PM 수석). MMC 관점의 실차 필요 코스(지점)를 선정해 공유하면 실차 코스를 수립할 예정이고, 이슈 수정과 한국 실차도 필요하다. 이슈 시트(링크 있음, 미수록)에는 터널 멈춤, 정차 중 속도 오류 등이 있다.
- **2025-09-08**: 개발 PM 수석이 MMC 이슈 수정 계획과 목표 일정 공유를 요청, 이어 이슈 발생 지역을 전달했다.
  - 터널 멈춤: 내곡터널, 하산운터널, 매봉터널.
  - 정차 중 속도 이상: 매봉역 부근, 강남세브란스병원 부근.
- **2025-09-24 (스레드)**: MMC 실차 담당 팀장이 전날 전달받은 최신 샘플앱(첨부 `대만향 내비이슈_25.09.23.zip`, zip 2.8MB)을 설치해 퇴근길에 테스트한 결과를 보고했다.
  - 판교역에서 역삼동(분당내곡방향)으로 주행 시 시작 후 5분 이상 지나도 GPS가 제대로 잡히지 않고 다른 위치에서 경로주행선이 잡힘.
  - 매봉터널, 내곡터널, 지하차도에서 모두 맵매칭이 되지 않음. 터널 진출 후에도 바로 GPS가 잡히지 않고 약 20초 후 정위치를 찾음.
  - 개발 PM 수석이 같은 날 "전일 한국향 빌드 버전이며 신규 MMC 엔진이 적용돼 있는지 확인"을 요청. 다른 SDK 개발 담당이 신규 엔진 버전을 0.5.5라고 답변.
  - 개발 PM 수석이 팀장급 실차 담당의 개발폰을 대여해 실차 가능 여부 확인을 요청했고, MMC 책임이 해당 폰을 전달받으면 실차 테스트로 확인하겠다고 답했다.

### 2.4 멀티탐색 규격 적용 (9월)

- **2025-09-25**: 개발 PM 수석이 현재 MMC 엔진에 "탐색엔진의 멀티탐색 규격" 포맷이 적용되지 않은 것으로 아는데 언제 전달받을 수 있는지 확인을 요청했다.
- MMC 책임이 사용자가 최종 하나의 경로를 선택하므로 선택된 경로를 기존 포맷으로 전달할 수 없는지 문의 -> 개발 PM 수석은 탐색 포맷의 주체가 탐색엔진이라 임의 수정은 좋지 않다고 답변.
- **2025-09-29**: MMC 책임이 일정을 공유: (1) 사용자 선택 경로 index 전달용 인터페이스 추가 및 테스트 메인앱 배포 9/29(월), (2) 멀티탐색 규격 포맷 적용 배포 10/2(목).
- 개발 PM 수석이 다시 확인한 결과 index 인터페이스는 불필요하다고 정정했다: 메인에서 멀티탐색 경로 중 선택된 경로를 0번째 경로에만 저장하면 MMC 엔진은 0번째만 읽으면 된다. MMC 책임도 동의하여 선택 경로를 0번째에 저장하는 테스트 메인앱 배포가 필요하다고 정리했다(멀티탐색용 API를 먼저 주면 테스트 프로젝트를 전달하기로 함).

### 2.5 구형 Android 단말 크래시와 minSDK (9/30~10/1)

- **2025-09-30**: 개발 PM 수석이 LG G7 단말(Android 10)에서 UMap(샘플앱) 실행 시 100% 비정상 종료한다고 보고(재현 단말 보유, 대여 가능). 예외는 `NoClassDefFoundError`로 `android.location.LocationRequest$Builder` 클래스를 찾지 못하며 MMC 엔진의 GPS 모듈(위치 요청 생성부)에서 발생했다. 이후 갤럭시 S9에서도 같은 크래시가 확인됐고, 사업(전략)팀 대리가 쓸 단말이라 수정 시점을 문의했다.
- MMC 수석(Android 담당)의 분석: 해당 API는 Android 12부터 추가된 것이라 Android 10 단말에서 지원되지 않아 발생한 문제. 오래된 Android 버전 지원이 필수인지, 앞으로도 오래된 기기를 지원해야 하는지 확인을 요청했다. 당일 내 수정은 가능하나 테스트 시간이 부족해 초기위치 등 기능이 정상 동작하는지 확인하기 어렵다고 덧붙였다.
- 개발 PM 수석은 Android 12 이하 단말 대응이 필요하다고 보고 사업부에 의견을 요청했다. **2025-10-01 08:39** 사업부와 협의 결과, 국내 NaviSDK와 동일한 minSDK를 쓰기로 정리했다(국내 NaviSDK minSDK 21, Android 5.0).
- 2025-10-01 13:38 MMC 엔진 팀장: 10월 실차 버전은 LG G7(Android 10)까지 대응 가능하며 10/15경 대만 실차 버전 발생 시 포함하겠다고 했다. 다만 minSDK는 필요하지만 5.0까지 지원이 필요한지는 재고가 필요하다는 의견(5.0은 2021년경 Google Play 서비스 업데이트도 중단됐고, 신규 앱에 NaviSDK와 같은 기준 적용은 무리로 보임; 대만 현지 Android OS 점유율 등을 근거로 재검토 요청). 같은 날 13:47 개발 PM 수석이 사업(전략)팀에 답변을 요청하며 참고로 AIR는 API 23(Android 6.0), 국내 NaviSDK는 API 21(Android 5.0)이 최소 지원임을 공유했다. 최종 결정은 이 스레드에 없다 ^[ambiguous].

## 3. 탐색·도로 데이터

### 3.1 한국/대만 도로 네트워크 검토 예시 (2025-07-31)

탐색엔진 담당 수석이 TomTom Orbis Maps 대만 및 한국 도로 네트워크 검토 결과의 예시 이미지를 스레드에 올렸다(이미지 5건, 설명은 제목만).
- 페리 항로 데이터 이슈
- 고립 링크 삭제로 인한 탐색 이슈
- 오토바이 전용(차량 진입 불가) 도로 링크 검토(이미지 2건)
- 한국 대용량 연결링크 중복 이슈

### 3.2 멀티(다중) 경로 탐색 (8/28~9/3)

- **2025-08-28**: 탐색엔진 담당 수석이 "다중 경로 탐색 기능 개발 결과(참고)"로 PDF 1건(`250828_해외다중경로출력.pdf`, 633KB)을 공유.
- **2025-09-03**: 개발 PM 수석이 개발 목표 일정을 문의 -> 탐색엔진 수석이 금주 중 API 명세서를 포함해 서버를 Release한다고 답변. 개발 PM 수석이 적용 엔진이 대만향 port뿐인지 한국향에도 적용되는지 문의(대만 데모 앱 영향 확인용) -> 멀티경로가 추가돼도 현재 쓰는 단일 탐색 API는 그대로 유지되므로 기존 앱에는 영향이 없다고 답변.

### 3.3 경유지에서 같은 링크로 되돌아오는 경로 (2025-09-08~15)

- **2025-09-08**: 개발 PM 수석이 구두로 문의했던 경유지 거리 관련 결과 파일(`route_sample.txt`, 4.2KB)을 공유. 탐색엔진 수석 분석: 결과 파일에서 4번 링크가 경유지 도착 링크(vertex 19~20)이고 5번 링크부터 경유지에서 목적지로 진행하는 링크(vertex 21~)다. 경유지 위치를 이용한 링크 위치가 링크 시작점에서 너무 가까워 4~5번 링크의 distance가 짧게 나온다.
- **2025-09-15**: 개발 PM 수석이 구두 논의를 공유. 논의 내용은 "경유지에서 동일 링크로 되돌아오는 경로가 생성됨". 결론은 탐색엔진에서 옵션을 제공해 경유지에서 방향성 기준으로 진행할지, 현재 링크로 되돌아오는 경로를 허용할지 선택하게 하는 것. 전시회 목표로 수정 중인 TBT 개선 이후에 진행하기로 협의했다.

### 3.3.1 교통정보·터널 속성

- **2025-09-11 교통정보**: 개발 PM 수석이 한국 탐색 시 교통정보가 반영되는지 확인을 요청(실차에서 에어와 ETA 차이가 심했음). 탐색엔진 수석(2025-09-12): 한국향 경로 탐색 서버는 Release 시 안내한 대로 실시간 교통정보 반영이 없고, 선행기술Lab Dev.2팀에서 한국은 TomTom에서 교통정보가 내려온다고 들었으나 자세한 내용은 해당 팀에 문의하라고 답했다. 개발 PM 수석: 한국 테스트에서 교통정보 반영 여부만 확인한 것이며 대만만 교통정보가 반영되면 문제없다.
- **2025-09-11 터널/지하차도 구분**: 개발 PM 수석이 NaviSDK TBT에 터널/지하차도 안내를 추가하려 검토 중이며, 탐색 규격에 `_is_tunnel`(지하차도/터널 유무, 0 기타 1 yes) 한 필드만 있는 것으로 보여 구분 가능 여부를 문의했다. 탐색엔진 수석 답변: 현재 Orbis Network 속성으로 덮여 씌워진 도로는 터널이든 지하차도든 tunnel 속성으로 존재한다. 초기 데이터 구성 시 도로 높이 값(zorder)으로 구분을 시도했으나 기준값을 찾기 어려워 구분이 어렵다는 결론이었고, 명확히 구분하려면 추가 데이터 확인이 필요하다. 개발 PM 수석이 원도(원도 기반 구분)에서 구분할 방법이 있는지 검토를 요청했다.

### 3.4 차로 정보 문의 (2025-09-10~15)

- **2025-09-12**: 사업(전략)팀 대리가 9/10(수) 메인팀+사업PM 실차 점검 결과 "차로 정보 부재가 가장 큰 아쉬운 점"으로 도출됐고, TomTom 담당자에게 문의했다고 공유. 답변 요약: lane 정보는 Routing API 경로 결과에만 포함(단일 road segment 조회 API는 없음). Orbis Map 데이터 자체에는 lane 속성이 모델링돼 있으나 Public API로 제공되지 않으며, lane 데이터를 쓰려면 Raw Map Data(Orbis) 접근이 필요하다. API로는 Snap-to-Roads, Routing Guidance 등 경로 기반 API만 사용 가능. 아이나비는 자체 탐색엔진을 쓰므로 Routing API의 차선 정보를 직접 활용할 수 없다.

- **2025-09-05**: 개발 PM 수석이 대만향 Demo 앱 발행 준비 중이라 대만 지도 정상 표출 일정을 요청. 주임이 지도 데이터 선임이 업로드 중이라 빠르면 당일, 늦어도 월요일 오전까지 style을 전달하겠다고 했고, 11:21 상용 style.json을 공유(미수록). 개발 PM 수석이 앱 개발 책임·SDK 담당에게 적용 확인을 요청했다. 앱 개발 책임은 공유 style로 지도 로드가 안 된다고 보고(웹 JS 로드 시 발생하는 부분이라는 스크린샷 첨부). 주임은 Map Style Studio와 개발용 웹 뷰어에서는 정상 표출된다고 답하고 재확인했다. 12:25 앱 개발 책임이 구성 재확인 결과 표출되며 glyphs URL이 바뀐 것 같다고 확인 요청, 주임은 glyphs URL만 변경됐다고 확인했다(추후 도메인이 바뀔 수 있음).
