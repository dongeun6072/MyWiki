### 컨소시엄 협업 → [[seoul-donghaengmap-consortium-slack-2026]]

- **버스 하차 알림 정리**: PM이 UX 사양은 하차 예고(하차 정류장 2정거장 전)·하차 임박(1개 전 통과) PUSH인데 LBS테크 안(1개 전 통과, 150m 전)과 다른 이유, SDK가 직접 푸시를 보내려는 이유를 물었다. 앱은 SDK가 예고·임박 이벤트를 콜백으로 주고 메인 앱이 푸시를 보내는 방식을 생각한다. LBS테크 회신: ① 화면기획서에 맞춘다(예고 2정거장 전 PUSH, 임박 1개 전 통과 PUSH) ② 하차 관리는 메인 앱과 SDK가 따로 해야 한다(예약 없이 내비만 쓰는 경우, 승하차 예약만 쓰는 경우) ③ SDK는 메인 앱에 콜백만 주고 알림(배너·알림음)과 문구는 메인 앱이 정한다. 이대로 설계 문서와 SDK 작업을 진행한다.
- **POI 접근성 상세 `GET /pois/inavi/detail`**: 서버 개발이 기획은 접근성 항목마다 있음·없음·미조사가 있는데 `dtl_data`가 true/false뿐이라 구분이 안 된다고 물었다. LBS테크 회신: `dtl_data` 안의 false는 모두 "조사했는데 없음", 조사하지 않은 항목은 null로 고친다. 이어서 정리한 응답 규칙: `data`가 빈 배열인 세 경우는 `message`로 구분한다("POI not matched" 이름·좌표로 매칭되는 POI 없음, "POI detail not found" POI는 매칭됐지만 장소 상세(출입구) 정보 없음, "POI detail not surveyed" 상세는 있으나 조사되지 않음). 값이 있으면 `message`는 "POI Detail fetched successfully"이고 조사된 상세만 내려간다. 출입구가 여러 개인 POI에서 일부 출입구만 조사되지 않았으면 그 출입구의 `dtl_data`만 null이다. `data` 배열의 출입구 순서에는 의미가 없다(대표 출입구가 맨 앞이 아니다). 회신의 "not surveyed" 설명은 "dtl_data 값이 전부 false인 경우"라고 적혀 있어 false=조사했는데 없음 규칙과 겹친다. ^[ambiguous]
- **실외 내비 바텀시트 전체 경로(LBS테크 SDK 담당)**: 바텀시트의 전체 경로가 지하철을 포함한 전체 경로인지 물었다. 실외-버스-실외-지하철-실외-목적지 경로라면 지도 표시를 1차(지하철 입구까지)와 2차(목적지 입구까지)로 나누려 한다. PM은 경로가 실외·실내로 나뉘어 시나리오를 내부 검토 중이라며 개발 검토 후 답하기로 했다(11-05).
- **lane API(LBS테크 API 담당)**: 화면기획서 2-3(상세 경로 지도에 탑승 구간 노선 표시) 때문에 `GET /dongheng/lane`을 만들었지만, ODsay 노선 그래픽 데이터 API 결과를 형식만 바꿔 넘기는 구조라 메인 앱이나 앱 서버가 ODsay를 직접 부르는 편이 낫다고 제안했다(경로 응답의 `routes[].mapObj`를 그대로 넘기면 된다, 주소 미수록). PM은 개발 검토 후 답하기로 했다(11-05).
