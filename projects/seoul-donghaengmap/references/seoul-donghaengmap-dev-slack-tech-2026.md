# 서울동행맵 내부 개발 채널 2026 (2) 앱 스택·서버 API·인증·시연 연동

[[seoul-donghaengmap-dev-slack-process-2026]]의 기술 편이다. 앱은 Compose Multiplatform으로 새로 만들고, 서버는 OpenAPI 규격에서 DTO를 생성해 앱과 맞춘다. 서버 주소, 접속 정보, 키, 토큰 값은 옮기지 않았다.

## 1. 앱 기술 스택 (9-10 협력사 회신 기준)

[[kmp-cmp-adoption]]의 방식을 그대로 쓴다. UI는 CMP 단일 코드베이스, 공통 로직은 KMP `commonMain`이다.

| 영역 | 내용 |
|---|---|
| 언어·빌드 | Kotlin 2.4.10, JDK 21(Zulu, jvmTarget 11), AGP 9.3.2, Gradle 9.6.1, KSP 2.3.11, Compose Multiplatform 1.12.0 |
| Android | minSdk 29, targetSdk 36 (compileSdk는 아래 쟁점) |
| iOS | 최소 배포 16.0, 패키지는 SPM, Xcode 26.x |
| 아키텍처 | MVI(Orbit), DI(Koin), 네트워크 Ktor 3.5.2, 로컬 Room3와 DataStore, 이미지 Coil3 |
| 지도 | 사내 iNavi Maps SDK(Android 0.22.1, Compose 래핑 0.3.0, iOS 0.22.0). 구글 지도는 쓰지 않는다. 벡터 베이스맵과 지하철역 실내지도(도면 타일) 레이어를 표출 |
| 기타 | R8/ProGuard keep 규칙은 직접 작성한 것이 없음 |
| 최소 OS | Android 10, iOS 16 |

- 실외 도보 내비게이션 SDK(LBS테크)도 같은 CMP/KMP 방식으로 받아 `commonMain` 의존성으로 통합한다. → [[seoul-donghaengmap-lbs-collaboration]]
- **Compose 지도 SDK**: 개발 리더가 CMP 지도 SDK를 개발해 9-21에 LBS테크에 배포했다. 앱 개발 책임이 래핑 요청을 정리했고(실내 층 제어 API, POI 픽킹, 커스텀 스타일 노출), 0.4.0에 실내 층 전환, POI 선택, 커스텀 스타일 API를 구현했다. 0.4.0에는 현재 위치 추적 모드가 없어 직접 구현해야 하는지 물었으나 답은 채널에서 확인되지 않는다.
- **compileSdk 쟁점**(10-13): 지도 SDK 0.4.1이 AGP 9.1 이상과 compileSdk 37을 요구해 LBS테크가 SDK를 37로 맞췄다. 9-10 회신에서는 메인앱 기준이 36이었다. 컨소시엄 채널의 회신은 "메인앱 compileSdk 37, targetSdk 36"이었다. 같은 질문이 두 채널에 있어 최종 기준은 후자로 본다. ^[ambiguous]
- **커스텀 지도 스타일**은 접근성 기준(명도 대비 4.5:1, 색 단독 의존 금지)을 맞춰야 한다. 운영 중인 맵 스튜디오가 없어 스타일 JSON을 지도 담당 팀장을 거쳐 서버에 수동 업로드한다.
- **시설물 표출**: 데이터팀 확인 결과 경사로, 장애인 화장실, 점자·유도블록, 휠체어 리프트 4종이 현재 지도에 표출되지 않는다. 경사로와 장애인 화장실은 코드와 데이터는 있으나 심볼 이미지가 없고, 나머지는 코드 정의 자체가 없다. 필수 표출이면 데이터팀에 코드·심볼을 요청해야 한다.
- 지도 앱키 발급(9-17)과 LBS테크용 배포 키는 값을 옮기지 않았다.
- 9-17에 화면 구성을 GeoJSON으로 바꿔 MapLibre 샘플앱으로 실내지도를 그려 보는 시도를 했다. 결과는 채널에서 확인되지 않는다.

## 2. 서버–앱 규격 연동 (OpenAPI)

- 서버는 **외주사 브로디언이 일괄 개발**하는 방향이다. 원래 사내 서버 개발자가 쓰던 서버 클래스 설계는 브로디언 문서로 이관되고 앱 쪽 클래스 설계만 남았다. 협업은 아이나비 기술 문서 기준이다. → [[seoul-donghaengmap-consortium-slack-2026]]
- 8-6~8-10 개발 내부 협의 결과: ① 규격서는 **Swagger로 배포**해 파트 간 공유 ② 앱은 별도 문서 없이 **source를 직접 연결** ③ 위키 게시용으로는 YAML·HTML을 `SvrAPIDoc`에 올리고 규격 변경 때 함께 갱신. 화면별 API 스토리보드 페이지가 규격서 배포 때마다 같이 배포된다(9-8).
- DTO는 OpenAPI Generator로 자동 생성한다. 날짜 타입은 옵션으로 `String`을 만들거나 `kotlin.time.Instant`를 검토했다(`kotlinx.datetime.Instant`는 0.7.0부터 `kotlin.time.Instant`로 옮겨져 deprecated typealias라는 점이 근거). 확정은 아니다.
- 생성 DTO에 `java.util.Objects` 같은 JVM 전용 import가 남으면 KMP에서 컴파일되지 않는다. 어노테이션은 빈 선언을 만들 수 있지만 `java.util.Objects`는 만들 수 없어, **생성 후처리로 제거**하기로 했다(9-3). `@JsonCreator` 등 생성기 옵션으로 끌 수 없는 것도 같은 후처리로 처리했다.
- 응답 공통 규격(8월): `isSuccess` 필드를 없애고 `code`/`message`만 둔다. `code`는 `SUCCESS`, `INVALID_REQUEST`, `UNAUTHORIZED`, `UNDEFINED_ERROR` enum이고 둘 다 required다.

## 3. 인증 구조 개편 (9-3~9-4 합의)

- `init` API는 토큰을 발급하지 않고 헤더 토큰만 보고 NONE/MEMBER/GUEST 상태를 응답한다. 요청 body의 deviceId는 없앤다.
- `login` API가 accessToken을 발급하는 곳이다. provider에 GUEST를 추가하고, SNS 미가입자에게는 signupToken을 반환한 뒤 회원가입 후 accessToken을 준다.
- 공통 헤더의 userId와 logout 응답의 token·userId 필드는 제거한다. 인증 에러는 사유와 관계없이 로그인 화면으로 이동한다.
- 교통약자 유형은 비회원이면 앱 로컬에, 회원이면 서버에 저장한다. 다중 로그인 세션 유지는 요구사항에 없어 기존 동행맵 사양을 따른다(8-20).
- 앱 시작·로그인·회원가입 API는 9-3에 개발 서버에 반영됐고 앱 인증 연동 가이드(v1.0.12)가 공유됐다. 첫 `init`의 authorization 헤더는 임시 값이고 정상 값은 빌드 76부터 들어간다.
- **애플 로그인 revoke**(10-7~8): 로그인 시 앱이 authorization code를 서버에 보내 refresh token을 받아 두고, 탈퇴 요청 때 서버가 애플 revoke까지 처리한다. 서버에 개발용 키가 없어 통신 오류가 났고 키를 받은 뒤 성공했다. 개발과 상용 정보는 분리하고 상용은 추후 생성을 요청한다(값 미수록).

## 4. 통신 암호화

- 요청·응답 DTO의 지정 필드를 **AES로 암·복호화**한다(9-16, 9-28). 서버는 `EncryptedString` 타입(`format: encrypted`)을 도입했고 대상 필드가 19곳에서 29곳으로 늘었다. 앱은 AES 키를 응답으로 받는 필드를 쓴다.
- 장소 상세 주소 호출이 평문으로 내려오는 문제는 서버를 고쳤다(목업 포함). 10-6에는 DB 암·복호화 적용을 위해 기존 회원 데이터를 초기화했다.
- DB 쪽 암호화: 소셜 ID와 SNS 갱신 토큰 컬럼은 평문이 아니라 암호화해 저장하며, 컬럼 길이를 1000자로 늘렸다. → [[seoul-donghaengmap-consortium-slack-2026]]

## 5. 시연 서버 연동 범위 (10-22 회의)

앱이 연결하는 API는 규격서 v1.0.47 기준 **29개**다.

| 구분 | 개수 | 내용 |
|---|---|---|
| 실연동 완료 | 14 | 앱 시작·계정 11, 약관 2, 택시 1 |
| 구현 후 제공 | 7 | 공지 2, 의견 보내기 2(공지·의견은 확인), 통합검색·장소 상세·역지오코딩 3 |
| 목업 제공(브로디언 소관) | 11 | 대중교통 6, 불편신고 4, 마일리지 1 |
| 불가 | - | 저상버스 예약 중계, 대화형 AI(브로디언 소관) |
| 규격 신설 필요 | - | 경로탐색 |

**리스크**
- 상: 경로탐색 API 규격 부재, 검색 제공처 미정(ODsay는 대중교통 POI만 보유), 3사(LBS테크, ODsay, 파파야)의 POI ID 체계 불일치, LBS테크가 대중교통 내비를 담당하는지 미정(10월 말 결정 예정).
- 중: 실내 경로를 통합 탐색에 넣을지, 앱–WAS 엔드포인트 제공 주체(브로디언 대 아이나비), 컨소시엄 산출물 요청 범위.
- 하: 외부망 방화벽·고정 IP 개방 대기(차주 초 예상).

**대응안**: 시연 시나리오를 출발·도착·경유 역으로 일찍 고정하고 그 구간만 목업한다. 통합 시나리오가 안 되면 실내 내비를 별도 데모 메뉴로 단독 시연한다(판교역 샘플). 경로탐색·통합검색 공통 규격 초안은 아이나비가 먼저 만들고 각사 데이터는 백엔드가 그 규격에 맞게 가공한다는 방침을 브로디언에 전달할 예정이다.

**개발 서버 이전**(10-21~23): 임시 개발 서버가 이사하며 DB 연결이 잠시 끊겼다. 방화벽과 포팅이 끝났고 앱 연동 포인트와 규격서 사이트 주소가 바뀌었다(값 미수록). iOS 테스트 앱은 새 주소가 인터넷 IP라 평문 HTTP가 ATS에 막혀 앱을 고쳐 재배포하기로 했다. 시연 환경에서 외부망 접속과 HTTPS 필요 여부는 미해결이다.

**11/13 앱 개발 가능·불가 점검**(10-28 스크럼, 11/16 시연·시연 역사 시청역 기준)

| 구분 | 항목 |
|---|---|
| 실동작 | 로그인·회원가입(SNS 4종), 지도 표출, 택시 호출, 마이페이지 |
| 목업 동작 | 홈, 장소 검색, 경로 검색, 대중교통, 인근 편의시설, 불편 신고, 마일리지 조회. 앱 화면 UI는 전부 완료, 서버 API는 실데이터와 일부 목업 |
| 불가·미완 | 실내 내비(시청역 구축 완료, 데이터 요청 중, 개발자 옵션 목업 화면만 있고 측위 SDK·전환 조건 미연동), 실외 길안내(안내 낭독 미호출, 경로 탐색·내비 서버 계약 없음), 상세경로 도착 카운트다운, 저상버스 예약(1단계 12/18), 마일리지 적립·이어보기(12/18), 음성모드 대화·긴급(대화 상태 8종·TTS 미구현), iOS 실내 실시간 길안내(Apple TN3111 Wi-Fi 스캔 차단으로 구조적 불가) |
| 부분 구현 | 진동 안내(서버에 `hapticEnabled` 없어 기기에만 저장), 팝업 7종 미구현 |

회의 안건은 시청역 데이터 수령일 확정, 데이터 수령 후 실내 내비 실기 테스트, 실외 길안내 목업 기준(경로선 표시, 안내 UI만, 가상 주행까지)이었다. 서버 항목은 컨소시엄 채널 기준이라 제외됐다.

## 6. 실외·실내 내비 연동 요점

- **실내 내비 진입 판단(출구 영역)**: 10-28에 개발자 옵션 "출구 영역 테스트"를 배포했다. 지하철 11개 역(사당, 신도림, 잠실, 고속터미널, 종로3가, 동묘앞, 청량리, 강남, 선릉, 신림, 시청)의 출구 영역을 출구 좌표 기준 약 10m 여유를 둔 사각형으로 잡아 지도에 표시하고, 내 위치가 영역 안인지 보여 준다. 영역 범위·출구 위치에 대한 의견을 채널에서 받는 중이다. 공통 지도의 다각형·선 오버레이는 [[mtech-demo-commit-history-2026]] 쪽 core에 같은 날 추가됐다.
- **측위 흔들림**: 정지 중 GPS 흔들림으로 지도가 계속 다시 그려지는 문제(발열·배터리 소모 Question)에 좌표 절삭·같은 좌표 미방출을 넣었다가, 10초 뒤 추적 해제 부작용 때문에 같은 날 되돌리고 반영 단계의 최소 이동·정지 판별로 대체하기로 했다(10-28).

- **실외 도보 내비(LBS테크 SDK)**: 배포 10월 말 예정. SDK 초기화·종료는 메인앱 Lifecycle에 맞추고 길안내 시작·일시정지·종료를 호출한다. 도보→버스→하차→도보 혼합 경로에서 안내 주체는 앱 개발 책임이 "SDK가 도보 데이터만 넘기고 앱이 안내 UI를 그린다"를 선호하는 쪽이고(UX·UI 통일, 화면 전환 없는 진행, 상태 제어, 다국어 음성), PM은 안내 화면을 SDK에서 처리하자고 제안했다. 컨소시엄 협의에서는 SDK가 구간 번호를 받아 도보 구간만 안내하는 방식으로 기울었다. 최종 결정은 10월 말 재협의 대상이다. ^[ambiguous] 음성은 OS 기본 TTS를 쓸 계획이다. → [[seoul-donghaengmap-consortium-slack-2026]]
- **전맹 모드**: 종료 시 확인 팝업을 동일하게 띄운다. 현재 위치 주소는 가능하나 메인앱이 처리할지 서버가 처리할지는 시나리오별 검토다. 거리 경과 멘트 등 안내 음성 차이는 사양 정리 후 공유한다.
- **실내 내비(파파야)**: 앱은 사용자가 역사 실내에 진입하면 실외 안내를 일시정지하고 실내 내비로 전환했다가 끝나면 실외로 복귀한다. 실내 길찾기 API는 출발지 1개와 목적지 1개만 지원해 경유지가 없다. 카카오맵 SDK는 실내지도 콜백이 오지 않았고 Zone API는 별도 협의가 필요해 실내지도 표출에 부적합했다. 테스트 이슈는 [[seoul-donghaengmap-papaya-slack-2026]]에 모았다.
- **Mapxus**: 실내 지도·내비 홍콩 업체로 9-28에 팅크웨어 주관으로 미팅했다. Core·UI SDK를 검토하려면 API 키와 시크릿이 필요해(값 미수록) 지원팀에 요청했고, NDA를 체결한 뒤 콘콜을 하기로 했다. 진행 결과는 불확실하다.
