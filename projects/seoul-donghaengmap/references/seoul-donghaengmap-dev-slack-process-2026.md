# 서울동행맵 내부 개발 채널 2026 (1) 운영·WBS·감리·스토어

[[seoul-donghaengmap]]의 아이나비시스템즈 내부 개발 채널이다. 2026-07-24에 열렸다. 앱은 [[이동은]]이 앱 개발 책임자와 함께 맡고, 서버·기획·디자인 파트와 총괄 PM이 함께 있다. 앱 스택, 서버 API, 인증은 [[seoul-donghaengmap-dev-slack-tech-2026]]에 따로 적었다. 사람 이름은 역할로 적었고, 서버 주소·계정·키·토큰·공유 링크는 값을 옮기지 않았다.

## 1. 일하는 방식 (AI-flow)

- 사업은 "PRD → 기획(UX) → 디자인 → 코드"로 이어지는 **Claude 기반 AI-flow**로 진행한다. 7-28부터 운영을 시작했고, 구성원이 저장소를 세팅하도록 지원했다.
- **mono repo**로 PRD, 디자인, 기획, 소스, 위키를 한 저장소에 둔다(7-29). 루트의 폴더는 다음과 같다.

| 폴더 | 용도 |
|---|---|
| `Appsource` | 앱 소스(ingest 제외) |
| `Svrsource` | 서버 소스(ingest 제외) |
| `UX` | 기획 산출물 |
| `Design` | 디자인 산출물 |
| `Documents` | 외부에서 받은 문서 보관 |
| `PRD` | 정책 문서(기획자만 수정) |

- 대문자로 시작하는 폴더는 산출물 폴더이고 위키 ingest 대상이다. **소문자 폴더는 LLM Wiki이며 사람이 고치지 않는다.** 루트의 `CLAUDE.md`와 `README.md`를 필수로 읽도록 했다. 연습용 파일은 저장소에 동기화하지 않는다는 원칙도 정했다.
- 8-5에 폴더 정책 2건을 더했다. 서버 담당이 Agent 규격서(YAML·HTML)를 올리는 `SvrAPIDoc/`, 담당자가 PM에게 묻는 질문 큐 `Question/`(처리하면 `Question/Done/`)이다. 질문은 `md 1개 = 질문 1건`이고, 나중에 PM 전용에서 담당자 공용으로 바뀌어 정합성 webhook이 담당자를 멘션한다.
- release 브랜치는 발행 기록용이라 develop에 병합하지 않는 것으로 이해한다. release에만 있는 Question 파일의 관리 방식은 8-19에 물었고 답은 확인되지 않았다.
- 시간 추적은 사내 Jira 클라이언트 앱 **JTT(Jira Time Tracker)**로 한다. 8-4에 소개 세션을 했고 1.0.765 → 1.0.785(진행 중 전환 시 시작일 자동 설정, 잠자기 구간 제외, 티켓 완료 전환) → 1.0.813까지 배포됐다. 앱 개발 책임이 요청한 마감일 정렬 옵션도 들어갔다.
- 스크럼은 7-30부터 매주 수요일 14시다. 휴일이나 감리 대응이 있으면 건너뛴다(9-23, 10-7, 10-14).
- 테스트 앱은 **Firebase App Distribution**으로 배포한다(8-13). 퇴근 전에 목표 명령을 주면 작업 후 자동 빌드·등록까지 하는 흐름이다. 당시 반영 범위는 PRD v0.10 기준 화면 42종과 내비 라우트 41개였고 대부분 골격 수준이었다.
- 8-14에 서버 파트가 "기획서 → API 규격 → 서버 코드(컨트롤러·DTO) → DDL" 자동 생성 사이클을 시험했다. 인증·계정 엔드포인트 5개 범위였고, 사용자 유형 선택은 기획 미확정이라 값이 바뀔 수 있다고 못 박았다. 자동 생성 DDL의 품질 평가는 채널에서 확인되지 않는다. ^[inferred] → 후속 구조는 [[seoul-donghaengmap-dev-slack-tech-2026]]

## 2. WBS와 Jira

- 7-29에 파트별 WBS 입력(상세 항목, 시작일, 종료일, 담당자)을 요청했다. 앱 개발 책임은 PRD 기반 기능일정안으로 앱 WBS 107건을 대조해 **신규 15행과 기존 3건 기간 조정**을 제안했다(지도 표출 신설, SNS 로그인 종료일 연장, 실내 내비 보강 앞당김, 온디바이스 음성모델 추가, 혼잡도 예약·폐쇄망 이관 등을 2027년으로 이동). 신규 15행은 약 14주 공수라 9~10월 배치와 겹쳐 재배치 협의가 필요하다고 했다. rev04에 얼마나 반영됐는지는 확인되지 않는다.
- 8-10에 시범서비스 오픈(2026-12) Epic 아래에 WBS 기준 하위 티켓을 만들었고, 8-11에 **WBS rev04** 기준으로 다시 만들었다. 운영 원칙은 "티켓 날짜를 수동으로 바꾸지 말고 수요일 플래닝에서 WBS부터 맞춘다"이다.
- 초기 프로젝트 구성 기간을 약 1개월로 잡고 한 명에게 몰아 배정해 일정이 어긋난 사례가 있었다. 실제로는 두 명이 동시에 하므로 이슈를 둘로 나눠 담당자를 지정했다.
- 8-31~9-1에 **감리용 WBS 보완**을 지시했다. 기존 WBS에 1 depth를 더해 상세화하고, 내부 Task 단위가 아니라 감리가 이해할 마일스톤 단위(홈 화면, 검색 화면 구현 등)로 나눈다. 협력사 파트도 같은 관점으로 보완을 요청했다. 9월부터는 주간 진행률 갱신과 서울시 월간 보고가 필요하다.
- 9-1 기준 실적: 요구사항·기획·디자인 컨셉 90%, 앱 UI 설계 60%, 교통약자 도보 내비 UI 설계 100%, 대중교통 정보 UI 100% 미만(80%), 지하철 실내 내비 UI 설계 50%(9-9로 변경).
- 8-21에 컨소시엄 통합 WBS(중분류 수준)를 감리 회사와 협의하기 전에 수정했다. **2차 앱스토어 등록 일정을 2027-01-20~22에서 2027-06-14~16으로**, 프로젝트 종료 보고는 6-17로 잡는다. → [[seoul-donghaengmap-wbs]]

## 3. 서울시·교통과 일정 (채널 공지 기준)

- 7-30 교통실장 보고에서 **실내 전파맵 과업 범위**(지하철역 10개+α 대 서울시 전체역)가 쟁점이 됐다.
- 8-6 교통과장 미팅: 지하철 역사 구축 범위가 정리되지 않았다. **1개 역사의 품질 검증을 먼저** 하고, 측위 품질이 2m 이하로 나오면 산출내역서 기준 구축 품셈의 타당성을 검토해 확정한다. 파파야가 단독으로 9-3까지 시연을 준비한다.
- 9-2 서울시 시연에서 위치 오차, 반복 재탐색, 이동 방향성 오류가 나와 파파야가 보완해 1~2주 안에 추가 시연하기로 했다. 판교역 일부 구간을 테스트베드로 구축해 제공하기로 협의했다.
- 서울시는 IRM(통합 위험 관리 및 정보자원관리) 평가 대상에 대국민 배포 채널이 포함돼 **스토어 4종(구글, 애플, 원스토어, 갤럭시)** 지원이 필요하다고 했다. 갤럭시 스토어는 올해 IRM 평가 지원 요청으로 추가된 곳이다(9-2).
- 10-22 PM 공지: 서울시 시연을 위해 **11-13까지 앱 통합**, 10-27 공지: **올해 개발 완료 목표 12-18**. 교통과장 보고는 11월 3주차(11-16~), 시청역 사전 점검은 11-11~12경이다.

## 4. 감리 산출물 대응

- 설계 단계 1차 감리는 10-7~10-15에 진행했다. 산출물은 10-2까지 NAS에 올리고, 문서명은 `문서명_버전_날짜_사명.hwp` 형식이다. 한글 라이선스가 Mac용이라 보유분이 없어 2 copy를 구해 공유하기로 했다(웹 편집 등 합법적 방법도 허용).
- 작성 대상: 개발은 클래스 설계서(DD432), 인터페이스 설계서(DD433), 데이터베이스 설계서(DD422), 기획·디자인은 메뉴구성도(DD411), 사용자화면정의서(DD412), PM은 요구사항정의서(RQ123).
- 10-2 리뷰 지적: 언어 변경이 5종인지 6종인지(번체를 홍콩과 대만으로 나눠 6종), 일반 질문용 1:1 문의는 제외하고 보행불편 신고 유형만 남길 것, 예외 상황 유스케이스(권한 off 등)가 의도된 것인지.
- 10-6 문서 ID 체계 통합: 아로정보기술 `1xxxx`, 아이나비 `2xxxx`, LBS테크 `3xxxx`. 파일은 업체별로 따로 두고 합치지 않았다. 요구사항추적매트릭스(`PJ3-8-1`)에는 유스케이스, 클래스, 화면정의, 인터페이스 내용을 최대한 넣었다.
- 10-7 감리 중 **서비스 점검 테이블과 기능은 이번 감리에서 제거**했다. 앱 초기화 때 점검 공지·상태를 내려 주는 사양인데, 아로정보기술이 사전에 알지 못했고 관리 포인트 증가에 민감해 내부 재검토가 필요하다고 했다.
- 10-8 압축본: 메뉴구성도와 사용자화면은 변경이 없고 DB·클래스·인터페이스 설계를 브로디언 내용과 합쳤다. 오픈소스 라이선스는 앱이 관리하는데 서버 DB에 관련 테이블이 남아 있다는 지적이 있었고, 감리 중이라 문서는 못 고치고 참고만 하기로 했다.
- 10-13 PM 지시로 **1:1 문의를 '의견 보내기'로 앱에 복원**했다. 불편신고와 별개로 앱 불편·기능 요구사항을 수집하기만 하고 AppServer가 관리자 페이지로 전송만 하는 단방향 사양이다.
- 10-15 지적 중 우리 쪽: 교통약자 유형별 경로 차이(휠체어·유모차는 계단 대신 엘리베이터)가 어느 문서에도 없어 사용자화면설계서에 Description으로 추가하기로 감리단과 협의했고, 문서 ID 통합, 실내 내비 클래스·인터페이스 설계서 현행화, 단위 테스트 문서 작성이 남았다.
- 10-19 요구사항추적매트릭스 정비: 서울시 요구사항(P열)을 개발 가능한 내용(Q열)으로 바꿔 서울시와 협의하는 문서다. 합의: '내비게이션' 표기(네비 아님), 진동은 켜기/끄기만 제공(단말 모터로 세기 구분 불가), 오류 안내 문구의 매핑 화면은 '전 화면'. 감리단이 새로 부여한 요구사항 ID를 이후 문서에 쓴다. 협의조정에서 BMS 3기 고도화로 넘어간 SFR-007-RF-002~005가 표에는 '수용'으로 남아 있어 확인이 필요하다고 했다.
- 10-26 감리 최종 결과 보고서가 CF에 올라왔다. 미흡한 부분 보완과 컨소시엄 요청 사항은 사전에 공유해 준비하도록 했다. → [[seoul-donghaengmap-design-audit]]

## 5. 스토어·소셜 로그인·단말 등록

- 9-3 서울시가 준 계정으로 원스토어·갤럭시 스토어 접속을 확인했다(이중 인증 없음). 구글 플레이 콘솔은 로그인 시 2단계 인증이 필요한 것까지 확인했고 애플은 이후 진행한다.
- 서울시 계정은 운영 중인 전체 앱에 접근할 수 있어 **매번 그 계정으로 로그인해 운영하는 것은 부적절**하다는 의견이 나왔다. 대안: 사내 개발 계정을 앱스토어·플레이스토어·갤럭시 스토어 멤버로 초대해 권한을 부여한다(원스토어는 초대 개념이 없다). 배포는 한 주체가 바이너리 업로드부터 출시까지 맡는 편이 소통 비용과 의존성에서 유리하다. 애플은 App Manager 이상으로 추가하고, Sign in with Apple 키 생성에는 Admin 권한이 필요하다.
- 서울시 회신 정리: 구글·애플은 개발셀이 등록과 출시 직전까지(구글은 게시 대기, 애플은 Pending Developer Release), 출시는 서울시 홍보 담당과 외주사가 맡는다. 갤럭시·원스토어는 apk를 서울시 담당에 전달한다. 갤럭시 스토어 API 연동은 개발·관리 요소가 늘어 우선 요청하지 않는다. 인증서(개발·배포)는 서울시 공공앱 계정으로 매년 5월쯤 서울시가 생성해 전달하고, Keys(APNs, Sign in with Apple)는 부서 요청 시 서울시가 만들어 준다.
- 소셜 로그인(카카오, 네이버, 구글, 애플) 개발자 콘솔 소유자는 서울시 관리 계정으로 이관하거나 신규 생성해 초대하는 방향이다. 기존 개발사 정보를 확인할 수 없으면 동일 패키지명 중복 등록이 안 되므로 우리 계정으로 프로젝트 이관이 필요하다(9-4: 네이버는 개발 계정 등록 문제로 막히고 카카오는 가능, 구글은 수정 후 배포). 상용 소셜 로그인과 스토어 계정은 서울시 계정 자산으로 두고 키·시크릿 발급·교체는 우리가 직접 한다.
- iPhone 개발 단말은 임의 등록이 안 돼서 단말 정보를 취합해 서울시에 전달했다. 서울시가 등록했고 TestFlight는 별도 등록이 필요 없다.
- 구글·애플 개발자 계정 초대는 9-29 진행하기로 했고 10-8 지연 가능성이 공유됐다. 시연 후 서울시 담당이 바빠 급하지 않은 계정 초대는 1~2주 내 연락해 진행한다. 서울시와 주고받은 내용은 [[seoul-donghaengmap-pm-slack-2026]]에도 있다.
