# 서울동행맵 컨소시엄 협업 채널 2026

2026-07-16에 열린 외부 협업 채널이다. 처음에는 LBS테크 단독이었고 9-9에 이름을 "컨소시엄 협업"으로 바꿔 아로정보기술 PM 이사와 브로디언(백엔드 협력사) 대표를 초대했다. 참여 주체는 LBS테크(보행 경로·내비 SDK, 앱 개발 일부), 브로디언(백엔드), 아로정보기술(주관사, PM·데이터), 아이나비시스템즈다. 프로젝트 맥락은 [[seoul-donghaengmap-lbs-collaboration]], [[seoul-donghaengmap]]을 본다. 사람은 역할로 적었고, 접속 정보, 토큰, API 키, 공유 링크는 옮기지 않았다.

## 2. SDK 발행과 시연 범위 (LBS테크, 10-22~27)

- 서울시 앱 시연(11월 중순)에 맞춰 아이나비가 1차 10-28, 2차 11-11로 임의 제안했다. LBS테크 역제안은 1차 11-06, 2차 11-13이었다. 아이나비는 1차는 기능보다 통합 확인 목적이라 늦어도 11-03, 2차는 11-13이 통합 마지막 날이라 11-12까지 필요하다고 맞섰다.
- LBS테크 확정안은 **1차 10-30, 2차 11-13**이다. 같은 스레드에 "1차 SDK는 11월 3일 전달"이라는 문구도 있어 어느 쪽이 최종인지는 확인되지 않는다. ^[ambiguous] 백엔드는 1차에 명세서, 2차에 API를 전달하고, SDK 지원 가능 항목은 스프레드시트로 정리해 회신하기로 했다. 아이나비 서버 쪽 일정에는 1차 명세서가 10-29로 적혀 있어 날짜가 더 어긋난다. ^[ambiguous]
- 아이나비 시연 범위안: 10-30에는 앱 전체 UI와 서버 API 연동(목업), 11-13에는 앱 전체 UI와 서버 API 연동(실연동과 일부 목업), 실내외 내비 길안내. 저상버스 예약과 마일리지 적립은 모두 제외한다.
- **10-29 1차 전달**: LBS테크가 실외 길안내 API 연동규격서 v1.0.0(API 목록, 공통 규약, 요청·응답 항목, 오류 코드, 목업 시나리오, 미확정 사항), Swagger html, openapi.json, 목업 응답 JSON 6종(대중교통·경유지·도보·근거리 경로, 노선 선형, 오류 응답), `lbstech-navi-sdk-0.1.0`을 보냈다. 개발용 서버 주소, API 키, 하루 호출 한도는 메시지 원문에 있음(미수록). 반복 테스트는 계산 없이 녹화 응답을 돌려주는 목업 API를 쓰라고 했다.
  - 경로 탐색 `GET /dongheng/routes`: 도보·대중교통, 경유지 1곳. 경로 리스트(2-9), 상세경로(2-3), 실외 내비(2-4-1) 화면용.
  - 노선 선형 `GET /dongheng/lane`: 상세경로 지도용, 상세 화면을 열 때만 호출.
  - 목업 `GET /dongheng/mock/routes?scenario=transit|via|walk|near`, `GET /dongheng/mock/lane?map_obj=…`(응답 형식은 실제와 같다).
  - 필드는 snake_case. 도보 구간 geojson은 기존 `/pathfinder` 응답과 같아 SDK에 그대로 쓴다. `user_type`은 아로 API 서버 코드와 같은 WS(휠체어·유모차), SP(고령자·임산부), LV(저시력), TB(전맹). 재탐색 때 같은 대중교통 경로인지는 `map_obj`로 비교한다. 요금은 일반(성인) 교통카드 기준이고 실시간 도착 정보는 없다(아로 API 서버 제공).
  - 운영 구조에서는 아로 API 서버가 이 API를 불러 앱에 전달하고, 전달된 키는 개발·테스트용이다. SDK는 실외 내비 화면의 턴바이턴 안내에 쓰며 사용법은 SDK 가이드 문서를 따른다.
- LBS테크가 물은 "실외 보행+대중교통 수준인지, 실내 지도까지 포함인지"에 대한 직접 답은 채널에서 확인되지 않는다. 10-27 아이나비는 앱 시연 일정이 확정돼 11-13 오전까지 개발 가능 항목과 계획 공유를 요청했고, 12-18을 단위 기능 개발 완료 시점으로 본다고 밝혔다.

## 3. 도보 내비 SDK 연동

### 혼합 경로 (10-13)
- 도보→버스→하차→도보 경로에서 SDK는 **도보 구간만** 안내한다. 합의 방향은 전체 경로 route를 한 번만 받고, 하차 후 도보 구간은 "새 안내"로 시작하는 방식이다.
- 예시 흐름(도보 0, 버스 1, 도보 2, 실내 3, 도보 4): `session.start(journey)`로 여정 등록과 0번 도보 시작 → 도착 콜백 후 앱이 버스 구간 처리 → `session.startWalk(2)` → 실내가 끝나면 `session.startWalk(4)`.
- 안내 화면을 SDK에서 처리할지, 앱이 처리할지, SDK–메인앱 통신은 아이나비가 10월 말에 검토해 다시 논의한다.

### 빌드 환경·CMP
- 빌드 환경 회신(9-9) 표는 [[seoul-donghaengmap-dev-slack-tech-2026]]와 동일하다(Kotlin 2.4.10, AGP 9.3.2, minSdk 29, iOS 16 등). LBS테크는 CMP 기반으로 개발하고 내비 SDK는 앱 `commonMain` 의존성으로 받는다.
- 공개된 아이나비 CMP 지도 SDK는 없고 베타로 개발 중이라(9-21 배포 가능 예상) 우선 공개된 Android·iOS SDK로 검토하도록 했고, 이후 CMP 지도 프로젝트와 가이드를 비공개로 공유했다(값 미수록).
- 10-13 질문: 지도 SDK 0.4.1이 compileSdk 37을 요구하는데 메인앱도 37인가 → 메인앱 compileSdk 37, targetSdk 36. 전맹 화면에서도 [안내 종료] 시 확인 팝업을 띄우는가 → 동일하게 띄운다. 좌표를 주면 현재 위치 주소를 보내 줄 수 있는가 → 가능하나 메인앱 대 앱서버 처리 주체는 시나리오별 검토.

### 음성 안내 규격 (10-01, 10-27)
- LBS테크 구현: 앱 TTS 단일 채널(스크린리더는 `aria-live`를 걸지 않음). 낭독 계기는 행동 이벤트(회전 예고, 회전 시점, 도착), 거리 경과, 사용자 요청 3종이다. 거리 경과는 100m 초과 시 50m, 100m 이하 시 30m, 30m 이하 시 10m 주기이고, 회전 예고는 30m 앞이며 이벤트가 거리 경과보다 우선한다.
- 아이나비 기획의 전맹 외 사양: 계기 7종(안내 시작, 회전 예고 30m 전, 회전 시점 10m 전, 경유지·목적지 도착, 이탈 재탐색, 시설물 진입 전 30m, 거리 경과). 거리 경과는 직진 구간 시작 시 1회와 남은 거리 500m 배수마다 1회이고 직전 낭독에서 200m 이상 걸었을 때만 적용한다. 우선순위는 긴급 > 이탈 재탐색 > 행동 이벤트 = 시설물 = 거리 경과(겹치면 이어 읽기)다.
- 멘트 차이: **전맹은 모두 시계 방향**("3시 방향으로 도세요", "12시 방향으로 464미터 직진입니다"), 전맹 외는 좌/우이며 5갈래 이상·대각선 횡단만 시계 방향이다.
- 쟁점: 5갈래 이상 교차로와 대각선 횡단을 판단할 데이터가 경로 데이터에 없다. LBS테크 링크 길이는 평균 200~300m(노드 간 약 300m), 최대 약 1km라 500m 배수 기준으로는 거리 경과 안내가 안 나오는 경우가 많다. 링크 속성(경사, 파손, 점자블록)이 바뀌는 단위로 연속 안내하며 방향 표현은 꺾임 각도만 쓰고 앱은 `maneuver` 값만 쓴다. 거리 경과 기준(링크 기준 대 다음 행동 지점 기준)의 최종 합의는 확인되지 않는다. ^[ambiguous]
- 10-27 방향지시 면: '누르면 재낭독'은 남은 거리와 방향("12시 방향 464미터 남았습니다(직진입니다)")이며 회전은 노드 도착 전 30m에서 예고하고 10m에서 다시 안내한다. LBS테크 개발자는 회전 예고가 너무 멀고 별도 예고 음성은 필요 없어 보인다고 봤다. 아이나비의 최종 회신은 보이지 않는다.
- 아이나비는 음성 발성 사양을 한 번에 정리해 달라고 요청했고 LBS테크가 정리해 공유하기로 했다. 10-28에 LBS테크가 음성 발화 사양 스프레드시트를 공유했다(링크 미수록, 내용은 미반영). 전맹 모드는 확정 사양이 아직 없다.

## 4. 브로디언: DB·API 설계와 역할 분담

### 협업 방식
- 순서는 "화면정의서·관리자 화면정의서 완료 → DB 설계 → API 연동 규격서"다(10-1). DB는 MySQL 8, 아이나비가 베이스 프로젝트를 제공해 양사가 같이 개발한다.
- 9-15 브로디언이 지하철·즐겨찾기·지하철역(서울)·광진구·저상버스 메시지·예약 정보의 컬럼명을 문의했다. 서비스 중인 동행맵 테이블은 서울시 운영유지보수 업체 확인이 필요한 건으로 보았다. 즐겨찾기는 개인정보(경위도, 주소)라 서버가 아닌 앱에서 관리하는 것으로 정리하고 문서 반영을 요청했다.
- 아이나비는 OpenAPI(yaml) 규격서를 공유했다. `[임시]` 표시는 컨소시엄 제공 규격이 없거나 담당 미정이라 기획 기준으로 먼저 쓴 부분이다.

### 감리 문서 (10-7)
- DD432 클래스 설계서, DD433 인터페이스 설계서(yaml 포함)는 브로디언이 쓴 문서만 업데이트하고 아이나비 것은 정리하기로 했다. ID는 10000번대(`CDD-A10101`, `API-10101`), 표지 제목은 "서울시 교통약자지원 통합플랫폼(서울동행맵) 고도화 구축", 문서 버전 0.91, 꼬리글은 "아로정보기술 컨소시엄"이다.
- 기능 추가: 실외/실내 길찾기 API, 저상버스 예약 화면 API, 스토어 링크 전달(OS 구분, 앱 ID·패키지명 전달, Android는 스토어 URL 전달). 삭제: 앱 메뉴 사용 이력 전송, 길찾기 검색 이력 전송, 오픈소스 라이선스 목록 조회(앱이 관리).

### 실외 길안내 API camelCase 통일 (11-03)
- LBS테크가 실외 길안내 API(NAV-101 경로 탐색, NAV-102 노선 선형)의 이름 규칙을 **camelCase로 통일**했다. 기존 문서는 snake_case와 섞여 있었다.
- 바뀐 것: 요청 파라미터(`start_x`→`startX`, `user_type`→`userType`, `map_obj`→`mapObj` 등), 밑줄이 든 응답 키 전체(`arrival_at`→`arrivalAt`, `walk_only`→`walkOnly`, `journey_seq`→`journeySeq` 등), 코드 값(`reason` `walk_failed`→`walkFailed`, `cautions[].type` `STAIRS`→`stairs`·`CROSSWALK`→`crosswalk`·`SHARED_ROAD`→`sharedRoad` 등, `warnings` `TRANSIT_UNAVAILABLE_WALK_FALLBACK`→`transitUnavailableWalkFallback`), 도보 구간 geojson의 고도 키(`start_z`→`startZ`, `end_z`→`endZ`)와 출발·도착 연결부 ID(`start_node`→`startNode`, `end_edge_2`→`endEdge2` 등), 429(호출 한도 초과) 응답의 `key_name`→`keyName`.
- 안 바뀐 것: 접속 주소, `x-api-key`, 하루 호출 한도(값 미수록), 응답 구조와 단위(시간 초, 거리 m), 교통약자 유형 코드(WS·SP·LV·TB). 내비 SDK 0.1.0 연동에는 영향이 없고, 도보 구간 geojson을 SDK 변환기(`Directions.fromGeoJson`)에 넣어도 결과가 같음을 LBS테크가 확인했다. 앱의 API 연동(PR #55, 10-30)은 필드명을 맞춰야 한다. ^[inferred]

### 버스 하차 알림 우선순위 (11-03)
- LBS테크가 메인 앱도 버스 하차 알림을 하는 것으로 보인다며 우선순위를 물었다. LBS테크 안은 **하차 전 정류장에서 PUSH와 음성 안내, 하차 정류장 150m 전에 PUSH와 음성 안내**이고, 메인 앱에 푸시 알림 권한이 있으면 SDK가 푸시를 보내겠다는 것이다.
- 11-04 PM이 UX 사양(하차 예고: 하차 정류장 2정거장 전, 하차 임박: 1개 전 통과 PUSH)과 다른 이유, SDK가 직접 푸시를 보내려는 이유를 물었다. 앱은 SDK가 이벤트를 콜백으로 주고 메인 앱이 푸시를 보내는 방식을 생각한다. LBS테크 회신으로 정리됐다: ① 화면기획서대로 예고·임박 PUSH ② 하차 관리는 메인 앱과 SDK가 따로 한다(예약 없이 내비만 쓰는 경우, 승하차 예약만 쓰는 경우) ③ **SDK는 콜백만 주고 알림(배너·알림음)과 문구는 메인 앱이 정한다**. 이대로 설계 문서와 SDK 작업을 진행한다.

### POI 접근성 상세의 미조사 구분 (11-04)
- 서버 개발이 `GET /pois/inavi/detail`(POI명·좌표로 매칭된 POI의 접근성 상세)의 `dtl_data`가 true/false뿐이라 기획의 있음·없음·미조사 중 미조사를 구분할 수 없다고 물었다. LBS테크: `dtl_data`의 false는 모두 "조사했는데 없음", 조사하지 않은 항목은 null로 고친다.
- 응답 규칙: `data`가 빈 배열인 세 경우는 `message`로 구분한다(`POI not matched` 매칭 POI 없음, `POI detail not found` 장소 상세(출입구) 없음, `POI detail not surveyed` 상세는 있으나 미조사). 값이 있으면 `POI Detail fetched successfully`이고 조사된 상세만 내려간다. 출입구가 여러 개면 미조사 출입구만 `dtl_data`가 null이고, **배열의 출입구 순서에는 의미가 없다**. "not surveyed"를 "dtl_data 값이 전부 false인 경우"로 설명해 false 규칙과 겹친다. ^[ambiguous]

### 실외 내비 바텀시트 전체 경로와 lane API (11-04)
- LBS테크 SDK 담당이 바텀시트의 전체 경로가 지하철을 포함한 전체 경로인지 물었다. 실외-버스-실외-지하철-실외-목적지 경로면 지도 표시를 1차(지하철 입구까지)·2차(목적지 입구까지)로 나누려 한다.
- LBS테크 API 담당은 화면기획서 2-3(상세 경로 지도에 탑승 구간 노선 표시)용 `GET /dongheng/lane`이 ODsay 노선 그래픽 API 결과를 형식만 바꿔 넘기는 구조라, 메인 앱이나 앱 서버가 ODsay를 직접 부르는 편이 낫다고 제안했다(경로 응답의 `routes[].mapObj`를 그대로 사용).
- PM은 두 건 모두 경로가 실외·실내로 나뉘어 시나리오를 내부 검토 중이라며 개발 검토 후 답하기로 했고(11-05), 앱 개발에 SDK 검토와 함께 정리해 달라고 했다. → [[seoul-donghaengmap-dev-slack-tech-2026]]

### 지하철 안내 주체와 멀티모달·lane API (11-05)
- LBS테크는 "LBS: 실외-버스-실외, 아이나비: 실내-지하철-실내"로 이해했다고 했고, PM은 대중교통(버스·지하철)은 LBS테크, 실내 안내만 아이나비로 이해한다고 답했다. LBS테크는 지하철은 GPS가 안 돼 안내할 수 없고, 과업은 원래 보행 내비이며 감리 때 구두로 버스까지 하겠다고 한 것이라고 했다.
- LBS테크 API 담당: 백엔드 멀티모달 개발은 LBS테크 담당이 맞다. 쟁점은 지하철 안내를 SDK와 메인 앱 중 어디서 하느냐이며, SDK에 지하철을 넣으면 SDK 도보 → 실내 내비 → SDK 지하철 → SDK 도보로 화면이 오가 더 부자연스러우므로 SDK는 도보 안내만 맡는 것이 맞다는 의견이다. PM은 과업 범위를 확인하겠다고 했다.
- 멀티모달 탐색은 한 번의 호출로 도보·버스·지하철을 묶은 경로 후보 전체를 준다(도보는 교통약자 유형별 보행 경로선, 대중교통은 노선·승하차 지점·정차 목록과 좌표·소요시간). lane API는 재탐색이 아니라 정차역 좌표를 이으면 꺾인 선이 되는 구간을 실제 노선 모양으로 그리기 위한 좌표 API다. 경로 리스트(2-9)에는 지도가 없어 후보마다 미리 받을 필요가 없고, 멀티모달 응답에 ODSay lane 호출 값(`mapObj`)이 있으니 메인앱 → 앱서버 → ODSay 직접 호출도 제안했다(현재 LBS테크 제공분을 그대로 써도 된다).
- 아이나비 검토(PM 전달): 목업 기준 `routes`는 도보 구간 경로열만, 대중교통 노선 경로열은 lane API로 따로 받는 구조다. 문의 3건은 ① 멀티모달 응답에 대중교통 선형이 포함되는지 ② 아니면 도보·대중교통을 결합하는 주체(SDK·앱 서버·앱) ③ 최종 구조에서도 lane API를 쓰는지. 바텀시트 전체 경로와 지도 구간 분할(지하철 입구까지 → 지하철 이동 → 출구에서 목적지까지)도 같은 문제로 본다. → [[seoul-donghaengmap-dev-slack-tech-2026]]
- 슬랙으로는 정리가 어려워 화상회의를 제안했고, LBS테크 일정으로 **11-09(월) 10:30 슬랙 허들**로 잡혔다. PM의 회의 초대 본문은 "도보·버스는 LBS테크(UI·데이터), 나머지 아이나비(UI·데이터)"와 "LBS테크는 데이터만, 아이나비가 UI 전체" 두 안을 정리 대상으로 적었다.

### 장소 상세 출입구 배열 (11-05)
- 서버 담당 문의에 LBS테크 답: `/pois/inavi/detail` 항목의 `x`·`y`는 출입구 좌표다. 한 장소에 한 개 이상 오고 정렬 조건은 없다. `data` 배열은 한 POI의 여러 출입구이며, 1건이면 수집된 출입구가 1개다.

### 길찾기 내역 저장과 다국어 범위 (11-05)
- 서버 담당이 브로디언 서버 저장소의 「로그인 이력·길찾기 내역 저장」 커밋(`TBL_ROUTE_HIST`에 사용자·출발지·도착지 이름·교통약자 유형 저장)이 10-07 길찾기 검색 이력 삭제 요청과 어긋난다며 배경을 물었다. 브로디언은 관리자 화면 통계 용도라고 답했고, 서버 담당은 유선 논의대로 `USER_ID` 등 개인정보 관련 컬럼을 빼는 방향으로 진행해 달라고 했다.
- PM이 아로 이사에게 백엔드가 말한 다국어 4종(KO·EN·JA·CN 간체)이 ODSay 검색 등 백엔드에만 해당하는지 서비스 전체인지 물었다(구간 안 회신 없음). 앱 쪽은 ODSay 연동 데이터만 간체로 받고 앱은 6종을 유지하는 쪽으로 정리했다. → [[seoul-donghaengmap-dev-slack-tech-2026]]

### 경로 탐색 필터와 다국어 파라미터 (11-06)
- 서버 담당이 LBS테크 API 담당에게 v110 경로 탐색 규격에 대해 두 가지를 물었다(11-04 스레드). 화면기획서 v1.2 41p(경로 리스트의 경로 탐색 시작)에는 필터 4종(저상버스·엘리베이터·경사로·계단 회피)과 교통약자 유형별 기본값(휠체어·유모차: 저상버스·엘리베이터·계단 회피, 노약자·임산부: 계단 회피, 저시력·전맹: 없음)이 있는데, API에는 도보 옵션 `option`(short·safe)만 있어 계단 회피는 `option`과 `hasStairs`로 처리할 수 있지만 엘리베이터·경사로·저상버스는 판단할 근거가 없다.
- 질문: ① 교통약자 유형별 기본 `option`(short·safe) ② 엘리베이터·경사로·저상버스로 경로를 거를 파라미터나 판단 필드 제공 ③ 언어 파라미터를 받아 ODSay 호출에 넘길 수 있는지(ODSay lang 0~3, 앱은 6종 언어이고 정류장·역·노선 이름은 ODSay KO·EN·JA·CN으로 받지만 경로 결과 이름은 한국어만 나옴) ④ 출구·엘리베이터 이름처럼 LBS가 만드는 이름도 다국어로 주는지. 구간 안 회신은 없다.
