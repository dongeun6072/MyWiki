# Slack #10_prj-orbis-navisdk 대화 (2025 Q4)

TomTom Orbis Map NaviSDK POC 공개 채널 `#10_prj-orbis-navisdk`의 2025-10-01~12-31 구간 기록이다(실제 메시지 범위 2025-10-01~12-30). 프로젝트 허브는 [[orbis-sdk]], 개발 흐름은 [[orbis-navisdk-development-2025]], 상용화 스크럼은 [[navisdk-commercialization-scrums-2025-2026]], 대만 사업 배경은 [[orbis-taiwan-business-2025]]를 본다. 이 분기는 10월 중순 대만 현지 전시회·평가를 마치고 10월 30일 "상용화 단계 전환"을 선언한 뒤 상용 서버, iOS 지원, 최소 OS, 데이터 후속 검토로 이어지는 흐름이다. 이후 기록은 [[navisdk-prj-slack-2026-h1a]], 앞선 기록은 [[navisdk-prj-slack-2025-q3]]를 본다.

구간 내 채널 메시지 38건(입장 알림 6건 포함)과 스레드 답글 125건을 모두 읽었다. 답글이 달린 스레드 19개를 전부 열었고 미열람은 0개다. 첨부는 파일명·종류만 기록했다(내용 미열람). 사람은 역할로 적었고, 서버 주소·경로·링크·인증 식별자·연락처는 옮기지 않았다(원본에 있음, 미수록). 개발 PM 수석이 대부분의 질의·공유를 주도한다.

## 1. 대만 지도 데이터: 한자 표기 우선순위와 타일 검수 (10월)

### 1.1 한자 표기(간체/번체) 문제 (2025-10-10~10-13)
- **2025-10-10 발단**: 개발 PM 수석이 통역사 의견을 전하며 지도 언어 문제를 제기. 대만은 번체를 쓰는데 첨부 스크린샷의 지도 표기가 간체였다. 개발 쪽 확인과 별개로 데이터 쪽 확인을 요청.
- POI 담당(POI Plus팀)의 확인 결과: 해당 POI는 대표 명칭 `name` 키에 간체가 들어가 있었다. 현재 추출 과정은 `name`에 한자가 있으면 그것을 우선 채택하고, `name_zh_hant`(번체)와 `name_zh_hans`(간체)가 있으면 각각 채택한다(name>번체>간체>영문). 조치안: 가공 단계에서 번체 키값이 있으면 표출 명칭에 우선 입력하도록 프로세스 수정. 한자 표출 우선순위를 "번체 > name > 간체 > 영문"으로 적용해도 되는지 검토 요청.
- 개발 PM 수석 질의 -> 우선순위는 한자 명칭에만 적용되며, 영문 명칭은 `name`이 영문뿐일 때 그 값 > `name_en` > `name_en_latn` 순으로 만들고 영문이 없으면 미표출. 순위를 조정한 데이터는 기제작 버전으로 제작하면 당일 전달 가능, 타일 재컨버전 일정은 타일링 담당 선임이 검토. 개발 PM 수석은 전시회용 리플렛·참고 이미지를 번체로 재적용해야 해 일정이 부족하니 앱 표출까지 차주 초에 마무리 가능한지 확인 요청, 해당 일정으로 진행하기로 했다.
- 후속 질의: 이번 순위 적용 후 나중에 간체를 표기하려 할 때도 간체+번체가 섞일 가능성이 있는가 -> 있다. 데이터상 명칭 정보에 간체만 있으면 간체가 표출될 수 있고, 주기명칭 기준 번체 또는 간체만 온전히 표출하려면 별도의 명칭 분석 프로세스 정비와 추가 시일이 필요하다.
- **2025-10-13**: 타일링 담당 선임이 당일 오전 pbf 업로드(CDN)를 마쳤고 경로를 공유(경로 미수록), 검수 페이지 연결 요청. 개발 PM 수석은 번체 지도가 언제까지 캡처되는지(이미지 제작 일정) 확인 요청, 당일까지 이미지가 전달돼야 리플렛을 인쇄해 전시회에 가져갈 수 있다고 전달.
- 10-13 POI 담당 확인: 보낸 스크린샷과 동일 지점 POI 주기가 번체로 정상 적용됐고, 번체 태그가 있는 다른 POI도 번체가 최우선으로 반영된 버전이다(한자 모드 우선순위: 번체 > 정식명칭(번/간 혼용) > 간체 > 영문).
- 웹서비스개발팀 주임이 테스트 페이지 연동을 마쳤으나 한문/영문 변경 로직 수정에 1시간 정도 더 필요하고, 도로 방향성 심볼이 잘못 표출되는 것 같다고 확인 요청. 타일링 담당이 심볼 설정을 고친 LIF csv를 재전달: `direction`이 들어간 10개 레이어의 `icon-rotate` 값을 0에서 90으로 수정, 다른 변동 없음. 같은 날 웹서비스개발팀이 검수 페이지를 다시 공유.

### 1.2 대만향 최종 타일링 데이터 사전 검수 (2025-10-15~10-17)
- **2025-10-15**: 타일링 담당(Digital&Display팀) 선임이 최신 TomTom 데이터(25.09.29 기준)로 만든 대만향 최종 타일링 데이터의 mbtiles 변환을 마쳐 사내 공유 서버에 올렸다고 보고(경로 미수록), 검수 페이지 연결을 요청하며 LIF 파일(`INAVI_TIWAN_SDK_LIF_3rd_251014.csv`) 첨부. 웹서비스개발팀이 담당자 휴가로 내일 중 공유 가능한지 문의. 타일링 담당은 이상 없으면 내일부터 검수하되, 수정사항이 생기면 목요일 퇴근 전까지 최종 shp가 재제작돼야 차주 월요일 오전까지 pbf 타일링 데이터를 공유할 수 있다고 안내. 개발 PM 수석은 담당자 복귀 후 진행하도록 회신.
- **2025-10-16**: pbf 컨버전·업로드 완료(경로 미수록). 웹기술개발팀 주임이 mbtiles 검수 페이지와 PBF 검수 페이지를 차례로 공유(개발서버, 방화벽 설정 환경이라 안 보이면 알려달라고 안내). 지도 데이터 팀장이 검토 항목(간체->번체 정상 반영, 인코딩 오류로 인한 "?" 표출, 도로 라인 dissolve 처리로 심볼 수 정리)을 요청, 타일링 담당이 세 항목 모두 정상 반영됐다고 확인(스크린샷 3건 첨부).
- 같은 날 검수 중 일부 데이터 오류 발견: 국립공원 주기가 버스정류장 심볼로 표출, 원본 데이터 오류로 잘못된 행정계 존재. 재컨버전 후 17일 오후 6시경 업로드 예정. 개발 PM 수석은 월요일(10-20)까지 앱 지도 표출에 번체가 적용돼야 한다며 일정 확인을 요청. 웹기술개발팀은 재컨버전이 금요일 오후 6시 이후 완료되면 바로 검수 페이지를 연결하겠다며 상용 반영 일정을 두 가지로 제시: (1) 금요일 오후 6시 이후 상용 반영, (2) 10-20(월) 오후 1시 이후 상용 반영.
- iOS/AOS 앱 담당(DC.KIM)의 답: 앱 패치는 필요 없으나 스타일 변경이 필요하고(Agent 쪽), 캐시 데이터가 남을 수 있어 이미 설치된 앱도 초기화가 필요하다. 지도 스타일 파일에 자동 반영되지는 않고 현재 구조상 영문/중국어 스타일을 별도로 반영하므로, 반영 후 알려주면 적용 및 테스트하겠다고 답. 개발 PM 수석은 앱 패치가 필요 없다면 월요일 반영도 될 것 같지만 패치가 필요하면 최대한 빨리 진행해야 한다고 정리.
- **2025-10-17**: 타일링 담당이 재변환 완료 후 업로드했으나(오전 11:35, 경로 미수록) 14시경 업로드 데이터에 문제를 발견해 다시 올리는 중이라고 공지, 오후 6시 완료 예정. 웹기술개발팀은 신규 데이터가 업로드돼도 style.json이 동일하게 유지될 것으로 판단해 251015 데이터 기준 style.json을 공유(링크 있음, 미수록). 이전 스타일과 비교해 `text-field`가 영문/한자 표기로 바뀌었다(도로명 `{name_en}` / `{name}`, 다른 POI `{NAME_EN}` / `{NAME}`). 타일링 담당 16:46 재업로드 완료 보고(경로 동일), 웹기술개발팀 17:02 동일 `sources`(`ServiceData`, 벡터 타입)로 신규 데이터 업데이트 및 최종 검수 페이지를 공유하며 앱 내 지도 표출 확인을 요청. iOS/AOS 앱 담당(DC.KIM)이 18:11 "지도 표출 정상 동작" 확인.

### 1.3 야간 지도 스타일과 폰트 (11월~12월)
- **2025-11-05**: 타일링 담당이 지난 9월~10월 스레드에서 프로덕트전략셀이 공유한 야간(Dark) 지도 컬러 기준으로 LIF 제작을 완료했다고 공유(`INAVI_TIWAN_SDK_LIF_night_251103.csv` 첨부). 주간/야간 구분은 리스트 상단 열 명칭에서 light/dark, 카테고리는 하단 시트 '배경/주기', 모든 색상은 RGB 값(주간 속성 값은 내부 관리용). 웹기술개발팀 주임이 야간 스타일 검수용 테스트 페이지와 야간 style.json을 공유(링크 있음, 미수록).
- **2025-11-14**: 개발 PM 수석이 스타일 검수 완료 여부를 문의. 지도 데이터 팀장이 컬러는 프로덕트전략셀 제공 값으로 작업이 완료됐다며 의도대로 적용됐는지 검토를 요청, 프로덕트전략셀 책임이 검토 완료, 추가 수정사항 없음으로 회신.
- **2025-12-03**: 웹기술개발팀 주임이 **중국어 폰트 통일화 검토**를 위해 기존 대만향 스타일 폰트를 Regular에서 Medium으로 바꾼 테스트 페이지를 공유(NotoSansRegular 161개 -> NotoSansSCMedium, NotoSansBold 23개 -> NotoSansSCBold, 두께는 동일하고 이름만 변경). 기존(상용) 페이지와 변경(테스트) 페이지를 나란히 제공하고 의견을 요청했다. 구간 내 답변은 없다.

## 2. 현지 평가 이후 상용화 전환과 일정 (10월 30일~11월)

- **2025-10-21**: 교통정보 서버 담당이 Orbis 대만지도 251001 버전 교통정보 생성 서버 업데이트를 공지(10-21 15:10~15:20, 서비스 영향은 1~2타임 순단). 15:31 업데이트 완료 보고. 작업자 연락처는 원본에 있음(미수록).
- **2025-10-30 개발 PM 수석 공지(@channel)**: 지난주 대만 현지 전시회와 평가가 진행됐고 실차평가에서 발생한 이슈를 공유한다. 공유된 시트(링크 있음, 미수록)에 `금주까지 목표 일정`을 기입해 달라고 요청했다. 금일 대표 보고에 현지평가 이슈가 보고될 예정이며 **대표 보고 이후 상품화(상용화) 단계로 전환**하려 하니 업무 진행을 부탁. 상용화 단계 필요 항목:
  - 상용서버 전환(담당: Agent, 탐색서버, 인증서버, 교통정보 서버) - 상용서버에 적용할 Spec 공유 요청
  - iOS 지원(담당: MMC Lib, Orbis Route Data Lib) - iOS lib 지원 일정 공유 요청
  - 상용화 프로세스 정립(담당: PM) - R&R 정립
- 스레드 요지(2025-10-30~11-27):
  - 탐색엔진 팀장이 상용서버를 일괄 적용할지, 일괄이면 AWS와 NHN 중 어디에 만들지, 담당별 운영인지 문의 -> 개발 PM 수석은 서버 구성을 아직 자세히 정의하지 않았고 우선 서버별 Spec만 공유해 달라고 답. 팀장은 교통정보 API 사용료가 TomTom에 지불되는지(상용화 이후 포함) 확인 요청.
  - 교통정보 서버 담당은 상용 서비스를 위해 AWS/NHN 클라우드로 이전할 때 TomTom 교통정보 API 호출에 추가 인증이 필요한지, 기존 방식으로 가능한지 확인 요청(5절 참조).
  - 개발 PM 수석: iOS는 AIR와 국내 NaviSDK 모두 최소지원 iOS 13. AOS는 문서상 "AIR - API 23(Android 6.0), NaviSDK - API 21(Android 5.0), 동일 기준으로 개발 요청"이라 AIR용인지 국내 NaviSDK용인지 명확히 해달라고 요청. 사업(전략)팀 과장은 타깃 서비스에 Taiwan Taxi(Android 5.0 이상 지원)가 포함돼 있어 국내 NaviSDK 기준으로 지원해 달라고 답. 과장은 대만 출장 준비 중 개발 PM 수석께 공유했던 `iOS 개발 필요성 및 Android 지원 버전 검토`를 전달하며 첨부(`Orbis_대만_NaviSDK_iOS_개발_필요성_AOS추가_Oct02_2025.pdf`, application/pdf)했다.
  - 10-31: 지도 데이터 팀장이 이슈리스트 5, 7, 9번 행의 검토를 요청. 2025-11-27 탐색엔진 담당 수석이 `[10월 대만 현지평가 이슈리스트]` 시트에서 탐색엔진 관련 3행, 6행, 19행을 업데이트했다고 보고.

## 8. POI와 motorcycle 데이터 검토 (12월)

### 8.1 Offline 내비용 POI 데이터 (2025-12-16~12-18)
- **2025-12-16**: 개발 PM 수석이 Offline 내비를 지원하기 위해 검토 중이며 그중 offline 검색 기능을 위해 데이터를 확인 중인데, TomTom 답변으로는 받는 지도에 POI 데이터도 존재한다는 취지의 답변을 받았다며 확인 가능 여부 검토를 지도 데이터 담당 책임에게 요청(전달받는 지도 타입에 따라 없을 수 있음). 추가로 TomTom이 전달하는 지도는 Full Bundle이라고 한다.
- 지도 데이터 담당 책임의 검토 결과(12-16 17:51): TomTom ORBIS 내 POI 데이터는 "Search"로 분류돼 있고 지명 및 영역 정보, POI(TomTom 명칭 Location of Interest), 전기차 충전소, 도로명 주소, 우편 번호 항목이 존재한다. POI 건수는 약 36만 개로, 아이나비 POI(약 690만 개)에 비해 절대적 양이 국내 대비 매우 적다. 음식점 카테고리 POI는 TomTom ORBIS 대만 약 10만 개 대 아이나비 약 100만 개.
- 12-17: 개발 PM 수석이 Search 관련 포맷 문의와 실제 데이터 확인 문의를 위해 16시 회의 시간을 확인했고 담당 책임이 가능하다고 답, 장소는 개발 PM 수석이 Path-1 회의실을 예약해 두었으며 책임은 4시에 맞춰 가겠다고 답.
- **2025-12-18**: 지도 데이터 담당 책임이 대만 내 POI 데이터 샘플을 전달(3건: 고속도로 휴게소, 전시장, 극장). 판단: 카테고리·명칭·주소는 대부분의 POI가 보유해 사용 가능하나, 샘플처럼 대표값이 영어/번체가 섞여 있는 경우가 있어 **전처리가 필요**. 샘플은 키(`name`, `name:en-Latn`, `name:zh-Bopo`, `name:zh-Hant`, `addr:*`)와 Feature Group(Driving, Business, Arts And Culture)의 구조로 제공됐다(스레드에 기록, 주소·좌표 상세는 미수록).
