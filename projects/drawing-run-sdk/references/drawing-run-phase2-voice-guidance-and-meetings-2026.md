# 드로잉런 2차 개발 항목과 음성 안내 협의 (2026-06 ~ 07)

1차 SDK 전달이 끝난 뒤([[drawing-run-sdk-release-history-2026]]) 2차 개발의 협의 항목을 정리한 "2차 개발 항목" 페이지와 그 하위 2개 페이지다. 전체 흐름은 [[drawing-run-course-guidance-data-flow-2026]]에 있다.

## 2차 개발 항목 (2026-06-11)

**진행 예정·협의**
- 앱 코스 목록·상세·주행·완료 플로우(기획안 요청 완료, 고객사 회신 대기).
- 삼성생명 어드민의 코스 등록 방식, GPX 등록·저장·상태값 관리.
- 안내데이터 생성 요청, 상태 조회, 실패 시 재요청 정책.
- 정책 확정: **코스 이탈 기준, 완주 판정 기준, 안내데이터 생성 실패 처리, GPX 오류·누락 처리**.
- 음성 안내: 안내 범위, 재생 주체(SDK vs 앱), TTS 방식, 백그라운드·무음모드 동작, 사용자 on/off, 안내데이터 문구 필드.
- 데이터 전달 포맷, 이미지·경로·주행 결과 저장 방식, 앱 배포와 SDK 전달 일정, 2차 서비스 예상 일정.

**체크리스트**
- 업무 R&R: 앱·어드민 화면, 서버 저장, 코스 목록 제공은 **삼성생명**, 안내데이터 생성, 경로 안내, 주행 판정, SDK/API 제공은 **아이나비**.
- **API 명세가 바뀌면 Slack과 Confluence를 동시에 현행화**해야 한다.
- 이탈·완주 기준과 GPX 오류 처리 등은 **개발 착수 전 확정**.
- Slack Connect의 외부 사용자 권한 만료 여부 확인(싱글 채널 게스트).
- 2차 항목이 확정되면 개발 요청, Jira 이슈 생성, 일정 관리.

## 음성 안내 개발 협의 항목 (2026-07-08)

1차를 완료한 것으로 보고, 2차 핵심인 음성 안내를 위해 삼성생명과 정할 항목이다.

### 결정해야 할 것

| 구분 | 핵심 질문 | 주 담당 |
|---|---|---|
| 음성 안내 범위 | 어떤 상황에서 안내할지 | 삼성 기획, 아이나비 SDK |
| 안내 문구 | 아이나비가 만든 문구를 그대로 쓸지 | 삼성 기획, 아이나비 |
| 재생 주체 | SDK가 직접 재생할지, 앱이 이벤트를 받아 재생할지 | 삼성 앱, 아이나비 SDK |
| TTS | 단말 OS TTS인지 음원인지 | 삼성 앱, 아이나비 SDK |
| 타이밍 | 몇 m 전, 이탈 시, 복귀 시 | 삼성 기획, 아이나비 SDK |
| 백그라운드 | 화면 꺼짐 상태에서도 필요한지 | 삼성 앱, 아이나비 SDK |
| 사용자 설정 | on/off | 삼성 기획, 앱 |
| 운영 | 운영자가 문구를 수정할 수 있어야 하는지 | 삼성 운영, 아이나비 |

### 역할 분담

| 영역 | 삼성생명 | 아이나비 |
|---|---|---|
| 기획 | 안내 상황과 문구 정책 | 가능한 이벤트와 제약 |
| 안내데이터 | 저장, 앱 제공 | 음성 문구와 안내 타입 생성 |
| 앱 | 음성 설정, 화면 표출, 권한 | SDK 이벤트 수신 방식 제공 |
| SDK | 호출, 이벤트 수신 | 안내 타이밍 판단, 이벤트 전달, 필요 시 재생 |
| 운영 | 코스 검수, 문구 확인, 노출 | 실패 사유·재생성 지원 |
| QA | 앱 환경별 검증 | 위치·안내 로직 검증 (백그라운드, 이어폰, 무음모드) |

### 음성 안내 범위 제안

| 상황 | 2차 포함 |
|---|---|
| 코스 시작 | 포함 권장 |
| 진행 방향 안내(직진·좌/우회전), 안내 지점 사전 안내, 경로 이탈, 완주 | 포함 |
| 안내 지점 도달 안내, 경로 복귀 | 포함 권장 |
| 일시정지/재시작, n km마다 거리·페이스 안내 | 협의 필요 |
| 실시간 재탐색 | 제외 권장(코스 따라가기 기준) |

### 안내데이터 필드와 앱/SDK 협의

- 필수 필드: **안내 타입**(시작, 좌/우회전, 직진, 이탈, 복귀, 도착 등), **화면 안내 문구**, **음성 안내 문구**, **안내 위치**(위경도 또는 경로 상 위치), **사전 안내 거리**. 권장: 중복 방지 키, 우선순위(이탈 안내와 일반 안내 충돌).
- 앱/SDK 질문: 재생 주체, 이벤트에 음성 문구를 담아 전달하면 충분한지, 백그라운드, 무음 모드, 이어폰·블루투스 출력, 다른 오디오와의 충돌(볼륨 ducking), 사용자 설정(on/off, 볼륨, 빈도), GPS 흔들림에 의한 중복 안내 방지, 이탈 안내 기준(몇 초/몇 m), 완주 기준과 문구.
- 운영 정책: 문구 수정 가능 여부, GPX 수정 시 재생성, 노출 전 검수, 생성 실패 시 노출 차단 여부, 기존 데이터를 덮어쓸지 버전 관리할지, 생성 후 자동 반영 vs 운영자 승인.

### 2차 개발 범위 제안

| 기능 | 포함 |
|---|---|
| 음성 안내 문구 생성, 안내데이터에 음성 문구 필드 추가, SDK 안내 타이밍 판단, SDK 음성 안내 이벤트 제공, 경로 이탈 안내, 완주 안내 | 포함 |
| 경로 복귀 안내, 앱의 음성 on/off 설정 | 포함 권장 |
| 백그라운드 음성 안내, 단말 TTS 직접 재생 | 협의 필요 |

### 삼성에 던질 핵심 질문 9개

1) 재생 주체 2) 문구 제공 3) 범위(시작·방향·이탈·복귀·완주) 4) 사전 안내 거리 5) 백그라운드·화면 꺼짐 6) 앱의 on/off 7) 이탈 안내 기준 거리 8) **1차 주행·이탈·완주 로직은 유지하고 2차는 음성 안내만 추가하는 방향인지** 9) 음성 안내데이터 생성 실패 시 코스 노출을 막을지, 음성 없이 주행하게 둘지.

## 2026-07-16 회의록

**1차 론칭 지연 사유**: 삼성생명이 **의료 마이데이터 연계 업체와 협의·개발**을 진행하며 건강정보 기반 맞춤형 달리기 프로그램 추천 기능을 만드느라 지연됐다.

| 논의 | 내용 |
|---|---|
| 기획안 제공 시점 | 서비스가 드로잉런(초기 컨셉)에서 **건강 중심(의료 마이데이터 연계) 컨셉으로 피봇** 중이다. 더헬스/모니모 반영 형태를 논의 중이고 착수 시점은 미정, **8월 중 제공 예정** |
| 어드민 코스 등록 | 아이나비 API가 제공되면 어드민 작업은 삼성생명이 한다. 응답 방식, 요청, 상태, 실패, 재요청, GPX 생성·등록·저장 방식은 확정이 필요 |
| 음성 안내 포함 여부 | 삼성 내부 검토 중이며 피봇 과정에서 필수 여부를 논의 중이다. 우선 트래킹(음성 내비게이션)만 선 검토 |
| 서비스 예상 일정 | 빠르면 **9월 말~10월 초**. 확정된 협의가 없어 변동 가능 |

**아이나비 내부 확인 사항**
1. 사용자 주행 좌표와 도보/자전거 경로의 **매칭 보정** 여부.
2. **최고 속도 제한** 로직: 도보 속도 상한 판단, 상한 초과 시 기록 미저장 같은 처리 가능 여부.
3. 주행 중 **주기적 데이터 전달**(구간별·시간별 수집 데이터 취득) 가능 여부.

## 해석

7월 회의 시점에는 기획안과 음성 안내 여부가 모두 고객사 내부 결정에 달려 있다. 아이나비가 할 수 있는 선제 작업은 안내데이터 API와 SDK 이벤트 규격을 먼저 확정하는 것이다. ^[inferred]
