# 서울동행맵 컨소시엄 협업 채널 2026

2026-07-16에 열린 외부 협업 채널이다. 처음에는 LBS테크 단독이었고 9-9에 이름을 "컨소시엄 협업"으로 바꿔 아로정보기술 PM 이사와 브로디언(백엔드 협력사) 대표를 초대했다. 참여 주체는 LBS테크(보행 경로·내비 SDK, 앱 개발 일부), 브로디언(백엔드), 아로정보기술(주관사, PM·데이터), 아이나비시스템즈다. 프로젝트 맥락은 [[seoul-donghaengmap-lbs-collaboration]], [[seoul-donghaengmap]]을 본다. 사람은 역할로 적었고, 접속 정보, 토큰, API 키, 공유 링크는 옮기지 않았다.

## 2. SDK 발행과 시연 범위 (LBS테크, 10-22~27)

- 서울시 앱 시연(11월 중순)에 맞춰 아이나비가 1차 10-28, 2차 11-11로 임의 제안했다. LBS테크 역제안은 1차 11-06, 2차 11-13이었다. 아이나비는 1차는 기능보다 통합 확인 목적이라 늦어도 11-03, 2차는 11-13이 통합 마지막 날이라 11-12까지 필요하다고 맞섰다.
- LBS테크 확정안은 **1차 10-30, 2차 11-13**이다. 같은 스레드에 "1차 SDK는 11월 3일 전달"이라는 문구도 있어 어느 쪽이 최종인지는 확인되지 않는다. ^[ambiguous] 백엔드는 1차에 명세서, 2차에 API를 전달하고, SDK 지원 가능 항목은 스프레드시트로 정리해 회신하기로 했다. 아이나비 서버 쪽 일정에는 1차 명세서가 10-29로 적혀 있어 날짜가 더 어긋난다. ^[ambiguous]
- 아이나비 시연 범위안: 10-30에는 앱 전체 UI와 서버 API 연동(목업), 11-13에는 앱 전체 UI와 서버 API 연동(실연동과 일부 목업), 실내외 내비 길안내. 저상버스 예약과 마일리지 적립은 모두 제외한다.
- LBS테크가 물은 "실외 보행+대중교통 수준인지, 실내 지도까지 포함인지"에 대한 직접 답은 채널에서 확인되지 않는다. 10-27 아이나비는 앱 시연 일정이 확정돼 11-13 오전까지 개발 가능 항목과 계획 공유를 요청했고, 12-18을 단위 기능 개발 완료 시점으로 본다고 밝혔다.

## 3. 도보 내비 SDK 연동

### 혼합 경로 (10-13)
- 도보→버스→하차→도보 경로에서 SDK는 **도보 구간만** 안내한다. 합의 방향은 전체 경로 route를 한 번만 받고, 하차 후 도보 구간은 "새 안내"로 시작하는 방식이다.
- 예시 흐름(도보 0, 버스 1, 도보 2, 실내 3, 도보 4): `session.start(journey)`로 여정 등록과 0번 도보 시작 → 도착 콜백 후 앱이 버스 구간 처리 → `session.startWalk(2)` → 실내가 끝나면 `session.startWalk(4)`.
- 안내 화면을 SDK에서 처리할지, 앱이 처리할지, SDK–메인앱 통신은 아이나비가 10월 말에 검토해 다시 논의한다.

### 빌드 환경·CMP
- 빌드 환경 회신(9-9) 표는 [[seoul-donghaengmap-dev-slack-tech-2026]]와 동일하다(Kotlin 2.4.10, AGP 9.3.2, minSdk 29, iOS 16 등). LBS테크는 CMP 기반으로 개발하고 내비 SDK는 앱 `commonMain` 의존성으로 받는다.
- 공개된 아이나비 CMP 지도 SDK는 없고 베타로 개발 중이라(9-21 배포 가능 예상) 우선 공개된 Android·iOS SDK로 검토하도록 했고, 이후 CMP 지도 프로젝트와 가이드를 비공개로 공유했다(값 미수록).
- 10-13 질문: 지도 SDK 0.4.1이 compileSdk 37을 요구하는데 메인앱도 37인가 → 메인앱 compileSdk 37, targetSdk 36. 전맹 화면에서도 [안내 종료] 시 확인 팝업을 띄우는가 → 동일하게 띄운다. 좌표를 주면 현재 위치 주소를 보내 줄 수 있는가 → 가능하나 메인앱 대 앱서버 처리 주체는 시나리오별 검토.

### 음성 안내 규격 (10-01, 10-27)
- LBS테크 구현: 앱 TTS 단일 채널(스크린리더는 `aria-live`를 걸지 않음). 낭독 계기는 행동 이벤트(회전 예고, 회전 시점, 도착), 거리 경과, 사용자 요청 3종이다. 거리 경과는 100m 초과 시 50m, 100m 이하 시 30m, 30m 이하 시 10m 주기이고, 회전 예고는 30m 앞이며 이벤트가 거리 경과보다 우선한다.
- 아이나비 기획의 전맹 외 사양: 계기 7종(안내 시작, 회전 예고 30m 전, 회전 시점 10m 전, 경유지·목적지 도착, 이탈 재탐색, 시설물 진입 전 30m, 거리 경과). 거리 경과는 직진 구간 시작 시 1회와 남은 거리 500m 배수마다 1회이고 직전 낭독에서 200m 이상 걸었을 때만 적용한다. 우선순위는 긴급 > 이탈 재탐색 > 행동 이벤트 = 시설물 = 거리 경과(겹치면 이어 읽기)다.
- 멘트 차이: **전맹은 모두 시계 방향**("3시 방향으로 도세요", "12시 방향으로 464미터 직진입니다"), 전맹 외는 좌/우이며 5갈래 이상·대각선 횡단만 시계 방향이다.
- 쟁점: 5갈래 이상 교차로와 대각선 횡단을 판단할 데이터가 경로 데이터에 없다. LBS테크 링크 길이는 평균 200~300m(노드 간 약 300m), 최대 약 1km라 500m 배수 기준으로는 거리 경과 안내가 안 나오는 경우가 많다. 링크 속성(경사, 파손, 점자블록)이 바뀌는 단위로 연속 안내하며 방향 표현은 꺾임 각도만 쓰고 앱은 `maneuver` 값만 쓴다. 거리 경과 기준(링크 기준 대 다음 행동 지점 기준)의 최종 합의는 확인되지 않는다. ^[ambiguous]
- 10-27 방향지시 면: '누르면 재낭독'은 남은 거리와 방향("12시 방향 464미터 남았습니다(직진입니다)")이며 회전은 노드 도착 전 30m에서 예고하고 10m에서 다시 안내한다. LBS테크 개발자는 회전 예고가 너무 멀고 별도 예고 음성은 필요 없어 보인다고 봤다. 아이나비의 최종 회신은 보이지 않는다.
- 아이나비는 음성 발성 사양을 한 번에 정리해 달라고 요청했고 LBS테크가 정리해 공유하기로 했다. 10-28에 LBS테크가 음성 발화 사양 스프레드시트를 공유했다(링크 미수록, 내용은 미반영). 전맹 모드는 확정 사양이 아직 없다.

## 4. 브로디언: DB·API 설계와 역할 분담

### 협업 방식
- 순서는 "화면정의서·관리자 화면정의서 완료 → DB 설계 → API 연동 규격서"다(10-1). DB는 MySQL 8, 아이나비가 베이스 프로젝트를 제공해 양사가 같이 개발한다.
- 9-15 브로디언이 지하철·즐겨찾기·지하철역(서울)·광진구·저상버스 메시지·예약 정보의 컬럼명을 문의했다. 서비스 중인 동행맵 테이블은 서울시 운영유지보수 업체 확인이 필요한 건으로 보았다. 즐겨찾기는 개인정보(경위도, 주소)라 서버가 아닌 앱에서 관리하는 것으로 정리하고 문서 반영을 요청했다.
- 아이나비는 OpenAPI(yaml) 규격서를 공유했다. `[임시]` 표시는 컨소시엄 제공 규격이 없거나 담당 미정이라 기획 기준으로 먼저 쓴 부분이다.

### 감리 문서 (10-7)
- DD432 클래스 설계서, DD433 인터페이스 설계서(yaml 포함)는 브로디언이 쓴 문서만 업데이트하고 아이나비 것은 정리하기로 했다. ID는 10000번대(`CDD-A10101`, `API-10101`), 표지 제목은 "서울시 교통약자지원 통합플랫폼(서울동행맵) 고도화 구축", 문서 버전 0.91, 꼬리글은 "아로정보기술 컨소시엄"이다.
- 기능 추가: 실외/실내 길찾기 API, 저상버스 예약 화면 API, 스토어 링크 전달(OS 구분, 앱 ID·패키지명 전달, Android는 스토어 URL 전달). 삭제: 앱 메뉴 사용 이력 전송, 길찾기 검색 이력 전송, 오픈소스 라이선스 목록 조회(앱이 관리).
- DD422 DB 설계서에서 누락된 테이블·컬럼을 점검했다. `tbl_service_maintenance`(서비스 점검, 이후 추가된 기획), `TBL_APP_VERSION.store`(설치 출처 스토어 4종: GOOGLE, GALAXY, ONESTORE, APPSTORE, 미전달 시 OS별 기본값) 등이 대상이다. `TBL_OPNSRC_LCN_INFO`(오픈소스 라이브러리 관리)가 v0.93에 남아 있어 이유를 물었으나 답은 확인되지 않는다.

### DB 설계서 v0.93 불일치 문의 (10-20)

| 항목 | 결론 |
|---|---|
| REG_ID·MDFCN_ID(서버가 자동 생성하는 행) | 서버용 고정 ID 값 두 종류(앱 서버용, CMS용)를 쓴다 |
| USE_YN(회원 상태) | 회원 `Y`, 비회원 `G`(처음 `N`에서 변경), 미사용(삭제) `N`, 탈퇴 `W` |
| USER_ID 길이 | 30자 유지(행안부 표준용어 기준, UUID 32자를 잘라도 중복 가능성이 거의 없다고 판단). 아이나비가 30자 유지에 동의 |
| SOCL_USER_ID, SNS_UPDT_TKN | 평문이 아니라 암호화 저장, 길이 1000자 |
| LANG_CD | 코드 5개(KO, EN, JA, CN, TW)에 홍콩 번체 `HK` 추가해 6개 언어 |
| TBL_TAXI_CALL.SRVC_CD | 컬럼 추가(40자, 필수, 중복 불가). 값은 `DISABLED_CALL_TAXI`, `WELFARE_CALL`, `MOM_DAD_TAXI_TADA`, `MOM_DAD_TAXI_PAPA`로 앱이 서비스별 다국어 이름을 붙이는 구분자 |

### 역할 분담안 (10-20, 10-27)
- 브로디언: 대중교통 정보(ODSay 연동), 저상버스 예약 중계, 불편신고 등록·조회·수정과 마일리지(티머니), MQTT 서버, 상용 인프라, 대화형 AI.
- 아이나비: 계정·인증(앱 시작 초기화, SNS 로그인, 회원가입, 닉네임 확인, 로그아웃, 탈퇴), 개인 설정(내 계정, 교통약자 유형, 글자 크기, 앱 언어, 닉네임), 택시 호출 연락처 설정값, 장소 검색·상세와 좌표→주소, 길찾기 실외·실내 연동.
- 공통: 인증·세션·전송 암호화·파일·오류 응답.
- **연동 방침**: 앱은 아이나비 App Server만 호출하고, 브로디언 소관 기능은 아이나비 규격서의 엔드포인트 뒤에서 데이터를 공급한다. 일부는 목업, 없는 엔드포인트는 기획 기준으로 아이나비가 만들어 계속 공유하며, 규격 변경은 먼저 협의 후 아이나비가 규격서에 반영한다.
- 10-27 서버 일정: 구현 완료는 로그인·회원가입, 택시 호출, 마이페이지(계정 조회, 유형·글자 크기·언어·닉네임 변경, 탈퇴, 공지, 약관, 의견 보내기)다. 장소 통합 검색·상세·리버스지오코딩은 아이나비와 LBS테크를 호출해 머지하며 금주 구현 예정이다. 길찾기(경로 리스트·상세경로)는 앱 연결 엔드포인트(규격 1.0.48)가 열려 있고 ODsay 샘플 목업으로 응답한다. 실내 안내 역사 범위 API는 11개 역사 폴리곤을 받으면 바로 동작한다.
- 임시 개발 장비는 아이나비 서버 담당이 구성했고 접속 정보는 DM으로 전달했다(값 미수록). 서버 레포에 배포 태스크가 있어 개인 설정 파일에 접속값을 넣고 한 번에 빌드·업로드·재기동한다.
- ODSay 키: 9-10 대중교통 API 키 발급을 약속했고, 대중교통 정보는 직접 연동이 필요하다는 아이나비 의견에 대해 브로디언이 LBS테크 처리 여부를 확인하기로 했다. 10-26 브로디언이 개발용 키를 요청했다(값 미수록). 최종 발급 여부는 확인되지 않는다.
