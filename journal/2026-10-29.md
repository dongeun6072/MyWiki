### 컨소시엄 협업 → [[seoul-donghaengmap-consortium-slack-2026]]

- **브로디언 연동규격서 v101 이식**: 서버 개발이 브로디언이 준 `AS_연동규격서-v101`을 기획과 기존 구조에 맞춰 검토하고, aro 폴더의 불편신고·대중교통·마일리지 코드를 아이나비 구조로 이식했다. 컨트롤러·DTO·enum은 OpenAPI 생성 코드로 바꿨고, 서비스 로직은 `svc/*ApiSvc.kt`에 두어 이후 브로디언이 그 안에서 고친다. 앱 통신 필드명·타입이 바뀌어 항목별 요청 문서(`REPORTS-`, `TRANSITS-`, `MILEAGES-API-CHANGES.md`, `EXCLUDED-APIS.md`)를 서버 저장소 `broadian/` 폴더에 두었다. 아이나비 분담이라 뺀 API는 택시 호출 연락 수단 조회, 장소 통합 검색, 장소 상세, 좌표 기반 주소 조회다.
- **저상버스 예약 구조 불일치**: 기획은 신청을 앱에만 저장하고, 앱이 조건(반경 50m, 예약 차량 2→1정거장 전)을 확인하면 서버를 불러 서버가 BMS에 예약을 전달하며, 확정된 예약은 취소할 수 없다. aro 코드는 신청 즉시 서버 DB에 저장하고 신청·확정 모두 취소할 수 있으며 BMS 전달이 없다. 이식하지 않고 브로디언에 구조 변경 가능 여부를 물었다(별도 협의).
- **DB 표준용어와 감리**: 브로디언이 DB는 행안부 2025년 표준 기준으로 설계했으니 필드 추가·수정은 표준용어·표준단어사전을 검토해 공유해 달라고 했다. 서버 개발이 API 요청·응답 필드명(예: 앱 필드명 대 DB 표준단어)까지 감리 대상인지 묻자, DB 감리는 테이블·쿼리 대상이고 API 감리는 별개라 매핑 문서를 요구할 수 있다는 개인 의견을 받았다. 의견 테이블의 `OPNN` 약어처럼 사전에 없으면 만들어 공유하면 브로디언이 사전에 등록한다. API 규격과 앱 필드명을 미리 표준용어에 맞출지는 아이나비 내부 논의가 필요하다는 의견이 나왔다.
- **LBS테크 실외 길안내 API·SDK 1차 전달**(18:38): 연동규격서 v1.0.0(xlsx), Swagger html, openapi.json, 목업 응답 JSON 6종, `lbstech-navi-sdk-0.1.0`을 전달했다. API는 경로 탐색 `GET /dongheng/routes`(도보·대중교통, 경유지 1곳, 경로 리스트·상세경로·실외 내비 화면용), 노선 선형 `GET /dongheng/lane`(상세경로 지도, 상세 화면을 열 때만), 목업 `GET /dongheng/mock/routes?scenario=transit|via|walk|near`와 `/dongheng/mock/lane`이다. 필드는 snake_case, 도보 구간 geojson은 기존 `/pathfinder` 응답과 같은 형식, 교통약자 유형 `user_type`은 WS(휠체어·유모차), SP(고령자·임산부), LV(저시력), TB(전맹)이다. 재탐색 때 같은 대중교통 경로인지는 `map_obj`로 비교하고, 요금은 일반(성인) 교통카드 기준, 실시간 도착 정보는 없다(아로 API 서버 제공). 운영에서는 아로 API 서버가 이 API를 불러 앱에 전달한다. SDK는 실외 내비 화면의 턴바이턴 안내에 쓴다. **개발용 서버 주소와 API 키, 호출 한도 정보가 메시지 원문에 있음(미수록).**
